# Local model benchmark scenario-to-oracle matrix

**Status: proposed research aid; not a benchmark corpus, approved protocol, or qualification result.** This maps candidate scenario classes to evidence SideEffect already exposes. It does not assert that existing development fixtures have independently reviewed labels. Use it with the [proposed qualification protocol](LOCAL_MODEL_QUALIFICATION_PROTOCOL.md); keep model quality no-go until a platform-specific, independently reviewed holdout and frozen acceptance criteria exist.

## Evidence and oracle map

| Scenario class | Linux `strace` evidence and deterministic oracle | Native Windows ETW evidence and deterministic oracle | Required interpretation / open gap |
|---|---|---|---|
| Supported, answerable syscall question | `sideeffect.explanation` `result_facts[]`: `syscall`, `outcome`, `meaning`, and exact `evidence` in `src/explain.rs`; the explanation selector assigns bounded evidence IDs in `src/local_model_explanation.rs`. Oracle: source trace row plus reviewed semantic label. | `model_explain` Windows preview rows: `evidence_id` (`W…`), `payload_decode_status`, corroborated `payload_observation`, and `evidence` containing capture digest, record ordinal, JSON pointer, and raw-payload digest in `src/local_model_explanation.rs`. | Compare semantic support, not only valid IDs. ETW labels are usable as decoded event observations only when raw payload re-decoding exactly matches the serialized sidecar. The Windows source does not establish the same syscall-level semantics as Linux. |
| Successful operation versus failed attempt | `SyscallOutcome` and `ResultMeaning` distinguish recognized success, recognized `-1/errno` failure attempt, `EINPROGRESS` for `connect`, and unknown result (`src/explain.rs`). Oracle: exact syscall result record and parser classification. | ETW decoded file/network/disk observations identify supported event fields and payload status. | A failed Linux attempt does not establish a higher-level effect. Windows FileIo/Network/DiskIo payloads do not establish operation success; do not use them as a success/failure oracle. |
| Process creation and relationship | `process_relations[]` provides `caller_task_id`, `child_pid`, `evidence`, and `supporting_evidence` (`src/explain.rs`). Oracle: the exact process-creation result row and its retained related trace rows. | Header `process_id` and `thread_id` are context only. Imported process-payload facts can be unknown when the required live TDH schema is unavailable. | Linux `caller_task_id` may be a TID under `strace -f`; it is not necessarily an OS parent PID. ETW header PID/TID alone cannot establish process ownership, lineage, or causation. Build separate, reviewed Windows process-start cases only where source evidence supports the claim. |
| Partial parsing, truncation, and capture limits | `parse_status`, `capture_completeness`, `known_unknowns`, omitted fact/reference counters, parser diagnostics, and process-lineage diagnostics in the deterministic explanation. Raw trace parsing does not prove capture completeness. | `source_status`, `parse_status`, `capture_completeness`, event-loss values and availability, `diagnostics`, `decoder_mismatch_or_unknown_count`, and per-row `payload_decode_status`. | Oracle must require uncertainty/abstention when relevant evidence is omitted, malformed, unsupported, or incomplete. Exercise each case class independently and retain the exact source artifact. A complete parse is not proof of complete capture. |
| Empty, ambiguous, unsupported-scope, and absence-seeking questions | Query plans support explicit `decision=abstain` with a closed `abstain_reason`; explanation coverage and unknown fields constrain answerability. The current development corpus has examples, but it is not a release holdout. | ETW preview carries capture status, diagnostics, loss availability, and decoded/unknown event rows; a zero matching row has no system-wide meaning. | Label answerability from the supplied scope and available evidence, never from presumed system truth. “No row found” cannot be labeled “nothing happened.” Include false associations, unknown records, and questions asking for proof of absence. |
| Citation validity and evidence injection | Selectors accept only enumerated evidence IDs and map them back to exact preview rows. Query results retain evidence IDs/references. | `W…` references bind to a capture fingerprint, ordinal, JSON pointer, and payload digest. Header context is explicitly labeled non-ownership data. | Score both reference resolution and semantic support. Include instruction-like paths, names, arguments, and metadata as inert data; test unknown/duplicate IDs, reordered rows, and attempt to cite an unprovided record. |
| Natural-language query plan | `LocalQueryPlan` and `QueryFilters` in `src/local_query_plan.rs` define a closed syscall plan; deterministic execution returns exact filtered rows and their evidence. The supported filter contract includes syscall, outcome, errno, lexical path, process/caller/child identifiers, and relation type. | `EtwPlan` / `EtwFilters` in `src/windows_etw_query_plan.rs` define a separate native-Windows-x86_64 ETW-only contract. It selects exact event/operation/transport/path/network payload fields from raw-payload/sidecar-corroborated ETW v3 observations and returns `W…` locators. It has deterministic contract tests but no semantic evaluation or quality qualification. | Ground truth is the full platform-specific plan, deterministic result set, and abstention decision. Never score ETW fields as Linux syscall entities/outcomes or infer Windows quality from Linux traces or Windows-hosted Linux fixtures. |
| Reordering, duplicates, and equivalent wording | Existing Linux development corpora include permutation groups; oracle comparisons should use semantic source-row identity rather than generated IDs. Query-plan cases can compare complete plans and resulting evidence rows. | ETW evidence uses record ordinals and capture digests; permutations must preserve the intended source identity mapping and exact per-capture references. | Require group-level consistency and citation remapping after reorder. Existing permutation samples are diagnostics until expanded, independently reviewed, and frozen in a holdout. |

## Corpus and release-readiness gaps

- The current Linux explanation and query-plan corpora are development material; their labels are not an independently reviewed qualification oracle. The recorded evidence-selection and query-plan candidates failed their frozen gates.
- Windows ETW explanation has a separate four-case, two-pinned-synthetic-capture development corpus and source-specific evaluator/runner (`tests/fixtures/local_model_windows_etw_explain_v1/`, `scripts/evaluate_local_model_windows_etw_explain.py`, and `scripts/run_local_model_windows_etw_explain_corpus.py`). The new Windows x86_64 ETW query-plan contract has no semantic corpus/evaluator yet. No Windows ETW model task has an independently reviewed or qualified holdout; contract tests and structural validation do not establish model quality.
- No single approved benchmark currently compares each model task with a deterministic baseline over the same unfiltered facts and reports per-platform answerability, citation support, abstention, unsupported claims, privacy behavior, and measured resources.
- The current ETW explanation path intentionally leaves process payloads unknown where imported captures lack live TDH schema. Benchmark questions must not assume those fields are available.
- Candidate-specific pass criteria, reviewer independence, corpus size, resource limits, and decision rules remain to be proposed, reviewed, and frozen before inference. Do not tune a candidate against a holdout or weaken a gate after observing results.
