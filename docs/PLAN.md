# SideEffect Delivery Plan

**Status:** implementation is underway; this is not a schedule or release claim. Bounded `inspect`, conservative `diff`, exact-reference `evidence` lookup, terminal-safe text output, Linux-only static HTML export, Linux `record --trace`, and opt-in `record --bundle` plus Linux inspection of its strict v1 bundle format are implemented. Bundle writing publishes `run.json` and `trace.strace` atomically as one private sibling directory using a no-clobber rename; bundle inspection validates the schema, fixed entries, ownership/modes, size bounds, trace length, and SHA-256 before parsing. A Linux integration test exercises real strace captures of a child's successful `execve`, represented as one complete row or separate continuation rows depending on tracer output, a temporary file operation, and loopback-only TCP activity through record, inspect, and diff; WSL runs used task-local extracted Ubuntu strace packages 6.8 and 6.19, without system installation. The hosted CI run at commit `30aa11968de0ad89d54054bf4e554c85b5286107` passed Linux, Rust 1.85 MSRV, Ubuntu 24.04 strace integration, and Windows jobs on 2026-10-25; the dependency advisory and declared-license jobs passed on earlier commits. SideEffect's declared strace minimum is 6.8, the lowest version exercised by real-tracer integration; other tracer versions, kernel/distribution combinations, broad syscall coverage, and browser compatibility remain unverified. See the [compatibility and observation matrix](INSTALL.md#compatibility-and-observation-matrix).

## Current implementation slice


`sideeffect inspect TRACE` reads a regular local file, accepts a bounded subset of `strace` text, preserves raw lines and source byte offsets in a schema-v4 JSON document, and writes that document to stdout. Its `outcome` field is attached only to complete `execve`/`execveat`, `openat`/`openat2`, and `connect` records. It reports `success` only for strict recognized successful results, `failure` only for strict Linux `-1 ERRNO (message)` results, `in_progress` for strict `connect` `EINPROGRESS` results, and `unknown` otherwise. This is a syscall-result summary; raw results and records remain unchanged and authoritative. Unfinished/resumed rows and other syscall names have no outcome field. `sideeffect inspect --bundle DIR` accepts the current Linux `sideeffect.run` v1 bundle, verifies its strict manifest, private fixed files, trace length, and SHA-256 before parsing, and produces the same document as inspecting the raw trace without including the bundle path. The manifest cap is 16 KiB and the trace uses the existing 32 MiB cap. Its `source_sha256` fingerprints the exact bounded byte buffer parsed. For `openat` and `openat2`, it may include an optional `lexical_path_hint` derived from a plain printable-ASCII path and an absolute `-yy` directory annotation; the hint does not query the filesystem, normalize path segments, follow symlinks, or establish descriptor identity. Earlier trace schemas v1-v3 and diff schemas v1-v2 are standalone; the CLI reads raw `strace` text only and does not import/migrate prior SideEffect JSON exports. `sideeffect inspect --format text TRACE` writes an ASCII-only terminal-safe view of every parsed, control, and unparsed row plus parser diagnostics and labels any hint as lexical. `sideeffect diff LEFT RIGHT` compares completely parsed raw trace inputs and writes schema-v3 JSON observed deltas with source offsets and separate left/right SHA-256 fingerprints; it includes optional side-specific lexical path hints as display-only fields, while `matching_policy.exact_fields` documents exact row/result comparison and `matching_policy.display_only_fields` explicitly excludes the hints. Fingerprints identify bytes only; they do not authenticate capture or establish completeness. `sideeffect evidence TRACE SHA256 LINE BYTE_OFFSET BYTE_LENGTH` verifies the supplied lowercase fingerprint against the exact parsed bytes before checking the source tuple against exactly one parsed syscall row. Partial input is labeled, and malformed/mismatched fingerprints and control, unparsed, out-of-range, or mismatched tuples are rejected. A successful lookup establishes byte identity relative to the supplied fingerprint and position within those bytes; it does not establish authenticity or capture completeness. Fingerprints are sensitive metadata, can reveal equality, and may be guessable for low-entropy traces; trace bytes are not uploaded. `sideeffect diff --format text LEFT RIGHT` writes a human-readable ASCII-only view with terminal controls escaped and clearly labels path hints as display-only. Linux `sideeffect diff --format html --output REPORT LEFT RIGHT` writes a bounded static offline report, with no scripts or remote assets, mode 0600, and no-clobber publication. It omits local input paths but can contain sensitive trace values. Parser and diff fixtures remain synthetic. The Linux integration test uses the real tracer for a narrow file plus loopback scenario; compatibility with broader tracer output remains unverified.
`sideeffect diff-summary` writes a separate `sideeffect_redacted_diff_summary` schema containing only added/changed/removed diff-group counts by fixed category. Its schema omits syscall names, raw arguments/results, lexical hints, source fingerprints, evidence references, and local input paths. It does not detect secrets or certify that the remaining counts are safe to share. JSON is written to stdout; Linux HTML is capped at 64 MiB, mode 0600, and published without replacing an existing file. This command uploads nothing and is not a redacted detailed diff.

Current hard limits are 32 MiB per input file (64 MiB combined for a diff), 64 KiB per physical record excluding LF, 100,000 records per input, 200,000 diff rows, and 64 MiB for serialized JSON, text, or HTML output. These initial values need review against real captures. `parse_status` describes syntax/continuation parsing only and cannot establish capture completeness. The diff fails closed on partial parses, ignores only parser-level PID/timestamp prefixes when matching, compares exact arguments/results, treats rows as a multiset, and reports excluded control-row counts. It emits a changed row only when exactly one unmatched same-signature record remains on each side; ambiguous result multiplicities remain additions/removals. Before/after references point to the first/second CLI input respectively. Unfinished and resumed rows remain separate observations.

## Product target beyond the current implementation

The product goal is an on-demand, local audit of software on a supported computer. It is broader than the current selected-command trace comparison. A completed product should combine source-linked software/process inventory, readable permission/configuration facts, startup-hook/script inventory, and observed activity from an explicitly bounded capture. It must separate configured facts, observed behavior, derived comparisons, and AI-generated interpretation. Each audit states what was checked, what was inaccessible, and what is unknown. No background daemon or continuous monitoring is part of the target.

The initial inventory and observation platform remains Linux x86_64. Native Windows support requires a separately designed platform adapter and is not implied by WSL2. Platform-specific permission and startup mechanisms must be named individually; the product must not suggest that it has an exhaustive or cross-platform permission model. The optional local LLM is a later, opt-in layer that can summarize selected evidence only; it cannot execute commands, change settings, or replace evidence. Cloud inference, telemetry, and automatic privilege escalation remain out of scope.

Milestones 6–9 below extend the v0 technical foundation and are required for the broader product target. Milestone 6 now has on-demand Debian package and visible `/proc` status snapshots; permission/ACL coverage remains planned. Milestone 7 has a first Linux XDG autostart discovery slice; systemd and non-XDG startup sources, effective applicability, and Milestones 8–9 remain unimplemented.

## Milestone 0 — Repository and dependency decision

- Review repository guidance and existing project state before implementation.
- Confirm available Rust toolchain and Linux x86_64 development/test environment; do not install a toolchain without explicit authorization.
- Define the supported `strace` minimum, exact initial capture profile, storage layout, and JSON schema policy. SideEffect now enforces strace 6.8 or newer, the lowest version exercised by real-tracer integration; `--kill-on-exit` itself was introduced in 6.6 ([release notes](https://strace.io/files/6.6/)). The exit-status contract propagates strace's reported code or signal only after successful trace publication; the parser's current schema-v4 inspection document is separate from the run-bundle schema.
- Record explicit resource budgets before parser/report implementation. `inspect` currently uses 32 MiB input, 64 KiB physical records, 100,000 records, and a shared 64 MiB JSON/text output cap; validate these values against real captures before release. The initial diff is bounded to 200,000 rows and the same JSON/text output cap; define further budgets for capture bundles and future report features.
- Decide the Linux filesystem operations needed to create evidence bundles and atomically publish reports without following attacker-controlled symlinks or replacing existing user files. See [SECURITY.md](../SECURITY.md).
- Resolve licensing and packaging implications of depending on an external `strace` executable before distribution.

**Exit criteria:** written implementation decisions identify supported platform/tool versions, known observation limits, status/error semantics, documented resource budgets, safe no-follow/no-clobber output semantics, and unresolved items. No unsupported native Windows promise.

The initial Rust/MSRV and parser limits are recorded in `Cargo.toml` and `src/limits.rs`. The recorder now declares strace 6.8 as its tested minimum; exact integration versions and remaining compatibility gaps are listed in [INSTALL.md](INSTALL.md#compatibility-and-observation-matrix). Compatibility with every later release and kernel/distribution combination is not established. Final release budgets remain open.

## Milestone 1 — Capture a single run

The first bounded recorder slice is implemented as `sideeffect record --trace OUTPUT -- PROGRAM [ARGS...]`. It sends strace output to a generated private FIFO, enforces the same 32 MiB cap as `inspect`, and publishes a non-empty raw trace only if the output name remains unused. Overflow kills only the direct strace process and discards the staged file. Traces are staged with mode 0600 in a private mode-0700 directory; command stdout/stderr remain inherited. strace introduced `--kill-on-exit` in 6.6, but SideEffect's tested minimum is 6.8; the option is only best-effort cleanup; descendants created with `CLONE_UNTRACED` can escape tracing. A Linux integration test records two small Python targets: both create unique temp files, the baseline opens a TCP connection to a local `127.0.0.1` listener, and the candidate starts a fixed Python child. The child's successful `execve` may appear as one complete row or as unfinished and matching-PID resumed rows, depending on tracer output; the parser keeps continuation rows separate. The paired diff asserts the observed child row and its evidence reference without reconstructing a logical call. The test captures command output in memory, checks selected fixture sentinels do not appear there, and verifies its private temp directory is removed. The workflow has no artifact-upload step. The test fails if `strace` or `python3` is missing; Linux CI installs those packages before running it. The WSL integration test passed with extracted, non-installed Ubuntu strace 6.8 and 6.19 packages. This narrow case does not validate other tracer versions, broad syscall coverage, or all kernel combinations. `--syscall-limit` detaches tracees after a call count and must not be treated as a complete run. Never pass a user-controlled `-o` value directly: strace treats output names beginning with `|` or `!` as commands. See the [`strace(1)` manual](https://man7.org/linux/man-pages/man1/strace.1.html).

- Exercise `record` against a real supported strace version and a harmless shell-free target; confirm the selected option profile and FIFO output behavior.
- Decide whether to capture tracer diagnostics/version metadata and how to distinguish tracer failure from target exit. The current CLI inherits strace stderr, propagates its reported status only after publishing a nonempty trace, and does not independently verify command status or tracer success.
- Validate cleanup behavior and document that this is not a sandbox and may not terminate descendants that escape tracing.
- Test output caps, no-clobber publication, symlink safety, and cleanup on real tracer startup and termination failures.
- `record --bundle DIR` writes the initial `sideeffect.run` v1 manifest and the exact bounded raw trace as one directory containing only `run.json` and `trace.strace`. The manifest omits command/program/argv, environment, cwd, username, absolute paths, output streams, tracer diagnostics, and event copies. It records the SideEffect and parsed strace major/minor versions, fixed capture profile, raw strace status, explicit unverified/unknown outcome markers, and exact trace length/SHA-256. Bundle files are mode 0600 in a mode-0700 directory; files and staging directory are synced before atomic sibling `renameat2(RENAME_NOREPLACE)`. Prepublication failure, overflow, and cancellation discard staging. If the post-rename parent-directory sync fails, the complete bundle is already visible and the CLI warns that persistence across sudden power loss is uncertain while propagating the recorded strace status. Bundle creation and inspection are Linux-only; there is no schema migration.
- Follow child processes where the chosen trace mode supports it.
- Keep command status distinct from tracer/parser/report failures.

**Exit criteria:** broader automated real-tracer integration covers a child execution and selected file/network calls; command stdout/stderr and exit result are handled according to the documented contract; missing tracer and tracer failure produce clear diagnostics; raw records remain inspectable; output tests prove an existing destination or symlink target is not overwritten/followed and failed writes do not publish partial final bundles. Linux integration tests exercise ordinary successful capture, a target exiting with status 37, a target terminated by SIGTERM, inherited target stdout/stderr, and a child `execve` attempt that fails with `ENOENT`, checking that evidence remains inspectable and the trace is published before SideEffect propagates the reported outcome. The capture integration suite passed locally with Ubuntu `strace` 6.19 and in hosted Linux CI, including Ubuntu 24.04 compatibility and Rust 1.85 MSRV jobs. These tests do not independently prove capture completeness, and the feature remains early and partially validated, not release-ready.

## Milestone 2 — Parse and model evidence

- The initial `inspect` parser is implemented for the documented bounded text subset. Continue validating it against real supported `strace` captures and add explicit format/version support before release.
- Phase 1 of the versioned run record is implemented as the opt-in `record --bundle` writer. Its `sideeffect.run` v1 manifest references the exact raw trace by fixed bundle filename, byte length, and SHA-256; it does not reconstruct events or prove authenticity/completeness. Bundle migration remains open.
- Direct comparison of two validated Linux v1 bundles is implemented as `diff --bundles LEFT_DIR RIGHT_DIR`; it reuses the strict bundle reader, then applies the existing parser and diff contract. Bundle migration and imported SideEffect JSON remain out of scope.
- Represent process, file, and connection-related observations without overstating success or identity.
- Track parse errors, unsupported records, and detectable incomplete/truncated input.

The parser and renderer must enforce the explicit budgets recorded in Milestone 0. Test each chosen file, record, string, event/collection, comparison, and rendered-output limit at the accepted boundary and just beyond it. Oversized, malformed, and truncated input must not cause unbounded allocation or silent truncation.

**Exit criteria:** fixture tests cover success/failure returns, child processes, conservative lexical path hints and unresolved cwd/dirfd cases, concurrent or unfinished calls, malformed and unsupported records, and evidence-reference integrity. Full filesystem path resolution remains open; unresolved path or process data must remain explicitly unresolved.

## Milestone 3 — Compare two runs

- The first `diff` slice is implemented for completely parsed trace documents. It groups raw syscall rows as a multiset, ignores only parsed PID/timestamp prefixes for matching, compares exact syscall names, arguments, and results, and links deltas to source offsets.
- Control rows are excluded from the initial event comparison, with per-input counts in the JSON output. Unfinished and resumed rows are retained and compared as separate observations rather than reconstructed into logical calls.
- Process/file/network labels are transparent syscall-name buckets, not claims about completed effects. The report says capture completeness is unknown; parser completeness does not establish absence of events.
- Extend matching only with independently justified rules for run-local identities. Keep descriptor/path uncertainty visible and preserve original values in source evidence. Never apply blanket path or file-descriptor normalization.

**Exit criteria:** fixture pairs cover timestamp/PID-prefix changes, added/removed/changed observations, duplicate multiplicity, and unstable event ordering; incomplete input is rejected; every emitted delta links to source evidence; any future normalization is explicit and never destroys raw values. The current exact-argument matcher can still report changes caused by run-local values inside arguments or results; resolve those only through separately reviewed rules.

## Milestone 4 — Export human-readable output and offline HTML

- Versioned JSON diff output is implemented.
- `inspect --format text` is implemented as an ASCII-only listing of every parsed/control/unparsed record and diagnostic. It may show the narrowly scoped lexical path hint; it does not canonicalize paths or infer syscall effects.
- `diff --format text` is implemented as an ASCII-only terminal view; escape trace-derived controls, quotes, backslashes, and non-ASCII scalars and enforce the shared output cap.
- Linux `diff --format html --output REPORT LEFT RIGHT` renders a self-contained offline report with static CSS, no scripts or remote assets, escaped trace-derived content, evidence references, and instructions for checking a cited row with `sideeffect evidence`. Input paths remain omitted; before/after evidence maps to the first/second CLI inputs.
- The HTML report shows comparison context, observed changes, and uncertainty; rendering is capped before no-clobber publication.
- State clearly that reports may contain secrets and are not automatically sanitized; HTML file export is currently Linux-only.

Report generation must enforce the documented event/string/output budgets. Create completed reports atomically without following destination symlinks or replacing existing files; define cleanup behavior for failed or interrupted writes.

**Exit criteria:** schema/round-trip tests pass; HTML tests prove trace-provided markup is inert and no remote assets are required; incomplete captures are conspicuous; export failures do not corrupt raw run evidence. Typed integration round-trips now cover inspect schema v4 and diff schema v3 JSON. Current renderer tests cover static markup safety and a keyboard skip link/main landmark; browser compatibility and broad accessibility review remain open.

Additional exit criteria: report generation respects documented event/string/output budgets; completed exports are published atomically without following destination symlinks or replacing existing files; interrupted or failed exports leave no partial final report and do not corrupt raw run evidence.

## Milestone 6 — On-demand software and permission inventory

The first slice is implemented as `sideeffect inventory packages --output FILE`: a user-triggered, read-only, point-in-time snapshot from the local Debian dpkg package database on Linux. It records source scope, capture time, source and overall status, package fields, per-row evidence references, and diagnostics in `sideeffect.inventory` v1 JSON. The fixed `/usr/bin/dpkg-query` query runs with a cleared environment and no privilege escalation. The bounded output file is mode `0600`, does not replace an existing destination, and remains until the user deletes it. Incomplete or unavailable source data is represented as partial/unknown and exits with status 2.

This is not a complete software inventory: manually copied and otherwise unregistered programs are outside dpkg's database. The separate Linux process snapshot reads only bounded numeric `/proc/PID/status` entries; it omits command lines and executable paths, records an explicit non-atomic observation interval, and marks missing, malformed, unreadable, vanished, and limit-omitted data partial. It does not establish exhaustive procfs visibility. Permissions and ACLs and broader inventory sources remain planned work. A narrow Linux XDG autostart file discovery slice exists; it reports selected configuration keys and other nonempty `[Desktop Entry]` lines as evidence only when within the 64 KiB physical-line bound. It examines at most 100,000 physical lines across a scan; reaching this limit produces a source-location diagnostic and partial status. Overlong lines produce a line/byte-offset diagnostic without retaining their contents and make the source partial. Invalid UTF-8 values are represented as hex, while source paths are serialized with lossy UTF-8 conversion and therefore do not preserve non-UTF-8 path bytes faithfully. Applicability remains unevaluated; this is neither effective nor exhaustive startup inventory. Other startup hooks/scripts remain planned work.
- Inspect selected file ownership, mode, and ACL data using documented system sources such as [`getfacl`](https://man7.org/linux/man-pages/man1/getfacl.1.html); report process credentials and Linux capability sets separately. These inputs do not prove the effective access decision in every namespace or security-module context.
- Collect only through bounded, read-only operations; make scope, collection time, source, and source-specific coverage visible.
- Report inaccessible or unsupported sources as unknown/not checked. Do not automatically elevate privileges.
- Keep inventory snapshots local and sensitive; give users an explicit output path and deletion guidance. Package names, versions, architecture, and raw source rows can reveal installed software and system details; review before sharing and delete when no longer needed.

## Milestone 7 — Startup hooks, scripts, and runtime evidence

- Extend the implemented first slice of bounded Linux XDG autostart `.desktop` discovery with the planned Linux [`systemd` service units](https://freedesktop.org/software/systemd/man/latest/systemd.service.html) and other startup sources. Keep discovered configuration inert, with source-file and configuration references; never execute discovered commands or scripts.
- Let the user request a bounded capture of a selected program or process tree, then connect observed events only when the evidence supports that link.
- Distinguish configured hooks/scripts from ones observed executing. Do not claim that absence from a snapshot proves a hook or behavior does not exist.
- Review the resulting coverage by platform and avoid any “everything observed” guarantee.

- Require source references for factual claims; never let the model launch commands or modify the system.

## Milestone 9 — Native Windows audit adapter

- Design a native Windows read-only inventory and bounded runtime-evidence adapter; do not treat WSL2 as Windows coverage.
- Start with [uninstall registry entries](https://learn.microsoft.com/en-us/powershell/scripting/samples/working-with-software-installations), a [Tool Help process snapshot](https://learn.microsoft.com/en-us/windows/desktop/ToolHelp/taking-a-snapshot-and-viewing-processes), [access tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-tokens), [file security descriptors and ACLs](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [Run/RunOnce keys](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys), [Startup folders](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid), [service configuration](https://learn.microsoft.com/en-us/windows/win32/services/service-configuration), and [scheduled-task definitions](https://learn.microsoft.com/en-us/windows/win32/taskschd/about-the-task-scheduler). These are curated sources: Microsoft documents that software inventory does not find every application, and inaccessible processes or entries must remain unknown. Avoid `Win32_Product`, whose installer checks can alter machine state.
- Evaluate bounded runtime collection through [Event Tracing for Windows (ETW)](https://learn.microsoft.com/en-us/windows/win32/etw/about-event-tracing) as a separate capability. Document provider/filter scope, event loss, and [session permissions](https://learn.microsoft.com/en-us/windows/win32/etw/controlling-event-tracing-sessions); do not elevate automatically or imply that ETW captures every event.
- Keep the same evidence, scope, collection-time, unknown-state, no-background-monitor, and no-automatic-elevation guarantees as other adapters.
- Validate Windows-specific privacy and security boundaries separately; do not reuse Linux coverage claims.

Milestones 6–9 are product requirements, not v0 exit criteria. The Debian dpkg package snapshot and bounded Linux process-status snapshot are implemented first slices of Milestone 6; bounded Linux XDG autostart discovery is the first slice of Milestone 7. The XDG slice is limited to 100,000 physical lines per scan and has bounded file and line coverage; it does not preserve overlong line contents and renders non-UTF-8 paths lossily. Discovered entries do not establish applicability. Permission/ACL inspection, systemd and non-XDG startup sources, effective applicability, broader source coverage, and Milestones 8–9 remain unimplemented.
