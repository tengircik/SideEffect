# SideEffect Delivery Plan

**Status:** implementation is underway; this is not a schedule or release claim. Bounded `inspect`, conservative `diff`, exact-reference `evidence` lookup, terminal-safe text output, Linux-only static HTML export, Linux `record --trace`, and opt-in `record --bundle` plus Linux inspection of strict v1 and v2 bundle formats are implemented. Bundle writing publishes `run.json` and `trace.strace` atomically as one private sibling directory using a no-clobber rename; bundle inspection validates the schema, fixed entries, ownership/modes, size bounds, trace length, and SHA-256 before parsing. A Linux integration test exercises real strace captures of a child's successful `execve`, represented as one complete row or separate continuation rows depending on tracer output, a temporary file operation, and loopback-only TCP activity through record, inspect, and diff; WSL runs used task-local extracted Ubuntu strace packages 6.8 and 6.19, without system installation. The hosted CI run at commit `a6bb3a7a2b2a691f182bf7fbc194f8bb7a703721` passed Linux, Rust 1.85 MSRV, Ubuntu 24.04 strace integration, and Windows jobs on 2026-10-25 (run [40204100065](https://github.com/tengircik/SideEffect/actions/runs/40204100065)); the dependency advisory and declared-license jobs passed on earlier commits. SideEffect's declared strace minimum is 6.8, the lowest version exercised by real-tracer integration; other tracer versions, kernel/distribution combinations, broad syscall coverage, and browser compatibility remain unverified. See the [compatibility and observation matrix](INSTALL.md#compatibility-and-observation-matrix).

## Current implementation slice


`sideeffect inspect TRACE` reads a regular local file, accepts a bounded subset of `strace` text, preserves raw lines and source byte offsets in a schema-v7 JSON document, and writes that document to stdout. Its `outcome` field is attached only to complete `execve`/`execveat`, `openat`/`openat2`, and `connect` records. It reports `success` only for strict recognized successful results, `failure` only for strict Linux `-1 ERRNO (message)` results, `in_progress` for strict `connect` `EINPROGRESS` results, and `unknown` otherwise. This is a syscall-result summary; raw results and records remain unchanged and authoritative. Unfinished/resumed rows and other syscall names have no outcome field. `sideeffect inspect --bundle DIR` accepts Linux `sideeffect.run` v1 and v2 bundles; recording writes v2, verifies its strict manifest, private fixed files, trace length, and SHA-256 before parsing, and produces the same trace evidence as inspecting the raw trace without including the bundle path. Schema-v2 bundles add `bundle_capture` with the stop reason and optional requested time limit; raw traces and v1 bundles omit it. Timed bundle inspection reports this metadata in JSON/text, warns about incompleteness, and exits 2. The manifest cap is 16 KiB and the trace uses the existing 32 MiB cap. Its `source_sha256` fingerprints the exact bounded byte buffer parsed. For `openat` and `openat2`, it may include an optional `lexical_path_hint` derived from a plain printable-ASCII path and an absolute `-yy` directory annotation; the hint does not query the filesystem, normalize path segments, follow symlinks, or establish descriptor identity. Inspection includes evidence-linked process-creation observations for complete successful `fork`, `vfork`, and qualifying `clone`/`clone3` rows. Schema v7 names the source `caller_task_id`: the `strace -f` prefix identifies a calling task/thread ID, not necessarily the Linux parent PID when a non-leader thread creates a process. The relation connects that caller ID to the child PID returned by the syscall, and is not an OS parent-child claim or a complete process tree. A uniquely paired unfinished/resumed `clone3` may carry both evidence references; `CLONE_PARENT`, thread clones, unpaired calls, and ambiguous relations are omitted with diagnostics. Earlier trace schemas v1-v5 and diff schemas v1-v2 are standalone; schema-v2 bundle inspection carries stop reason and optional time limit in `bundle_capture`, while raw traces and v1 bundles omit it. The CLI reads raw `strace` text only and does not import/migrate prior SideEffect JSON exports. `sideeffect inspect --format text TRACE` writes an ASCII-only terminal-safe view of every parsed, control, and unparsed row plus parser diagnostics and labels any hint as lexical. `sideeffect diff LEFT RIGHT` compares completely parsed raw trace inputs and writes schema-v3 JSON observed deltas with source offsets and separate left/right SHA-256 fingerprints; it includes optional side-specific lexical path hints as display-only fields, while `matching_policy.exact_fields` documents exact row/result comparison and `matching_policy.display_only_fields` explicitly excludes the hints. Fingerprints identify bytes only; they do not authenticate capture or establish completeness. `sideeffect evidence TRACE SHA256 LINE BYTE_OFFSET BYTE_LENGTH` verifies the supplied lowercase fingerprint against the exact parsed bytes before checking the source tuple against exactly one parsed syscall row. Partial input is labeled, and malformed/mismatched fingerprints and control, unparsed, out-of-range, or mismatched tuples are rejected. A successful lookup establishes byte identity relative to the supplied fingerprint and position within those bytes; it does not establish authenticity or capture completeness. Fingerprints are sensitive metadata, can reveal equality, and may be guessable for low-entropy traces; trace bytes are not uploaded. `sideeffect diff --format text LEFT RIGHT` writes a human-readable ASCII-only view with terminal controls escaped and clearly labels path hints as display-only. Linux `sideeffect diff --format html --output REPORT LEFT RIGHT` writes a bounded static offline report, with no scripts or remote assets, mode 0600, and no-clobber publication. It omits local input paths but can contain sensitive trace values. Parser and diff fixtures remain synthetic. The Linux integration test uses the real tracer for a narrow file plus loopback scenario; compatibility with broader tracer output remains unverified.
`sideeffect diff-summary` writes a separate `sideeffect_redacted_diff_summary` schema containing only added/changed/removed diff-group counts by fixed category. Its schema omits syscall names, raw arguments/results, lexical hints, source fingerprints, evidence references, and local input paths. It does not detect secrets or certify that the remaining counts are safe to share. JSON is written to stdout; Linux HTML is capped at 64 MiB, mode 0600, and published without replacing an existing file. This command uploads nothing and is not a redacted detailed diff.

Current hard limits are 32 MiB per input file (64 MiB combined for a diff), 64 KiB per physical record excluding LF, 100,000 records per input, 200,000 diff rows, and 64 MiB for serialized JSON, text, or HTML output. These initial values need review against real captures. `parse_status` describes syntax/continuation parsing only and cannot establish capture completeness. The diff fails closed on partial parses, ignores only parser-level PID/timestamp prefixes when matching, compares exact arguments/results, treats rows as a multiset, and reports excluded control-row counts. It emits a changed row only when exactly one unmatched same-signature record remains on each side; ambiguous result multiplicities remain additions/removals. Before/after references point to the first/second CLI input respectively. Unfinished and resumed rows remain separate observations.

## Product target beyond the current implementation

The product goal is an on-demand, local audit of software on a supported computer. It is broader than the current selected-command trace comparison. A completed product should combine source-linked software/process inventory, readable permission/configuration facts, startup-hook/script inventory, and observed activity from an explicitly bounded capture. It must separate configured facts, observed behavior, derived comparisons, and AI-generated interpretation. Each audit states what was checked, what was inaccessible, and what is unknown. No background daemon or continuous monitoring is part of the target.

The initial inventory and observation platform remains Linux x86_64. Native Windows support requires a separately designed platform adapter and is not implied by WSL2. Platform-specific permission and startup mechanisms must be named individually; the product must not suggest that it has an exhaustive or cross-platform permission model. The optional local LLM is a later, opt-in layer that can summarize selected evidence only; it cannot execute commands, change settings, or replace evidence. Cloud inference, telemetry, and automatic privilege escalation remain out of scope.

Milestones 6–9 below extend the v0 technical foundation and are required for the broader product target. Milestone 6 has bounded Linux package snapshots for dpkg, RPM, pacman, and APK sources, visible `/proc` status and executable-link snapshots, and a selected-path metadata/POSIX ACL/file-capability slice. Milestone 7 has a curated Linux startup snapshot covering XDG autostart, systemd unit files and enablement-link references, common SysV init/runlevel paths, and common cron paths, plus bounded exact-path candidate correlation for supported XDG and systemd command values against a saved raw trace. Effective applicability, exhaustive source coverage, and Milestones 8–9 remain unimplemented.

## Milestone 1 — Capture a single run

The first bounded recorder slice is implemented as `sideeffect record --trace OUTPUT -- PROGRAM [ARGS...]`. It sends strace output to a generated private FIFO, enforces the same 32 MiB cap as `inspect`, and publishes a non-empty raw trace only if the output name remains unused. Overflow kills only the direct strace process and discards the staged file. Traces are staged with mode 0600 in a private mode-0700 directory; command stdout/stderr remain inherited. strace introduced `--kill-on-exit` in 6.6, but SideEffect's tested minimum is 6.8; the option is only best-effort cleanup; descendants created with `CLONE_UNTRACED` can escape tracing. A Linux integration test records two small Python targets: both create unique temp files, the baseline opens a TCP connection to a local `127.0.0.1` listener, and the candidate starts a fixed Python child. The child's successful `execve` may appear as one complete row or as unfinished and matching-PID resumed rows, depending on tracer output; the parser keeps continuation rows separate. The paired diff asserts the observed child row and its evidence reference without reconstructing a logical call. The test captures command output in memory, checks selected fixture sentinels do not appear there, and verifies its private temp directory is removed. The workflow has no artifact-upload step. The test fails if `strace` or `python3` is missing; Linux CI installs those packages before running it. The WSL integration test passed with extracted, non-installed Ubuntu strace 6.8 and 6.19 packages. This narrow case does not validate other tracer versions, broad syscall coverage, or all kernel combinations. `--syscall-limit` detaches tracees after a call count and must not be treated as a complete run. Never pass a user-controlled `-o` value directly: strace treats output names beginning with `|` or `!` as commands. See the [`strace(1)` manual](https://man7.org/linux/man-pages/man1/strace.1.html).

- Exercise `record` against a real supported strace version and a harmless shell-free target; confirm the selected option profile and FIFO output behavior.
- Status contract: do not infer target exit outcome or tracer success from the wrapper exit code. `strace` normally mirrors the wrapped command's code/signal; SideEffect labels the value `strace-reported`, inherits runtime stderr diagnostics, and keeps capture completeness unknown even when nonempty trace data exists. Failures that prevent tracer version verification or startup are reported before the target launch. This contract avoids guessing when an internal tracer error cannot be separated from a target outcome.
- Validate cleanup behavior and document that this is not a sandbox and may not terminate descendants that escape tracing.
- Test output caps, no-clobber publication, symlink safety, and cleanup on real tracer startup and termination failures.
- `record --bundle DIR` writes `sideeffect.run` v2 and the exact bounded raw trace as one directory containing only `run.json` and `trace.strace`. Schema v2 adds optional requested duration in milliseconds and a stop reason (`tracer_exited` or `time_limit_reached`); the reader continues to accept v1 and v2. The manifest omits command/program/argv, environment, cwd, username, absolute paths, output streams, tracer diagnostics, and event copies. It records tool/tracer/profile metadata, raw strace status, explicit unverified/unknown outcome markers, and exact trace length/SHA-256. Bundle files are mode 0600 in a mode-0700 directory and publish atomically without replacing an existing path. If an optional duration limit is reached, the available nonempty partial trace is published and CLI status is 2; command outcome and capture completeness stay unknown.
- Follow child processes where the chosen trace mode supports it.
- Keep command status distinct from tracer/parser/report failures.

**Exit criteria:** broader automated real-tracer integration covers a child execution and selected file/network calls; command stdout/stderr and wrapper exit status follow the documented limited contract; missing/unlaunchable tracer conditions fail before the target launch, runtime tracer diagnostics pass through stderr, raw records remain inspectable when produced, and output tests prove existing destinations/symlink targets are not overwritten/followed and failed writes do not publish partial final bundles. Linux integration tests exercise ordinary successful capture, a target exiting with status 37, a target terminated by SIGTERM, inherited target stdout/stderr, and a child `execve` attempt that fails with `ENOENT`, checking that evidence remains inspectable and the trace is published before SideEffect propagates the reported wrapper outcome. A separate fake-tracer contract test checks argument boundaries, inherited diagnostics, inspectable trace output, and the intentionally limited wrapper-status claim; it does not replace real-tracer integration. The capture integration suite passed locally with Ubuntu `strace` 6.19 and in hosted Linux CI, including Ubuntu 24.04 compatibility and Rust 1.85 MSRV jobs. The status contract does not distinguish all tracer-internal errors from target outcomes, and capture completeness remains unknown.

## Milestone 2 — Parse and model evidence

- The initial `inspect` parser supports a bounded `strace_text` outer-record syntax subset; it accepts the current versioned schema. Real output was parsed from strace 6.8 and 6.19. Raw trace text has no reliable tracer-version header, so the parser does not guess or claim the origin version. Bundles record the version queried by SideEffect. Unsupported/malformed rows stay visible as diagnostics and partial status; broader syntax/version coverage is not established.
- The opt-in `record --bundle` writer emits `sideeffect.run` v2, referencing the exact raw trace by fixed bundle filename, byte length, and SHA-256. It records optional duration/stop reason but does not reconstruct events or prove authenticity/completeness. The reader supports v1 and v2; no migration is performed.
- Direct comparison of two validated Linux v1 or v2 bundles is implemented as `diff --bundles LEFT_DIR RIGHT_DIR`; it reuses the strict bundle reader, then applies the existing parser and diff contract. Imported SideEffect JSON remains out of scope.
- Represent process, file, and connection-related observations without overstating success or identity.
- Track parse errors, unsupported records, and detectable incomplete/truncated input.

The parser and renderer must enforce the explicit budgets recorded in Milestone 0. Test each chosen file, record, string, event/collection, comparison, and rendered-output limit at the accepted boundary and just beyond it. Oversized, malformed, and truncated input must not cause unbounded allocation or silent truncation.

**Exit criteria:** fixture tests cover success/failure returns, child processes, conservative lexical path hints and unresolved cwd/dirfd cases, concurrent or unfinished calls, malformed and unsupported records, and evidence-reference integrity. Full filesystem path resolution remains open; unresolved path or process data must remain explicitly unresolved.

## Milestone 3 — Compare two runs

- The first `diff` slice is implemented for completely parsed trace documents. It groups raw syscall rows as a multiset, ignores only parsed PID/timestamp prefixes for matching, compares exact syscall names, arguments, and results, and links deltas to source offsets.
- Control rows are excluded from the initial event comparison, with per-input counts in the JSON output. Unfinished and resumed rows are retained and compared as separate observations rather than reconstructed into logical calls.
- Process/file/network labels are transparent syscall-name buckets, not claims about completed effects. The report says capture completeness is unknown; parser completeness does not establish absence of events.
- Extend matching only with independently justified rules for run-local identities. Keep descriptor/path uncertainty visible and preserve original values in source evidence. Never apply blanket path or file-descriptor normalization.

**Exit criteria:** fixture pairs cover timestamp/PID-prefix changes, added/removed/changed observations, duplicate multiplicity, and unstable event ordering; incomplete input is rejected; every emitted delta links to source evidence; any future normalization is explicit and never destroys raw values. The current exact-argument matcher can still report changes caused by run-local values inside arguments or results; resolve those only through separately reviewed rules.

## Milestone 6 — On-demand software and permission inventory

`sideeffect inventory packages --output FILE` is a user-triggered, read-only, bounded point-in-time snapshot from available dpkg, RPM, pacman, and APK package databases at fixed system paths. Schema `sideeffect.inventory` v2 associates each package row with a source ID and records source/overall status, evidence, and diagnostics. Collection shares byte, row, and deadline budgets, clears child environments, disables APK network access, and requests no elevation. Known-inapplicable managers are distinguished from unavailable or unsupported sources; unknown distributions remain partial when applicability cannot be established. The mode-0600 no-clobber output remains until deleted.

This is not a complete software inventory: unregistered programs, unsupported manager formats, and custom installs outside checked paths may be missed. The separate Linux process snapshot reads bounded numeric `/proc/PID/status` entries and `/proc/PID/exe` link text; it does not read command lines or open executable targets. It records an explicit non-atomic observation interval and marks missing, ambiguous, malformed, unreadable, vanished, and limit-omitted data partial. It does not establish exhaustive procfs visibility. The Linux `inventory permissions` slice accepts explicit paths only and reads ownership/type/mode, supported POSIX ACL xattrs, and `security.capability` Linux VFS file-capability xattrs for regular files and directories. It preserves bounded raw xattr bytes and exact Unix path bytes, and marks inaccessible, unsupported, malformed, and limit-affected data partial. It does not recurse, follow final-component symlinks, elevate privileges, or calculate effective access. The startup command writes aggregate schema `sideeffect.startup_inventory` v2 with bounded XDG autostart, systemd unit/drop-in/enablement-link references, common SysV init/runlevel paths, and common cron configuration/periodic paths. Components retain source status, diagnostics, and line- or link-target evidence; commands remain inert. Component scans are time/size/entry/line bounded; the XDG physical-line cap is 10,000. Inaccessible, malformed, unsupported, or limit-affected sources are partial; missing optional paths remain distinct. Applicability and effective startup behavior remain unevaluated, and this curated set is neither effective nor exhaustive.
- Inspect selected file ownership, mode, and ACL data; report process credentials and Linux capability sets separately. These inputs do not prove the effective access decision in every namespace or security-module context.
- Collect only through bounded, read-only operations; make scope, collection time, source, and source-specific coverage visible.
- Report inaccessible or unsupported sources as unknown/not checked. Do not automatically elevate privileges.
- Keep inventory snapshots local and sensitive; give users an explicit output path and deletion guidance. Package names, versions, architecture, and raw source rows can reveal installed software and system details; review before sharing and delete when no longer needed.

**M6 exit criteria:** the supported package adapters must share strict byte/row/time bounds and preserve source identity/evidence; unsupported, unavailable, unknown, and skipped sources must not appear as empty success. Process status duplicates and malformed fields must remain ambiguous/unknown, and executable links must be read as bounded link text without opening targets. Explicit-path permission snapshots must pin the selected object, preserve raw ACL/capability evidence, strictly validate supported Linux VFS capability formats, and report malformed/unsupported/inaccessible/limit states. Deterministic fixtures must cover each adapter, ambiguity, malformed and over-limit inputs; filesystem-backed xattr tests must report when a host filesystem cannot provide that optional prerequisite. Linux/Windows CI, clippy, format, output privacy/no-clobber behavior, and documentation must pass review before M6 is marked complete. Completion does not imply a full system inventory, effective-access determination, native Windows support, or the completion of Milestones 7–9.

## Milestone 7 — Startup hooks, scripts, and runtime evidence
The implemented Linux `sideeffect.startup_inventory` v2 aggregate combines bounded XDG autostart, systemd unit/drop-in and enablement-symlink reference discovery, common SysV init/runlevel paths, and common cron configuration/periodic paths. It preserves component status and source evidence and treats commands as inert values. `correlate-startup` accepts that saved schema and a saved raw strace trace, then reports exact literal absolute executable-path candidate matches for XDG `Exec` and systemd `Service.Exec*` values against successful `execve`/`execveat` filename arguments. It preserves all matching evidence and input status; unsupported relevant command forms make the result partial. Copied configuration/source metadata is capped at 8 MiB. The operation does not resolve command semantics, symlink targets, or canonical paths, evaluate effective applicability, prove configured entries ran, or cover every distribution-specific source. A complete result covers only this narrow supported subset.

**Status: complete for this bounded Linux slice.** M7 includes the curated XDG, systemd, SysV, and cron inventory plus exact-path candidate correlation for the supported XDG and systemd subset. SysV and cron are inventory-only in M7. “Complete” refers to this documented subset and its explicit partial/unknown states; it does not mean every startup source is covered or that a matching hook ran.

- Keep discovered startup configuration inert, with source-file and configuration references; never execute discovered commands or scripts. The current snapshot reports XDG, systemd, SysV, and cron source data with per-component status. Runtime evidence links the calling task/thread ID to the PID returned by a process-creation syscall; this is not necessarily the Linux parent PID or an OS parent-child claim. `correlate-startup` creates a narrower candidate match only from an exact literal absolute path and successful exec filename, with both input references retained; its runtime field is named `caller_task_id` for the `strace -f` row prefix and may represent a thread ID. This does not prove hook execution or causation.
- `record` captures a selected command and traced descendants and now accepts an optional bounded wall-clock limit. Trace schema v5 introduced process-creation relations, including a uniquely paired split `clone3` with both source references. Schema v7 adds capture stop-reason and requested-time-limit metadata when inspecting a v2 run bundle, and names the caller identifier `caller_task_id`; schema v6 was not published. The field is the task/thread ID from the `strace -f` prefix, not necessarily the Linux parent PID; the relation links it to the child PID returned by the syscall. Broader configured-startup matching, effective applicability, and any causal linkage remain open and must not be inferred.
- Distinguish configured hooks/scripts from ones observed executing. Do not claim that absence from a snapshot proves a hook or behavior does not exist.
- Review the resulting coverage by platform and avoid any “everything observed” guarantee.

## Milestone 8 — Optional local analysis

- **Progress:** the deterministic trace, trace-diff, and package-inventory explanation slice is implemented through `sideeffect explain`. Trace summaries retain typed outcome classifications, source references, process-relation references, capture/parse limitations, and known unknowns while omitting raw arguments/results and free-form diagnostics. Package inventory comparison accepts only bounded strict schema-v2 Linux package snapshots, compares package identity/version/status, preserves evidence tuples, and suppresses unmatched add/remove claims for missing, partial, or inapplicable source coverage. This does not compare process, startup, or permission inventory snapshots.
- Optional local model analysis is not implemented or release-ready. Before selecting it, review exact weights and immutable revision, conversion provenance, model and runtime licenses, runtime source/binary provenance, local-only enforcement, data flow, quality, and resource use. Initial research candidates were [Qwen3.5-0.8B](https://huggingface.co/Qwen/Qwen3.5-0.8B) and [Qwen3-0.6B](https://huggingface.co/Qwen/Qwen3-0.6B); a Qwen3-0.6B GGUF Q4_0 candidate, its current file-page hash, and the open checks are recorded in [the local model evaluation](LOCAL_MODEL_EVALUATION.md). The short revision and inference quality/resource behavior have not been validated. Do not treat a model card or GGUF file page as sufficient approval for shipping weights.
- Require explicit opt-in, an explicit local model selection, and an input preview that lists exactly which evidence will be analyzed. Send only bounded, user-selected evidence; do not include a whole raw trace, environment, command output, or unrelated inventory by default. Never auto-download weights or send evidence to a hosted API. If the runtime cannot enforce a local-only path, do not claim offline processing.
- Treat all trace and inventory values as untrusted prompt input. Give the model no command, shell, filesystem-write, privilege, or tool interface. Validate model output against a strict schema and allow factual claims to cite only evidence identifiers supplied in that request; visibly label generated prose as interpretation and keep the source facts available beside it.
- Measure usefulness and false-claim rates on synthetic fixtures and reviewed examples before shipping. Keep all feature boundaries and capture limitations visible; a model summary must not imply complete observation, causation, safety, or root cause.

## Milestone 9 — Native Windows audit adapter

- Design a native Windows read-only inventory and bounded runtime-evidence adapter; do not treat WSL2 as Windows coverage.
- Start with [uninstall registry entries](https://learn.microsoft.com/en-us/powershell/scripting/samples/working-with-software-installations), a [Tool Help process snapshot](https://learn.microsoft.com/en-us/windows/desktop/ToolHelp/taking-a-snapshot-and-viewing-processes), [access tokens](https://learn.microsoft.com/en-us/windows/win32/secauthz/access-tokens), [file security descriptors and ACLs](https://learn.microsoft.com/en-us/windows/win32/fileio/file-security-and-access-rights), [Run/RunOnce keys](https://learn.microsoft.com/en-us/windows/win32/setupapi/run-and-runonce-registry-keys), [Startup folders](https://learn.microsoft.com/en-us/windows/win32/shell/knownfolderid), [service configuration](https://learn.microsoft.com/en-us/windows/win32/services/service-configuration), and [scheduled-task definitions](https://learn.microsoft.com/en-us/windows/win32/taskschd/about-the-task-scheduler). These are curated sources: Microsoft documents that software inventory does not find every application, and inaccessible processes or entries must remain unknown. Avoid `Win32_Product`, whose installer checks can alter machine state.
- Evaluate bounded runtime collection through [Event Tracing for Windows (ETW)](https://learn.microsoft.com/en-us/windows/win32/etw/about-event-tracing) as a separate capability. Document provider/filter scope, event loss, and [session permissions](https://learn.microsoft.com/en-us/windows/win32/etw/controlling-event-tracing-sessions); do not elevate automatically or imply that ETW captures every event.
- Keep the same evidence, scope, collection-time, unknown-state, no-background-monitor, and no-automatic-elevation guarantees as other adapters.
- Validate Windows-specific privacy and security boundaries separately; do not reuse Linux coverage claims.

Milestones 6–9 are product requirements, not v0 exit criteria. The supported package adapters, bounded Linux process-status/executable-link snapshot, and explicit-path Linux metadata/POSIX ACL/file-capability snapshot implement the current bounded first slice of Milestone 6; they do not establish a complete software or permission inventory. The curated XDG/systemd/SysV/cron Linux startup snapshot and narrow saved-input candidate correlation implement the current Milestone 7 slice. Correlation input, copied-metadata, row, and output limits are explicit; partial inputs and unsupported relevant command forms remain partial. The permissions slice is not recursive or exhaustive and does not calculate effective access. XDG autostart, systemd, SysV, and cron scans each have documented per-source bounds and diagnostics; overlong or unsupported input is not silently treated as complete. Discovered entries do not establish applicability, and a candidate path match does not establish execution causation. Effective applicability and exhaustive startup coverage remain unimplemented. The deterministic explanation slice of M8 is implemented, while optional local model analysis and Milestone 9 remain incomplete.
