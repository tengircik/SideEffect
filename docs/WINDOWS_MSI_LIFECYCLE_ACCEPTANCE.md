# Windows MSI lifecycle acceptance

The Windows CI matrix runs `scripts/test_windows_msi_lifecycle.ps1` on disposable GitHub-hosted Windows Server runners after building the SideEffect CLI. The script requires the hosted-runner markers, `RUNNER_TEMP`, `WIX`, WiX Toolset 3 (`candle.exe` and `light.exe`), and `msiexec.exe`. Both observed transitions require the runner's existing permission to control the shared NT Kernel Logger; SideEffect does not elevate, and ETW setup must succeed before it starts each target. It rejects local and self-hosted execution before creating fixtures or invoking an installer.

The test builds two local, scriptless MSI packages with a single `payload.bin` file. Both use per-user, limited-privilege installation and a shared upgrade code. Each MSI embeds its payload cabinet with a package-specific cabinet identifier, which the test confirms through a read-only query of the MSI Media table. The package fixture has no custom actions, registry authoring, services, shortcuts, scheduled tasks, or persistence behavior. Separately, a fixed PowerShell harness wrapper runs only on the already-administrative disposable hosted runner. During each observed command window it creates one unique disabled SCM service and one unique disabled logon task, both configured with a unique executable path that does not exist. The task and trigger are created disabled, and the service is created with disabled start configuration; neither is started or enabled. These are test-harness configuration mutations, not MSI-authored changes. All package files, logs, snapshots, and the selected install root live under a unique child of `RUNNER_TEMP`; the MSI-authored default install path is the same selected root. The wrapper waits for the real `msiexec.exe` child, writes its exact process ID and exit code to a bounded sidecar, and exits with that same code. After SideEffect returns and publishes the session with its after snapshot, the parent removes only the generated GUID-named service and task before invoking `compare-observation`; cleanup runs on success and failure paths. The scripts do not request elevation, execute the inert fixture actions, or install software on a developer machine.

The real Windows Installer sequence installs version 1, performs a major upgrade to version 2, then exercises a downgrade strategy by uninstalling version 2 and reinstalling version 1. It finally uninstalls version 1. Both the v1 install and the v2 major upgrade are invoked through SideEffect `audit --observe-root --startup` with `--hash-regular-files` and the `windows-etw` runtime source. The fixed wrapper passes the same separate MSI argument vector used by the direct lifecycle helper to the waited `msiexec.exe` child: `/i`, the generated MSI path, `/qn`, `/norestart`, `/l*v`, the generated log path, and `INSTALLROOT=<selected root>`. It returns the child's exact exit code; the acceptance reads the sidecar and verifies success. The only package payload remains a fixture data file; no package-authored code is executed by this test. The shared observation helper is parameterized by the expected selected-root delta kind and the expected post-transition payload SHA-256, plus the expected pre-transition payload SHA-256 for a change. The downgrade uninstall, downgrade reinstall, and final uninstall transitions remain direct MSI operations.

For each observed install/upgrade, the script requires a complete before/after selected-root comparison showing exactly one expected `payload.bin` delta with SHA-256 values matching the expected fixture bytes and installed file. It requires a same-session startup comparison with verified references to both Windows startup v10 artifacts. When the before sources can enumerate their scope, the before artifact must lack the generated SCM service and task identities. The after artifact checks any observed unique SCM row is configured disabled and any observed task and its logon trigger are disabled with a missing inert action path; a partial source may omit a row and remains explicitly partial. When relevant startup sources are complete, `startup_diff` must link the expected after-only deltas to the exact service, trigger and action rows. If startup source coverage is partial, unavailable, inaccessible, unsupported, or not checked, the report and acceptance output preserve those statuses and the comparison remains partial; the test does not infer absence or claim a complete delta from unavailable data. The harness removes its exact generated service and task after SideEffect publishes the after snapshot and before comparison output is read. Startup differences report configuration observed in two snapshots and do not attribute the mutations to the MSI or imply causation.

For the same command window, the script requires ETW process-start evidence for the PowerShell wrapper target and a separate decoded process-start row for the exact waited `msiexec.exe` child PID. If that child row is missing, the test fails without inferring the relationship from an unrelated process start. It also requires a decoded file-name observation containing the fixture payload basename whose UTF-16 text is present in its raw payload bytes. When the capture provides a same-spelling absolute DOS drive path candidate for the installed payload, each candidate reference is checked against the capture document digest, the separate artifact-byte digest, its actual `/events/<index>` row and ETW record ordinal, and the SHA-256 of that row's raw payload; the decoded sidecar path must equal the payload path. If ETW reports a path that the comparator cannot associate, the test accepts the basename evidence only when the comparison reports zero candidates with an explicit unresolved namespace or no-exact-path diagnostic; the root/runtime relationship remains unresolved and the script emits a capped set of raw evidence locators. ETW FileIo name observations do not prove operation success, process ownership, or causation. Any unrelated or unsupported events remain governed by the capture's partial status and unknown completeness. The test checks Windows Installer's current-user unmanaged product registration, version, and installed state through `MsiGetProductInfoEx`, as well as installed payload bytes and SideEffect selected-root snapshots. It also takes `inventory packages` snapshots before installation and after each transition. If the MSI's generated ProductCode appears with the expected display name/version in SideEffect's current-user native or WOW64-32 Uninstall view, `explain --inventory-diff` must report the registration addition/removal across install, major-upgrade, downgrade, and uninstall. Each emitted delta must point back to exactly one source registration row by source ID, hive/view, subkey identity, and registration index. When the MSI API confirms installation but the exact generated ProductCode is not observed in either selected Uninstall view, the test reports MSI registration correlation as unknown and emits only bounded booleans for reads of those generated GUID keys; it does not convert the MSI API fact into an Uninstall-registry observation. A separate hosted-only fixture writes one generated GUID key with fixed `DisplayName` and `DisplayVersion` strings, then verifies SideEffect's evidence-linked addition and removal diffs; cleanup deletes only that exact generated key. This separately validates the adapter path without implying that MSI authored the same registry evidence. Other machine-wide source views may make aggregate comparisons partial; the test requires both selected current-user views to be complete on each side and accepts the CLI's documented partial exit code when unrelated sources are incomplete. Registry facts do not prove that a product is available, launchable, or running. The payload lifecycle verifies observed SHA-256 values and addition, content-change, and removal diffs, including their selected-root evidence ordinals across the observed install, observed major upgrade, direct downgrade reinstall, and direct uninstall. If payload verification fails, the output reports whether the expected payload appeared in the selected root and includes a bounded tail of the MSI log.

This acceptance validates the scriptless MSI package fixture, separate disabled startup test-harness configurations, and tested SideEffect selected-root/startup workflows on the named hosted Windows images. It does not validate third-party installers, in-place MSI downgrade, system-wide installation, causal attribution, persistence detection, all Windows inventory sources, or complete filesystem coverage. The snapshots are before/after observations; they do not prove that MSI caused a change beyond the controlled fixture operations.
