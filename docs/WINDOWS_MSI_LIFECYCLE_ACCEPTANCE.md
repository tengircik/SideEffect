# Windows MSI lifecycle acceptance

The Windows CI matrix runs `scripts/test_windows_msi_lifecycle.ps1` on disposable GitHub-hosted Windows Server runners after building the SideEffect CLI. The script requires the hosted-runner markers, `RUNNER_TEMP`, `WIX`, WiX Toolset 3 (`candle.exe` and `light.exe`), and `msiexec.exe`. It rejects local and self-hosted execution before creating fixtures or invoking an installer.

The test builds two local, scriptless MSI packages with a single `payload.bin` file. Both use per-user, limited-privilege installation and a shared upgrade code. Each MSI embeds its payload cabinet with a package-specific cabinet identifier, which the test confirms through a read-only query of the MSI Media table. The fixture has no custom actions, registry authoring, services, shortcuts, scheduled tasks, or persistence behavior. All package files, logs, snapshots, and the selected install root live under a unique child of `RUNNER_TEMP`; the MSI-authored default install path is the same selected root. MSI is launched as a waited process with explicit quoted package, log, and install-root paths; the script leaves the hosted runner's `TEMP` and `TMP` environment unchanged. The script checks path containment and removes the test directory in its cleanup block. It does not request elevation or install software on a developer machine.

The real Windows Installer sequence installs version 1, performs a major upgrade to version 2, then exercises a downgrade strategy by uninstalling version 2 and reinstalling version 1. It finally uninstalls version 1. The test checks Windows Installer's current-user unmanaged product registration, version, and installed state through `MsiGetProductInfoEx`, as well as installed payload bytes and SideEffect selected-root snapshots. It also takes `inventory packages` snapshots before installation and after each transition. If the MSI's generated ProductCode appears with the expected display name/version in SideEffect's current-user native or WOW64-32 Uninstall view, `explain --inventory-diff` must report the registration addition/removal across install, major-upgrade, downgrade, and uninstall. Each emitted delta must point back to exactly one source registration row by source ID, hive/view, subkey identity, and registration index. When the MSI API confirms installation but the exact generated ProductCode is not observed in either selected Uninstall view, the test reports MSI registration correlation as unknown and emits only bounded booleans for reads of those generated GUID keys; it does not convert the MSI API fact into an Uninstall-registry observation. A separate hosted-only fixture writes one generated GUID key with fixed `DisplayName` and `DisplayVersion` strings, then verifies SideEffect's evidence-linked addition and removal diffs; cleanup deletes only that exact generated key. This separately validates the adapter path without implying that MSI authored the same registry evidence. Other machine-wide source views may make aggregate comparisons partial; the test requires both selected current-user views to be complete on each side and accepts the CLI's documented partial exit code when unrelated sources are incomplete. Registry facts do not prove that a product is available, launchable, or running. The payload workflow verifies observed SHA-256 values and addition, content-change, and removal diffs, including their selected-root evidence ordinals. If payload verification fails, the output reports whether the expected payload appeared in the selected root and includes a bounded tail of the MSI log.

This acceptance validates the synthetic fixture and the tested SideEffect selected-root workflow on the named hosted Windows images. It does not validate third-party installers, in-place MSI downgrade, system-wide installation, causal attribution, persistence detection, all Windows inventory sources, or complete filesystem coverage. The snapshots are before/after observations; they do not prove that MSI caused a change beyond the controlled fixture operations.
