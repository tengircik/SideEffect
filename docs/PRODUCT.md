# SideEffect Product Brief

**Status:** implementation in progress. The repository provides bounded Linux inventory and `strace` workflows, plus bounded native Windows inventory and ETW workflows. Linux sessions may include a runtime bundle; Windows audit sessions can include an explicitly selected ETW v3 artifact. Audit-session envelopes v9-v16 preserve per-source coverage, source settings, runtime loss state, collector identity, artifact provenance, and bounded host OS/version and caller privilege facts. It supports selected-root metadata v1 by default and opt-in bounded regular-file fingerprints v2. Session v7 and v8 remain readable with their exact historical contracts; v9 adds optional current-user MSIX registration evidence, v10 permits Windows startup v6, v11 adds optional App Paths while retaining startup v6, and v12 preserves startup v7 as a historical contract; v13 preserves Windows startup v8; v14 preserves Windows startup v9; v15 permits Windows startup v10 while retaining App Paths. The nested coverage manifest v2 adds bounded runtime unsupported-category counts derived from retained selected artifacts; missing or differing runtime detail makes sessions incomparable. Session inspection checks its manifest, fixed artifact contracts, lengths, and hashes; hashes establish byte consistency, not authenticity. OS identity and privilege are reported only from platform APIs; privilege status does not describe every resource access, and architecture is never used to infer it. This is one metadata increment and does not complete the R0 roadmap. Windows ETW supports bounded capture, offline inspection, event-level comparison, candidate attribution, and static HTML review. See the compatibility matrix for tested OS, tracer, and provider scope. The portable `sideeffect-audit` Agent Skill routes a user-selected agent and model through the local deterministic CLI; SideEffect's local-model experiments remain an optional, unqualified workstream.

## Product summary

The source reports the current process PATH metadata and its limits/status as a point-in-time inventory. It does not execute candidates or determine command or shell resolution; local paths and names can be sensitive.

`inventory root --output FILE SELECTED_DIRECTORY` emits `sideeffect.selected_root_inventory` v1 for one explicitly selected directory and its direct children, reading metadata only. The opt-in `--hash-regular-files` emits v2 and reads only direct-child regular files to calculate SHA-256. Hashes are sensitive equality fingerprints and can reveal that two files contain identical bytes; they do not authenticate content. Child names, not enumeration ordinals or file IDs, are the match key. When either input opted into hashing, content is compared only when both sides have observed digests; unavailable or unrequested hashes are unknown and make the comparison partial. Added/removed rows require complete snapshots and no known conflicting root identity hints; ambiguous duplicates and incomplete inputs suppress presence claims. File IDs are nonpersistent local hints only. A known hint conflict is reported as uncertainty, does not prove the root object changed, and conservatively suppresses unmatched presence claims. Unknown types and metadata absent on both sides remain unknown and make the comparison partial. The comparator accepts at most 32 MiB across both inputs. Entry order is unstable, enumeration is non-atomic, and permission/limit/race diagnostics make the snapshot partial. The comparison does not establish persistent object identity, installation, removal cause, or filesystem history. udit --observe-root PATH records v16 selected-root snapshots before and after an explicitly bounded Linux strace or Windows ETW command capture. SideEffect is intended to be a user-triggered, local audit of software on a computer. An audit should show what software is present or running, which permission/configuration facts can be read, what startup hooks or scripts are configured, and what activity was observed during an explicitly bounded capture. Every claim should link to the source record or system artifact that supports it. The report must distinguish configured facts from observed runtime behavior and derived analysis, and label inaccessible or unsupported areas as unknown or not checked. SideEffect does not run as an always-on monitor.

The current implementation is a narrower technical foundation: on Linux it reads point-in-time package listings from available dpkg, RPM, pacman, and APK sources at fixed system paths plus Flatpak installed refs; selected process facts from visible numeric `/proc/<pid>/status` entries and executable-link text; selected-path metadata, supported POSIX ACLs, and `security.capability` xattrs; and curated startup configuration from XDG autostart, common systemd unit paths, SysV init/runlevel paths, and cron paths. It also parses local `strace` text, compares two fully parsed traces, records one selected command under external strace, adapts Linux strace and Windows ETW evidence into common event envelope v4, and compares saved startup inventories to runtime evidence for narrow exact-path candidates. The Windows associated-behavior adapter also compares exact literal REG_SZ Run/RunOnce commands with decoded ETW process-start image paths only when raw UTF-16 sidecars strictly agree with their display text; missing or inconsistent sidecars leave the row unmatched and the result partial. It compares SCM service binary_path strings with those same decoded image paths without interpreting commands or path variants. Package data does not inventory all software: unregistered programs and unsupported sources may be absent. The process snapshot is a bounded, non-atomic walk over an interval; it does not read command lines or open executable targets and does not claim exhaustive system coverage. Startup values remain inert; the collector does not execute commands, determine applicability/effective state, or prove that a configured hook runs. The candidate correlation does not prove hook execution or causation. The explicit-path permissions command does not recurse or calculate effective access. Trace process lineage records evidence linking the calling task/thread ID in a `strace -f` row to the child PID returned by a successful process-creation syscall. A non-leader thread can make such a call, so the caller task ID is not necessarily the Linux parent PID; these links do not assert an OS parent-child relationship or form a complete process tree. The common event envelope v4 also segments Linux task-prefix observations at exact, prefixed task-termination rows when the trace parse is complete. These observed task epochs are source-local context segments, not OS process/PID generations or ancestry; partial parses retain task-ID-only contexts. The envelope preserves the caller-to-returned-child relation separately, and on Windows decodes process start/end IDs from retained raw payload bytes for reviewed Kernel-Process v0-v3 layouts, matching them against the serialized TDH sidecar before emitting observed process identities, lifecycle links, or reported parent relationships; image names remain decoder metadata only, while unsupported, malformed, truncated, zero-PID, or mismatched rows remain unresolved and invalidate lifecycle continuity; this check does not authenticate the capture or establish causal parentage. Unresolved network payload PIDs remain visible without an instance link, while file/disk header PIDs remain context candidates. The graph remains source-local for each runtime artifact; on Windows, supplying both startup inventory and ETW capture additionally renders exact service-path matches as evidence-linked candidate edges. These candidates do not establish service launch or causation. A bounded static HTML export is available for a source-local timeline over one Linux trace or one validated Windows ETW capture. It preserves event evidence locators, process-link status/basis, and source diagnostics/completeness, but does not merge sources, normalize clocks, infer causal order, or establish complete system coverage. Cross-source graph exploration and an integrated complete timeline remain unimplemented. A Linux integration test covers a child execution, temporary-file activity, and loopback-only TCP; broad compatibility and event coverage remain unverified.

Linux x86_64 is the first implementation platform, and its current capture backend uses an external `strace` executable. Windows is also a first-class target. Its bounded native inventory slices cover selected Uninstall registry registrations, a Tool Help process snapshot, explicit selected-path owner/group/DACL inspection, and Run/RunOnce, Startup-folder, SCM-service, and Task Scheduler boot/logon-trigger configuration. These curated sources are not exhaustive. The experimental native ETW workflow captures selected process, FileIo, DiskIo, TCP, and UDP records in a bounded system-wide window. Users can inspect a capture, compare two captures using exact record multisets plus conservative candidate matches, generate static HTML reports, and request a separate candidate attribution view for process lineage, network payload PIDs, and file/disk header-PID context. The output preserves raw-record references and reports uncertainty; it does not establish causation, complete coverage, or safety. Live ETW acceptance is configured in the hosted Windows CI matrix; compatibility claims remain limited to versions with recorded evidence. WSL2 does not count as native Windows coverage. Rust is the implementation language. The optional local model is an opt-in layer for selected audit evidence; the core audit works without an LLM or hosted service.

The Agent Skill is distributed using the open Agent Skills format and can be installed for Codex, Claude Code, OpenCode, and other compatible clients. Oh My Pi (OMP) users can use its native skill directory. The skill contains command guidance only: SideEffect remains a local CLI, while model selection and provider data handling stay under the user's agent configuration. It does not install or invoke SideEffect's local model runtime.

Published traces, bundles, report files, and inventory snapshots are written to paths chosen by the user and remain there until the user deletes them. SideEffect does not upload, rotate, or automatically delete published data. Handled failures and cancellation clean up private staging directories; a machine crash can leave one behind. Treat traces, reports, and inventory snapshots as sensitive data.

## Problem

People often cannot tell what installed or running software is configured to do, which permissions or startup entries it has, or what it does when they run it. OS tools expose these facts in different places and formats. SideEffect should bring supported sources into a local report while preserving the source of each claim, distinguishing configured access from observed behavior, and showing areas it could not inspect. Runtime traces can help explain a selected program's actions, but correlation must not be presented as proof of cause.

## Intended users and use cases

- A computer user reviewing installed and running software, supported permission facts, and startup hooks or scripts.
- A developer or maintainer inspecting a selected program's bounded runtime activity or comparing two runs.
- A security-conscious user auditing a local tool before deciding whether to run it. The report is an observation aid, not a security verdict or sandbox.

The current foundation release focuses on one reproducible pair of command runs. The broader product goal is an on-demand audit, not a continuously running endpoint monitor or a claim to enumerate every possible behavior.

## Current implementation

`sideeffect inventory packages --output FILE` is a user-triggered, read-only point-in-time snapshot. On Linux it reads available dpkg, RPM, pacman, and APK package databases at fixed paths and, when installed, Flatpak refs from `/usr/bin/flatpak list --columns=ref`. The Flatpak adapter reports refs without package versions or installation-scope identity; missing Flatpak is optional and does not alone make otherwise complete package sources partial. Child processes use fixed arguments, cleared environments, no stdin, no user-provided command text, and no privilege escalation; the APK adapter disables network access. JSON schema `sideeffect.inventory` v2 records source scope, capture timestamp, source/overall status, package rows with source IDs, evidence, and diagnostics. Malformed rows remain represented with diagnostics and raw bytes encoded as hex. Required unavailable, unsupported, failed, or not-checked sources prevent a complete result; a partial document is still published and the command exits `2`. The shared snapshot budgets are 32 MiB stdout, 64 KiB stderr, 8 KiB per row, 200,000 rows, 20 seconds across adapters, and 64 MiB serialized output. The selected output file is private (mode `0600`) and no-clobber; it remains until the user deletes it. This is not a complete software inventory: manually copied/unregistered software, unsupported managers, and custom installations outside checked paths may be missed. Package metadata and raw rows are sensitive; output is not automatically redacted or uploaded. On Windows, the command reads selected values from current-user and accessible machine Uninstall registry views into sideeffect.windows_software_inventory v1. It preserves exact selected value bytes, leaves REG_EXPAND_SZ literal, and does not launch uninstall commands. This is a curated registry snapshot; portable and unregistered applications can be absent, and the current-user-only DACL output is sensitive.

On Windows, `sideeffect inventory app-paths --output FILE` separately snapshots selected values below current-user and accessible machine `Software\Microsoft\Windows\CurrentVersion\App Paths` registry keys into `sideeffect.windows_app_path_inventory` v1. This source records registry registration only. It does not scan the filesystem, expand environment strings, parse or run values, or establish that a registered executable exists, is installed, available, or launchable. Values are inert, exact local evidence and may expose usernames or installation paths; output remains private and should be reviewed before sharing. This inventory is deliberately separate from Uninstall registrations. Audit-session v11 can include it as an optional source, and `compare-sessions` compares exact source/view/subkey registration identities while hashing selected values; the comparison does not validate the target path or establish launchability.

On Windows, `sideeffect inventory msix --output FILE` separately snapshots current-user AppX/MSIX package registrations into `sideeffect.windows_msix_inventory` v1. It reads package metadata only for the calling user. It does not query other users, activate packages, inspect package contents, or claim a package is available, launchable, healthy, or previously run. Package metadata and install locations can expose sensitive local information; the private output should be reviewed before sharing. `compare-sessions` compares this source by exact valid package-family UTF-16 identity, reports selected version/metadata changes and source-linked additions/removals, and suppresses unmatched presence claims if sources are incomplete, contain duplicate family identities, or contain any invalid identity. This comparison remains a bounded registration observation and does not establish installation history, availability, health, launchability, or execution.

`sideeffect explain TRACE`, `sideeffect explain --diff BASELINE CANDIDATE`, and `sideeffect explain --inventory-diff BEFORE.json AFTER.json` provide bounded deterministic summaries without requiring a model. Trace summaries preserve typed selected-syscall outcomes, source references, direct process-relation references, and parse/capture uncertainty while omitting raw arguments/results. Trace diffs require completely parsed inputs. Inventory comparisons accept same-platform pairs of Linux package v2, Windows software-registration v1, Linux process v3-v5, Windows process v3-v4, Linux selected-path permission v1, Windows selected-path permission v1, Linux startup v2/v3, Windows startup v4-v10, and Linux or Windows selected-root v1/v2 snapshots. Selected-root comparison uses exact platform path/name encodings, metadata for direct children only, and compares opt-in content SHA-256 only when both sides have a hash; otherwise content is unknown and can make the result partial. It does not establish file history or hash authenticity. Linux v5 records a boot-ID and caller PID-namespace inode hint; matching domains allow only `candidate_changed` facts for exact PID/start-tick matches, while additions/removals are suppressed because namespace inode values can be reused. Missing or mismatched v5 domains suppress all Linux v5 deltas. Linux v4 has no PID-namespace identity, so matching boot IDs permit only candidate changes and unmatched presence is suppressed; Linux v3 lacks an identity domain and is not compared. Windows v3-v4 have no reviewed reusable host boot identity, so exact PID plus creation-FILETIME matches may show candidate field changes only; PID-only matches and unmatched additions/removals are suppressed. These snapshot identifiers are evidence hints, not host authentication or process history. Exact process matches compare selected inert process name/path, UID/GID/capability/seccomp/no_new_privs or Windows parent/token facts, and preserve both sides' evidence references. Missing or duplicate generation identities remain ambiguous. Permission comparisons use the exact selected path encoding and compare only bounded metadata and native ACL/capability facts; duplicate paths are ambiguous and incomplete snapshots suppress unmatched additions/removals. They do not calculate effective access or prove object persistence from inode/file-index values. Startup comparison uses source-specific native identities, compares selected XDG/systemd/SysV/cron facts on Linux and Run/RunOnce, Startup-folder, service, task-trigger, and ordered task-action-sequence facts on Windows. Linux systemd changes to selected dependency directives (`Requires`, `Requisite`, `Wants`, `BindsTo`, `PartOf`, `Upholds`, `Conflicts`) and ordering directives (`Before`, `After`) receive separate static labels; raw values remain omitted, and these labels do not claim effective dependencies or startup order. Windows startup v7 also compares a point-in-time SCM service state separately from configured start type; unsupported raw values remain unknown, and this observation does not identify cause. Startup v8 compares delayed-auto-start only when both inputs are v8 or later and both values are observed; startup v9 compares dependency and load-order-group values only for same-version v9 pairs with observed configuration. Unknown/incomplete values and mixed v8/v9 pairs suppress service presence claims. Windows ignores this configuration bit unless service start type is automatic, it gives no exact start time, and it does not prove execution. Windows `audit --startup` embeds startup v10 in session v15; session v13 remains readable with startup v8 and v12 remains readable with startup v7 and v10/v11 retain their startup-v6 contracts. Duplicate identities, incomplete sources, missing task paths, and lossy XDG paths remain uncertain and suppress presence claims. The output omits raw command/configuration values and carries only hashed identities, changed-field labels, counts, and source references. Hashes are not anonymization: common paths or names may be guessable, and output can remain sensitive. A startup pair does not show installation/removal, effective state, or execution. These bounded snapshots are not process start/exit history, exhaustive inventory, causation, or proof of absence. PIDs, generation values, paths, source references, and output can be sensitive. Permission evidence remains sensitive; raw xattr and security descriptor bytes stay in the source inventories and are omitted from the comparison. Windows registration matches use source, hive, registry view, and exact UTF-16 subkey evidence; the report compares display name, version, and publisher while omitting uninstall commands and raw registry values. Per-task local runtime paths can be configured and hash-checked without executing or installing them; local-model implementation and evaluation are active again, qualification remains incomplete, and model commands remain experimental and optional with no release-approved model. The preview may include strictly parsed errno names and bounded conservative lexical path hints for selected file-open records; these values are untrusted and potentially sensitive, and path hints are not filesystem-resolved. The model may select at most one evidence ID already in the request or abstain. It may select the wrong record, so deterministic source facts stay beside the selection. The model output is not a finding and is not suitable for decisions. The runtime is not sandboxed, so only use a trusted local runtime with an approved model; see [the evaluation record](LOCAL_MODEL_EVALUATION.md).

`sideeffect inventory processes --output FILE` has two distinct platform adapters. On Linux it reads bounded numeric `/proc/<pid>/status` and `/proc/<pid>/stat` entries, `/proc/<pid>/exe` link text, seven namespace links, `/proc/sys/kernel/random/boot_id`, and `/proc/self/ns/pid`, and writes `sideeffect.process_inventory` v5. It records selected status fields and source-line evidence, the reported `NSpid` vector, namespace link identities, start-time ticks, and bounded exact-byte evidence for the boot ID and caller PID-namespace link. The combined boot-ID and namespace inode value is a reusable hint for the observed procfs view, not host authentication or a durable namespace identity; inode values can be reused and cloned VM state can duplicate boot IDs. Missing or malformed identity inputs make the identity domain unknown; read failures and per-process races remain visible and may make the inventory partial. It does not read command lines or open executable targets, and does not request elevation. The directory walk is non-atomic and scoped to entries visible in the current procfs view.

`sideeffect inventory path-executables --output FILE` writes `sideeffect.path_executable_inventory` v1 from the current process's `PATH` only. It preserves PATH component order and duplicates. Entry ordinals follow the observed filesystem enumeration order, which may differ between runs. Empty components map to the current working directory and that mapping is recorded. The collector inspects one directory level without execution or recursion. Linux candidate rows are regular files with at least one execute bit; Windows rows are regular files with a suffix in the captured current-process `PATHEXT`; if `PATHEXT` is unavailable, regular-file rows remain unknown. Exact path/name bytes (Linux) or UTF-16 code units (Windows), directory and row ordinals, candidate/not-candidate/unknown status, metadata status, limits, and diagnostics are retained. Metadata checks mark observed directory symlinks/reparse points unknown and retain child links as unknown rows without following them. Concurrent filesystem changes can race between checks and enumeration. Bounds are 256 components, 4 KiB per Linux path component / 32,767 UTF-16 units per Windows component, 20,000 directory entries, 16 MiB aggregate path/name bytes on Linux or UTF-16 code units on Windows, a 5-second boundary-checked deadline, and 64 MiB serialized output. Output uses the private no-clobber publisher. This is a PATH candidate inventory, not proof that a file can be launched or will be selected by a shell; environment and path data can be sensitive.

On Windows the command writes `sideeffect.windows_process_inventory` v4 from one Tool Help process snapshot (`PROCESSENTRY32W`) and queries accessible image paths, creation FILETIME, and token facts through one process handle per PID. Handle-bound facts are internally generation-consistent, but the snapshot's PID-only row cannot be bound to that later handle and remains candidate context. Windows host boot identity is unknown. Access-denied, vanished, mismatched, and other query failures remain explicit unknowns and make the result partial. SID is an identifier and is not resolved to an account name. It records the snapshot's process ID, parent process ID, thread count, executable name, source used for each field, and per-query status. It does not read command lines, inspect process memory, launch processes, or request elevation. The snapshot and handle queries happen at different times, so a process may exit or a PID may be reused between them. The collector stops at 8,192 processes or a 10-second deadline, caps one image path at 32,768 UTF-16 code units, aggregate paths at 4 Mi UTF-16 code units, each SID at 256 UTF-16 code units, aggregate SID text at 2 Mi UTF-16 code units, and serialized output at 64 MiB. The output is staged under an explicit current-user-only DACL in a sibling directory and published without replacing an existing destination. Process names, image paths, and SIDs are sensitive; output is not redacted or uploaded. This is not an exhaustive process inventory or a security verdict.

Linux `sideeffect inventory startup --output FILE` writes aggregate schema `sideeffect.startup_inventory` v3 (v2 remains readable), containing component inventories for XDG autostart, systemd unit files and enablement-symlink references, common SysV init scripts/runlevel links, and common cron configuration and periodic directories. Each XDG, systemd, and legacy entry carries `startup_state` v1 with configured `present` and effective/observed `unknown`; the row's presence is a source fact, not proof of applicability or execution. Component source locations, statuses, diagnostics, and configuration evidence remain separate. XDG selected lines, systemd directives, and inert file lines carry source line/byte references and hashes; paths preserve non-UTF-8 bytes alongside their display form where supported. Symlink targets are inert reference data. The collector records a curated set of common paths; user/systemd manager load paths can be customized and other distribution-specific startup mechanisms may not be represented. Missing optional locations are reported separately from inaccessible or limit-affected sources. Discovered commands and scripts are never executed or shell-parsed, and applicability/effective runtime behavior is not evaluated. A unit file or enablement link is configuration evidence, not proof a unit starts; cron data is not proof a daemon/job ran; SysV scripts/links do not prove SysV init is active. A partial snapshot is still published and returns exit status `2`; output is a private mode-0600 no-clobber file. It is not an effective or exhaustive startup inventory.

The standalone native Windows `sideeffect inventory startup` command writes `sideeffect.windows_startup_inventory` v10 (v4-v8 remain readable). In addition to selected Run/RunOnce keys, Startup folders, services, and Task Scheduler sources, it queries only local `ROOT\subscription` for permanent WMI `__EventFilter`, `__EventConsumer`, and `__FilterToConsumerBinding` objects. It retains their exact object/reference strings, selected filter query and consumer command/script fields, creator-SID bytes as bounded hexadecimal when available, and relationship resolution status. Unsupported consumer classes, inaccessible data, and unresolved bindings remain visible and make coverage partial. WMI configuration strings are untrusted, potentially sensitive evidence; they are never executed, activated, or shell-parsed. The query uses the current token and explicit proxy security, without elevation or remote access. Per-class row, string, aggregate-string, diagnostic, and enumerator-wait limits apply; the shared deadline cannot cancel in-flight WMI provider calls. Standalone v7 also includes a point-in-time SCM service state under `service_observation`; known raw codes are mapped to names and unknown codes remain explicit. Standalone v8 adds read-only SCM `delayed_auto_start` configuration as observed true/false or unknown with a source diagnostic. Windows ignores that bit unless service start type is automatic; it gives no exact start time and does not prove execution. V9 adds `QueryServiceConfigW` dependency entries as observed service or load-order-group names, preserving the `+` group distinction, and separate load-order-group membership as observed text or no group. Malformed, inaccessible, or over-limit values remain unknown with fixed diagnostics that do not echo raw names. These are SCM-reported configured values only: they do not establish effective startup order, activation, execution, or causation, and the returned configuration may not reflect a concurrent change to a running service. Names are inert and potentially sensitive. This is separate from `startup_state.observed` and does not establish startup causation. V7's WMI fields are optional as one all-or-none group; v6 retains its required WMI contract. Windows `audit --startup` embeds v9 in session envelope v14. Session v13 remains readable with startup v8, and v12 remains readable with startup v7; App Paths is available alongside startup v9 in v14, while App-Paths-only sessions stay at v11. Envelopes v10 and v11 continue to require startup v6.

Linux `sideeffect inventory permissions --output FILE PATH...` checks only the explicitly supplied paths and writes the separate `sideeffect.permission_inventory` v1 schema. It records observed file type, UID, GID, mode, device/inode, supported `system.posix_acl_access`/directory `system.posix_acl_default` xattrs, and Linux `security.capability` xattrs (VFS revisions 1–3). Paths are opened with `O_PATH|O_NOFOLLOW` and pinned; xattr reads use a read-only descriptor reopened through `/proc/self/fd`, with identity checked against the pinned object. The final path component is not followed when it is a symlink; intermediate path components follow normal Linux path resolution. Only regular files and directories are supported. Raw supported xattr bytes are retained as hex with byte length and SHA-256; ACL entries and file capability bits/effective flag/root ID are decoded only when their formats validate. Missing xattrs are `absent`; permission denial, unsupported xattrs/filesystems, malformed bytes, I/O errors, and limits remain distinct statuses/diagnostics and make the snapshot partial (exit 2). Bounds include 256 selected paths, 4 KiB per path, 64 KiB and 8 MiB aggregate ACL bytes, 64 KiB and 8 MiB aggregate capability bytes, a 5-second between-path deadline, and 64 MiB serialized output. Non-UTF-8 path bytes are preserved in hex. No privilege escalation is requested. The 5-second deadline is checked between paths; an in-flight filesystem syscall cannot be canceled by the collector and can take longer. This reports configuration observed for selected objects; it does not calculate effective access or cover unselected paths. The private mode-0600 output is sensitive and remains until deleted.

`sideeffect diff --bundles LEFT_DIR RIGHT_DIR` directly compares validated `sideeffect.run` v1 or v2 bundles after applying the same strict bundle validation used by `inspect --bundle`. The JSON and text outputs match the corresponding raw-trace comparison semantics, and the Linux offline HTML export is available with `diff --bundles --format html --output REPORT LEFT_DIR RIGHT_DIR`. Manifest status fields are metadata and do not prove command success or capture completeness; partial parsed traces still fail before a comparison document is written. Bundles stopped at their requested time limit are also rejected before bundle comparison.

`sideeffect inspect TRACE` reads a regular file without executing the represented command and writes schema-v7 JSON to stdout; it fingerprints the exact bounded bytes parsed with SHA-256. Linux `sideeffect inspect --bundle DIR` validates a supported `sideeffect.run` v1 or v2 bundle without exposing the local bundle path. Schema-v2 bundle output also includes its stop reason and optional requested time limit as `bundle_capture`; raw traces and v1 bundles omit this context. Timed bundle inspection returns status 2 and warns that absence is not evidence of non-occurrence. `inspect --format text TRACE` renders all rows and diagnostics as ASCII-only terminal-safe text. Some `openat`/`openat2` records include a clearly labeled lexical path hint; it is not canonical or filesystem-resolved. Complete `execve`/`execveat`, `openat`/`openat2`, and `connect` rows include a conservative `outcome` derived only from strict syscall result spellings: recognized success, recognized Linux `-1 ERRNO (message)` failure, `connect` in progress for `EINPROGRESS`, or `unknown`. Unfinished/resumed rows and other syscalls have no outcome. Schema v5 introduced process-creation relations derived only from complete successful `fork`, `vfork`, and qualifying `clone`/`clone3` records, each linked to the result row and supporting unfinished row when a `clone3` call is split across records. In schema v7 the source is named `caller_task_id`: the `strace -f` prefix identifies the calling task/thread, not necessarily the Linux parent process when a non-leader thread creates a process. Current relations connect this caller task ID to the syscall's returned child PID; they do not claim an OS parent-child relationship. A uniquely paired unfinished/resumed `clone3` may provide flags and child result from separate evidence rows. Unpaired calls, unsupported flags, thread clones, `CLONE_PARENT` calls, and ambiguous child PIDs do not produce guessed relations. This is not a complete process tree or proof of ancestry across PID reuse. The outcome does not infer higher-level effects, and the raw line/result and evidence reference remain available. `sideeffect diff LEFT RIGHT` compares complete parses and writes schema-v3 JSON deltas with raw source line/byte references and independent hashes for the exact left/right inputs; `--format text` renders the same differences as ASCII-only terminal-safe text. `sideeffect evidence TRACE SHA256 LINE BYTE_OFFSET BYTE_LENGTH` checks that the supplied lowercase SHA-256 matches the exact bounded bytes parsed, then verifies a diff reference against one parsed syscall row and prints that row safely. Partial inputs carry a warning and status 2; malformed or mismatched hashes and control, unparsed, missing, or mismatched references are rejected. The hash helps identify bytes, but does not authenticate them, redact data, or prove capture completeness; hashes can reveal equality or be guessed for low-entropy inputs. Trace bytes remain local. On Linux, `--format html --output REPORT LEFT RIGHT` writes a bounded static offline report with no scripts or remote assets. Linux `sideeffect record --trace OUTPUT -- PROGRAM [ARGS...]` runs the selected program under external strace, inheriting its stdout/stderr, and writes a bounded raw trace. Add `--duration-seconds <seconds>` with an integer from 1 to 3600 to request a wall-clock limit: if reached, the available nonempty trace is published as partial, the direct tracer is terminated, and the command exits `2`; target outcome and capture completeness remain unknown. The diff fails closed on partial parses, compares syscall rows as a multiset, ignores only parsed timestamp and PID prefixes for matching, and compares raw syscall arguments/results exactly; `matching_policy.exact_fields` names these fields. Optional before/after lexical path hints are display-only, listed in `matching_policy.display_only_fields`, and cannot affect matching. A result change is shown as changed only when one unmatched same-signature row remains on each side; ambiguous residual multiplicities stay as additions/removals. It reports control-row counts outside the comparison. Paired unfinished/resumed records are treated as separate rows. Capture completeness remains unknown, and process/file/network labels are syscall-name buckets rather than claims of successful effects. Text escaping prevents terminal control injection; HTML escaping prevents markup interpretation; neither redacts sensitive content.
`sideeffect diff-summary` is a separate aggregate-only export with its own schema. It includes counts of added, changed, and removed diff groups by fixed category, omitting syscall names, raw arguments/results, lexical path hints, source fingerprints, evidence references, and input paths. The command does not attempt secret detection; remaining categories and counts can still be sensitive. The summary is not a safe-to-share verdict and does not retain event-level evidence. JSON goes to stdout; Linux HTML is local, bounded, mode 0600, offline, and no-clobber.

The parser and recorder enforce a 32 MiB trace limit; the parser also enforces a 64 KiB physical-record limit and a 100,000-record limit. Diff results are bounded to 200,000 rows; inspect JSON/text and diff JSON/text output are capped at 64 MiB before stdout is written. Invalid UTF-8 and hard limit violations fail without producing an inspect document. Included trace fixtures and fake-tracer tests are synthetic. A limited real capture integration test exists but does not validate broad syscall output or file/network event coverage; strace remains uninstalled system-wide in the WSL environment.

`sideeffect case init --output CASE.json --title TITLE --session SESSION_DIR` creates a private empty `sideeffect.investigation_case` v2 draft bound to verified session IDs and exact manifest digests. Repeat `--session` to include up to 16 sessions from one native platform. V2 records analyst workflow status, a branch-local revision, and the SHA-256 of exact parent-case bytes; the digest does not authenticate a writer or prevent history forks/rewrites. `case set-status` implements the documented draft/open/in-review transitions, with closed and cancelled terminal. `case add-note` reads one regular UTF-8 text file up to 16 KiB, rejects empty/invalid/NUL-containing text, and appends an existing schema-v2 note entry with `analyst_supplied_unverified` authorship and no evidence locators; it accepts no inline note text and never echoes note contents. `case add-entry` validates one bounded analyst-authored note/assertion, verifies all supplied sessions and locators, and writes a new private revision without modifying or replacing the source; entries are allowed only in draft/open cases. `case add-evidence` builds that existing v2 note/assertion shape from a separate 16 KiB UTF-8 text file and strict 64 KiB JSON array of up to 64 locators, verifies each supplied exact row against all supplied sessions before publication, and labels both kinds analyst_supplied_unverified. Missing/mismatched sessions or unresolved rows fail without a new file; resolved rows from partial/unknown sources preserve that state and exit 2. Source references do not validate analyst interpretation. Schema v1 remains readable and resolvable but has no inferred status; `case migrate` requires an explicit initial draft/open status and preserves the original evidence bindings. Assertions require at least one evidence locator and are explicitly marked `analyst_supplied_unverified`. `sideeffect case resolve --case CASE.json --session SESSION_DIR...` verifies the supplied session manifests and artifacts, then resolves Linux trace-record, Windows ETW-record, and selected-root ordinal locators to source rows. It preserves case status/revision plus session/source/parser/loss status and exits `2` when evidence remains partial or unknown. `--format html --output NEW_REPORT.html` produces a bounded private static offline report with local links from entries to resolved facts. Optional `--redact GROUP...` applies only the explicit whole-field groups `case-text`, `artifact-paths`, `source-records`, and `evidence-identifiers`; `--preview-redaction` preserves selected groups' omission counts and adds renderer-known retained/omitted occurrence counts for case-text, artifact-paths, source-records, and evidence-identifiers; it writes no report. Redacted HTML now includes a counts-only receipt for selected groups, using that same renderer-known calculation. These counts describe renderer fields/record blocks only, are not a content scan, and may overlap. Retained source records can contain arbitrary strings, arguments, or payloads; this is not a secret scan and does not make sharing safe. The `artifact-paths` group replaces all values under the exact structured key `artifact_path` in rendered source records as well as the separate artifact-path field; unrelated `path` or `display_name` values are untouched. The source case and evidence remain unchanged. Redaction does not find sensitive substrings in retained text and does not make the report safe to share; users must inspect the complete output. HTML and JSON may contain sensitive local evidence. Hashes check byte consistency but do not authenticate producers, prove capture completeness, or validate analyst assertions. `sideeffect case show --case CASE.json [--format json|text]` is a bounded, read-only summary that needs no session directories. It emits `sideeffect.investigation_case_summary` v1 by default, preserves v1 as `untracked`, reports v2 lifecycle fields and case-declared session bindings, and includes only entry metadata, text byte lengths, and locator counts. It never prints analyst text or raw evidence rows; evidence remains `not_resolved`; the case parser checks locator structure and internal bindings, but show does not open sessions or resolve locators against artifacts. It makes no authenticity or claim assessment. Text output escapes controls and non-ASCII for terminal safety. The workflow still has no interactive entry editor, role-specific report set, or general investigation query engine.

## Partial access-check probe

`inventory access-check` is an experimental, explicitly selected-path probe on Linux and Windows. Linux checks only the calling thread's current credentials with `faccessat2` and always leaves the calculated effective-access conclusion unknown. Windows evaluates a supported local file object's DACL against a process primary token selected by PID and observed creation FILETIME; even a successful DACL grant or denial leaves the overall conclusion conditional. Both preserve what the native check observed and name important unevaluated controls. Neither executes the selected operation, requests elevation, or claims to determine everything a program can access. See [the command and limitations](INSTALL.md#run-a-partial-access-check).

## Planned capture and comparison workflow

1. Record two command runs with `sideeffect record` or obtain external `strace` text files.
2. Run `sideeffect diff LEFT RIGHT` to compare parsed syscall rows and receive exact source references.
3. Inspect the source rows for each reported delta; the tool does not infer a cause or prove capture coverage.
4. On Linux, `sideeffect diff --format html --output REPORT LEFT RIGHT` creates a static offline report with source references; review it before sharing.

The recorder uses a private FIFO sink with a 32 MiB ceiling and publishes a bounded nonempty raw trace without replacing an existing file or symlink. `record --bundle` instead stages `run.json` and `trace.strace` together and publishes the directory atomically with no-clobber semantics. The mode-0700 bundle directory contains mode-0600 files. New `sideeffect.run` v2 manifests store tool/platform/tracer/profile metadata, raw strace status, explicit unknown/unverified markers, exact trace length/hash, optional duration and stop reason; v1 remains readable. The manifest omits the command, argv, environment, cwd, username, absolute paths, output streams, tracer diagnostics, and parsed events. The trace remains sensitive and its hash can reveal equality; neither authenticity nor completeness is established. Bundle inspection accepts supported strict v1/v2 schemas and fixed files; it rejects extra entries, symlinks, wrong ownership/modes, over-limit inputs, and trace length or hash mismatches before parsing. If the trace byte limit is exceeded, recording fails and discards staging. If the optional duration limit is reached, the available nonempty partial trace or bundle is published and the command exits `2`. Inspecting a timed bundle also exits `2` with a warning that absence is not evidence of non-occurrence; `diff --bundles` refuses timed bundles because their event sets are incomplete. SideEffect's tested minimum is strace 6.8; strace introduced `--kill-on-exit` in 6.6. The option is best-effort cleanup, and descendants using `CLONE_UNTRACED` may escape. The command runs without a shell under the user's permissions, and stdout/stderr are inherited. After finalizing and publishing a nonempty trace or complete bundle, the CLI propagates strace's reported exit code or signal. The strace manual says it normally mirrors the wrapped command's outcome; this does not independently verify the target status, tracer success, or capture completeness. Detected SideEffect capture errors take precedence. Capture is not a sandbox and may change process timing or behavior. One real smoke test confirms FIFO capture and parsing for trivial process invocations, but broader option compatibility, cleanup, and event coverage remain unvalidated. The HTML exporter is Linux-only, caps the rendered file, publishes mode-0600 output without replacing an existing destination, and includes no local input paths. Raw syscall values can still be sensitive. The initial diff does not normalize file descriptors, paths, or PID-like values embedded in syscall arguments/results; those may appear as differences. Its fixture pair is synthetic.

## Product principles

### Evidence before interpretation

Reports state what the capture observed: for example, a process executed a child command, a syscall attempted to open a path, or a process attempted a socket connection to an IP address and port. A failed syscall is still an observed attempt, not a successful effect. Event ancestry and timing can help readers investigate; they do not establish complete causal attribution.

Derived comparison fields must retain references to the raw events from which they were derived. Exact captured values remain available in the local run record; normalization is a separate, documented comparison view.

### Capture completeness is visible

Each run must record capture status and relevant limitations, including tracer startup/exit status, command exit status, parser warnings, and indications of truncated or incomplete input when detectable. Missing data must not be rendered as evidence that an event did not occur. A report should make incomplete or unsupported observation conspicuous.

### Local by default, sensitive by design

`inspect` and `diff` read local inputs and write to stdout; `record` creates one local trace file. There is no upload or telemetry path. Traces retain raw syscall text and can contain sensitive arguments, paths, endpoint details, and other values. Command stdout/stderr are inherited rather than collected. Users must inspect traces before sharing them.

### Honest network representation

The first release may observe connection-related syscalls. It must distinguish an observed destination IP address and port from a hostname or DNS identity. It must not claim that the process contacted a particular hostname unless that information is independently and explicitly observed. Network payload capture and DNS identity resolution are outside v0.

## Proposed v0 scope

- Inspect one selected local, regular `strace` text file and emit a versioned JSON evidence document to stdout, with an optional terminal-safe text listing of all parser records and diagnostics.
- Preserve raw records and source byte offsets; report malformed, unsupported, or unpaired continuation lines as diagnostics.
- Enforce the current parser budgets: 32 MiB per input, 64 KiB per physical record, 100,000 records, and 64 MiB JSON or text output. These initial limits require review against real captures before release.
- Linux x86_64 with a separately installed `strace` executable.
- Run one command under tracing and save a local evidence bundle.
- Capture process execution/lifecycle, selected file-related calls, and connection-related calls supported by the chosen trace configuration.
- Parse and preserve raw trace evidence; create a versioned canonical event representation.
- Compare two runs with explainable normalization and event-level references.
- Produce JSON and offline HTML reports with escaped untrusted values.
- Preserve the wrapped command's exit status and stdout/stderr behavior as closely as the implementation permits, and document any differences.
- Include deterministic fixtures for parser, normalization, diff, incomplete-capture, and report-rendering behavior.

## Explicit non-goals for the current implementation

- Claiming native Windows support before its inventory and bounded runtime workflows are implemented and validated.
- Identical low-level event coverage or permission semantics across operating systems.
- A sandbox, malware detector, vulnerability scanner, or guarantee that all relevant behavior was observed.
- Full syscall coverage independent of `strace` and kernel support.
- Network payload capture, packet inspection, or authoritative DNS-to-process attribution.
- Automatic secret removal or a guarantee that an exported report is safe to publish.
- Automatic root-cause analysis, LLM-generated explanations, or claims that an event caused another event.
- Cloud accounts, hosted dashboards, telemetry, team collaboration, or report upload.
- Blanket suppression of temporary paths or other changing values. Any comparison normalization must be explicit and inspectable.

## Success criteria for the v0 technical foundation

- A user can record two supported command runs and receive a report that identifies added, removed, and changed observed event groups.
- Every reported event difference links back to raw evidence and identifies which run it came from.
- The report distinguishes observed facts, derived comparison keys, and unavailable/uncertain fields.
- The run record exposes capture warnings and does not treat incomplete observation as proof of absence.
- A stable fixture pair with changed top-level PIDs and timestamps does not create differences solely because those prefixes changed, while the exact raw source lines remain available.
- A fixture with a real added child execution, file operation, and connection event displays those changes accurately without claiming root cause or successful connection unless the trace shows success.
- Malicious markup in trace strings renders as inert text in the offline HTML report.
- Documentation states the Linux/strace prerequisite, local storage behavior, sensitive-data risk, and observation limits before asking users to share reports.

These are acceptance targets for future implementation and tests, not claims about the current repository.

## Cross-platform release gate

Before calling SideEffect 1.0 cross-platform, a native Windows user must be able to take a useful software/process/selected-path-permission/startup snapshot, record a bounded runtime window, inspect its evidence, compare two runs, and export a readable offline report using the same high-level workflow available on Linux. Reports must state Windows-specific source scope, privilege requirements, event loss, and unknowns. Windows CI and a real Windows integration run are required; parser fixtures or WSL2 runs alone do not satisfy this gate. The portable Agent Skill is an additional interface to the same local CLI and does not replace native platform validation. Optional local-model quality work is active again, remains experimental, and is not part of the core product completion gate.

## Open decisions

- Exact `strace` version range, supported distributions, and behavior when a requested event class is unavailable.
- Whether raw traces should be compressed; published-data retention and deletion are user-controlled as described above.
- Capture diagnostics needed to independently distinguish tracer failure from a wrapped command result. `record` currently propagates strace's reported status only after successful trace publication and does not independently verify tracer success or command status.
- Safe handling of command output when stdout/stderr are streamed or captured.
- JSON schema versioning and compatibility policy.
- License compatibility, packaging, and whether/how an external `strace` dependency is pinned or installed. No licensing or redistribution conclusion is made here.
- Which normalization rules are sufficiently reliable for v0 and how ambiguous path resolution is presented.
