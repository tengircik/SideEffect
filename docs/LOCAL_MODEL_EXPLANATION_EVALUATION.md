# Local evidence explanation development

**Status:** experimental development path; not a release endorsement. The original local evidence-selection and query-plan experiments have separate frozen quality gates. This explanation path has a separate, development-only corpus and has not passed a semantic quality gate. The model now selects evidence rows; it does not write explanation prose. Selection quality is still unqualified and must not guide safety, security, permission, or operational decisions.

## Data flow

The catalog includes `explanation-qwen3.5-4b-q4-k-m` for Linux x86_64 and native Windows. Use `sideeffect model list` and `sideeffect model show explanation-qwen3.5-4b-q4-k-m` to inspect its source, revision, 2,783,446,368-byte size, Apache-2.0 license, and evaluation status. Install it with `sideeffect model install explanation-qwen3.5-4b-q4-k-m`, review the terms, and type the exact `ACCEPT Apache-2.0` confirmation; then run `sideeffect model select explanation explanation-qwen3.5-4b-q4-k-m`. It failed its development check, answering only 4 of 26 synthetic questions, and is not recommended for decisions. There is no positive quality recommendation. An alternative existing local GGUF can be registered with `sideeffect model add --name NAME --path FILE --for explanation [--license ID]`; the file is bounded to 3 GiB, and any supplied license ID is unverified. The runtime is separately obtained and installed by the user.

`sideeffect model-explain-preview --question QUESTION --backend auto|cpu|cuda TRACE` parses the bounded local trace and previews the exact question, typed evidence facts, coverage metadata, prompt, output schema, selected model identity, deterministic scope-abstention decision, and request SHA-256. It may include a conservative, plain-ASCII lexical executable path hint derived from the `execve`/`execveat` path argument and lexical file path hints for selected `openat`/`openat2` rows. It does not include argv or environment strings, resolve paths, or establish which file was ultimately executed. These hints and evidence labels may still disclose sensitive information; inspect the preview before running inference. Preview schema v3 exposes `deterministic_abstain_reason`; a non-null value means `model-explain` returns a deterministic abstention without starting a model runtime. The bounded English phrase checks cover selected unsupported conclusions and are not a general natural-language understanding guarantee. The digest binds the selected model ID and SHA-256, source/revision or user-provided marker, license/evaluation status, runtime revision, backend preference, output schema, and this deterministic decision.

`sideeffect model-explain` requires the selected runtime path and exact preview digest; the model path comes from the per-task selection. A changed selection invalidates the digest. It stages a hash-verified copy of the selected model and private, bounded prompt files in a per-user temporary directory, invokes the local runtime once without a shell, and removes the staging directory on completion. The runtime receives no command-execution interface. The model response schema accepts only a bounded array of unique IDs from `observed_syscall_results`; process-relation IDs, model-authored text, kinds, and status claims are rejected. SideEffect maps the selected IDs to the exact syscall-result rows in the reviewed prompt. The output's `selection_status` is `selected`, `partial_selection` when the source parse is not complete, or `abstained` for an empty selection. These labels report selection and parse state only; they do not say the model answered the question or that its selection is correct. Deterministic scope abstentions still return without starting the runtime.

Qwen3.5-4B Q4_K_M was the historical development candidate: repository `gguf/Qwen3.5-4B-GGUF`, revision `76e05555d64c8d045dd4b9c9f1ebaef1e35d99f7`, file size 2,783,446,368 bytes, SHA-256 `c3c2cf023efdbd913c2363a14d5c7266db5e05c4602f1c0790eaed567d8aff23`. It is not a positive quality recommendation. Current inference uses the registered, per-task selected model and reports its identity in the preview. The selected llama.cpp runtime must report revision `19cce6919992fdffd92e0ac152caaf1e2b8f254e`; the reported version string does not authenticate the executable binary. Treat the runtime and its loaded libraries as trusted code running with the current user's permissions. SideEffect can download this pinned GGUF through the explicit catalog install flow after typed license acceptance; it does not download the runtime or send evidence to a hosted service.

## Windows GPU path

Native Windows inference supports explicit `cpu`, explicit `cuda`, and `auto`. `auto` prefers CUDA when the selected runtime reports `CUDA0`; otherwise it reports CPU. A CUDA initialization or inference failure is returned as an error, partial output is discarded, and there is no silent CPU fallback. CUDA is reported as used only if the runtime diagnostics contain positive layer-offload evidence.

The runtime is llama.cpp's `llama-completion` built from the pinned source revision with CUDA enabled. For example, from a llama.cpp checkout at that revision, configure with `cmake -B build -DGGML_CUDA=ON` and build the `llama-completion` target. SideEffect can install the pinned explanation GGUF from its catalog after the user reviews its license terms and provides the explicit typed acceptance; analysis itself never downloads a model. The runtime remains separately obtained and installed by the user. Users may instead register and select an existing local GGUF as described above. SideEffect verifies the selected model's SHA-256 and size again before inference. Model architecture/runtime compatibility is not guaranteed by registration.

The Windows runner starts the child suspended, assigns it to a kill-on-close Job Object before resuming it, limits the process tree to one process, caps host process memory at 6 GiB, bounds runtime and captured output, and stages the verified model privately. It clears the inherited environment and supplies only required Windows and validated runtime dependencies. These controls do **not** limit CUDA VRAM or deny network access. `--offline` is a runtime option, not an isolation boundary. The result includes this limitation. GPU availability is not a promise of a hard VRAM ceiling; allocation failures are surfaced and CUDA usage is not measured as process-isolated peak VRAM.

Example, after obtaining and verifying the pinned artifacts:

```powershell
$preview = sideeffect model-explain-preview --question "What happened to the observed connection?" --backend cuda TRACE.strace | ConvertFrom-Json
sideeffect model-explain --question "What happened to the observed connection?" --backend cuda --runtime LLAMA_COMPLETION.exe --confirm-sha256 $preview.request_sha256 TRACE.strace
```

Review the preview's complete JSON and sensitive fields before confirming. Replace the placeholder paths with local paths. `auto` prefers CUDA when the selected runtime reports a device, otherwise it reports CPU; CUDA errors do not silently fall back. Windows Job Objects do not limit CUDA VRAM or deny network access. Model downloads require the separate explicit `model install` and license-confirmation flow; inference does not download a model, and SideEffect does not install the runtime.

## Development corpus and release gate

`tests/fixtures/local_model_explain_v1/corpus.json` pins 26 synthetic cases, 14 synthetic traces, one four-case source-order permutation group, and its expected semantic/evidence labels. Its SHA-256 is `cd67fd08e783743808b08914b775992f9c6ee0a24a14ad7a3568684940ff16be`. The `process-relation.trace` fixture uses a supported `clone3` flag so its expected child relation is present in the parser evidence; the earlier `flags=0` fixture was rejected as unsupported and could not support that question. The evaluator command `py -3 scripts/evaluate_local_model_explain.py --check-corpus` verifies only corpus structure and fixture hashes. The corpus bytes and schema stay at historical v1. `--results` dispatches by results `schema_version`: v1 continues to check the saved prose-response contract, while v2 checks only `selection_status`, unique selected evidence IDs, source parse state, ID membership, and diagnostic evidence-label coverage. V2 requires bounded run metadata (`model_id`, `model_sha256`, `runtime_source_revision`, and `backend_preference`) and records per-case `backend_used`; it accepts no runtime paths. Backend and model identity are supplied metadata, not authenticated by the validator. A `cuda` backend value must come from product output, which is emitted only after the runtime reports positive layer offload; the validator does not independently verify that evidence. V2 reports required labels unavailable to the syscall-only selector separately and excludes them from its available-label recall denominator. The supplied `available_evidence.semantic_labels` are annotations and are not verified automatically; recall is diagnostic only. Per-case `latency_ms` is supplied by the results producer, not independently measured; the percentile covers cases with valid selector results and excludes execution-error cases. V2 does not compare selector states to legacy `expected_status`/`expected_abstain_reason` or verify semantic correctness. Neither mode launches a model. The corpus is development-only, must not be used as the final release gate, and must not replace or modify the frozen local query-plan v2 holdout.

The first direct CUDA quality sweep of the explanation path returned an answer for only 4 of 26 synthetic cases; the remaining cases abstained, including several with explicit requested facts. A follow-up four-case prompt experiment with concrete examples also abstained on all four cases. CUDA layer offload and output-schema validity do not establish useful semantic quality. These results are a no-go for treating the current explanation model/prompt as a user-ready capability. Do not describe M8 as complete based on GPU execution or schema-valid output.

### Compact candidate triage — 2026-10-28

Two compact Apache-2.0 GGUFs were checked on the straightforward synthetic case `Which executable was observed to start successfully?` using SideEffect's native Windows `model-explain-preview` / `model-explain` path and a CUDA-requested pinned llama.cpp runtime. IBM Granite 4.0 1B Q4_K_M (`ibm-granite/granite-4.0-1b-GGUF` at `b27c2fe3f211b7f44e80fa620177aea371099aaa`, 1,023,645,440 bytes, SHA-256 `22ec0f9cc99a90185312de3c882c84e7bd6789bdd050389844380a01a831d7f1`) and Qwen2.5 1.5B Instruct Q6_K (`Qwen/Qwen2.5-1.5B-Instruct-GGUF` at `dd26da440ef0330c47919d1ecae0966d24022222`, 1,464,178,720 bytes, SHA-256 `e16d94f3b1eb243f6f6be9eee51090ef5dfd741324394fd5b6e0e425c33df5c7`) both returned `status=abstained`, `abstain_reason=unsupported_scope`, and no statements. The results were produced by the actual product command with isolated temporary Windows model registries and synthetic fixtures. Both previews reported `backend=cuda` and `backend_status=cuda_requested_device_available`; no process-isolated VRAM peak was measured. These one-case triage failures do not constitute a full evaluation, but neither candidate justifies a larger explanation-corpus run. Their weights are temporary and are removed after their results are recorded. No explanation prompt, schema, evaluation set, or acceptance criteria changed.

The Granite file was also selected in an isolated WSL registry. Before the Linux resource-limit fix, `model-explain` rejected its configured 6 GiB address-space cap because the shared Linux runner permits at most 4 GiB; that failure was a product runtime defect and not a model result. The Linux x86_64 configuration now uses 4 GiB, while Windows retains its 6 GiB Job Object limit; platform-specific tests verify that each limit is accepted by its runner. After the Linux diagnostic cap was raised to 32 KiB, the rebuilt product command completed inference on the same synthetic preview and emitted a schema-valid `abstained` / `unsupported_scope` result with no statements. The command returned nonzero for the abstention. This verifies the corrected Linux execution path, not answer quality; Granite remains a no-go for the tested task, and no model is recommended or release-approved.

### Qwen3 candidate and deterministic scope guard — 2026-10-30

A second, user-registered Qwen3 4B Q4_K_M model (`Qwen/Qwen3-4B-GGUF`, model revision `bc640142c66e1fdd12af0bd68f40445458f3869b`, 2,497,280,256 bytes, SHA-256 `7485fe6f11af29433bc51cab58009521f205840f5b4ae3a32fa7f92e8534fdf5`, Apache-2.0) was evaluated through SideEffect's release-mode Windows CLI on the same 26-case development corpus using CUDA and the pinned llama.cpp source revision. The runtime reported GPU layer offload to an NVIDIA RTX 3060. Across this development run, 26/26 response contracts were valid, there were no runtime errors, expected status/reason matched 26/26 after correcting the deterministic absence classification, required evidence-label recall was 100%, and the four-case source-order permutation group was consistent. P95 latency was 16,966 ms. The fast deterministic abstentions took about 1.8 seconds; the model-backed cases were materially slower. These measurements are specific to this machine and synthetic corpus.

An independent read-only review of every historical generated statement found semantic defects: an ENOENT statement broadened the exact observed result into “not found or accessed”; an injection-bearing question received only the path and omitted its requested EACCES result; a partial-parse answer omitted the successful return that qualified the observed start; and one permutation answer repeated the same network event. One other permutation answer used a less precise “network operation” label. The review found the instruction-like text was not followed and other reviewed facts/citations matched the synthetic records. These were defects in the former prose response contract. The current schema v2 does not expose model-authored prose; it returns exact selected preview rows. That change does not establish that a selected row answers a question. This historical review was not a human-reviewed holdout and does not verify broad real-world accuracy. The candidate remains not release-approved because selection quality has not passed a separately frozen, independently reviewed holdout. The deterministic guard handles selected English phrases only and is not general natural-language validation.

Before release consideration, create an independently reviewed, frozen corpus with preregistered scoring, meaningful unanswerable cases, order controls, injection cases, independent reviewers for semantic support and unsafe claims, repeatable latency/resource measurement, and explicit platform/runtime coverage. Keep candidate prompt development separate from the frozen holdout. Require zero invalid citations, zero unsupported safety/root-cause/effective-access/completeness conclusions, strong answerable evidence-label recall, correct abstention on unanswerable cases, and improvement over a deterministic baseline. Passing synthetic criteria would still not prove real-world accuracy. Until that gate and platform security review pass, the feature remains experimental and local-model quality work remains open and release-blocking; M8's administrative implementation closure does not certify model readiness.
