# Local evidence explanation development

**Status:** experimental development path; not a release endorsement. The original local evidence-selection and query-plan experiments have separate frozen quality gates. This explanation path has a separate, development-only corpus and has not passed a semantic quality gate. The model now selects evidence rows; it does not write explanation prose. Selection quality is still unqualified and must not guide safety, security, permission, or operational decisions.

## Data flow

The catalog includes `explanation-qwen3.5-4b-q4-k-m` for Linux x86_64 and native Windows. Use `sideeffect model list` and `sideeffect model show explanation-qwen3.5-4b-q4-k-m` to inspect its source, revision, 2,783,446,368-byte size, Apache-2.0 license, and evaluation status. Install it with `sideeffect model install explanation-qwen3.5-4b-q4-k-m`, review the terms, and type the exact `ACCEPT Apache-2.0` confirmation; then run `sideeffect model select explanation explanation-qwen3.5-4b-q4-k-m`. It failed its development check, answering only 4 of 26 synthetic questions, and is not recommended for decisions. There is no positive quality recommendation. An alternative existing local GGUF can be registered with `sideeffect model add --name NAME --path FILE --for explanation [--license ID]`; the file is bounded to 3 GiB, and any supplied license ID is unverified. The runtime is separately obtained and installed by the user.

`sideeffect model-explain-preview --question QUESTION --backend auto|cpu|cuda TRACE` parses the bounded local trace and previews the exact question, typed evidence facts, coverage metadata, prompt, output schema, selected model identity, deterministic scope-abstention decision, and request SHA-256. It may include a conservative, plain-ASCII lexical executable path hint derived from the `execve`/`execveat` path argument and lexical file path hints for selected `openat`/`openat2` rows. It does not include argv or environment strings, resolve paths, or establish which file was ultimately executed. These hints and evidence labels may still disclose sensitive information; inspect the preview before running inference. Preview schema v3 exposes `deterministic_abstain_reason`; a non-null value means `model-explain` returns a deterministic abstention without starting a model runtime. The bounded English phrase checks cover selected unsupported conclusions and are not a general natural-language understanding guarantee. The digest binds the selected model ID and SHA-256, source/revision or user-provided marker, license/evaluation status, runtime revision, backend preference, output schema, and this deterministic decision.

`sideeffect model-explain` requires the selected runtime path and exact preview digest; the model path comes from the per-task selection. A changed selection invalidates the digest. It stages a hash-verified copy of the selected model and private, bounded prompt files in a per-user temporary directory, invokes the local runtime once without a shell, and removes the staging directory on completion. The runtime receives no command-execution interface. The model response schema accepts only a bounded array of unique IDs from `observed_syscall_results`; process-relation IDs, model-authored text, kinds, and status claims are rejected. SideEffect maps the selected IDs to the exact syscall-result rows in the reviewed prompt. The output's `selection_status` is `selected`, `partial_selection` when the source parse is not complete, or `abstained` for an empty selection. These labels report selection and parse state only; they do not say the model answered the question or that its selection is correct. Deterministic scope abstentions still return without starting the runtime.

Qwen3.5-4B Q4_K_M was the historical development candidate: repository `gguf/Qwen3.5-4B-GGUF`, revision `76e05555d64c8d045dd4b9c9f1ebaef1e35d99f7`, file size 2,783,446,368 bytes, SHA-256 `c3c2cf023efdbd913c2363a14d5c7266db5e05c4602f1c0790eaed567d8aff23`. It is not a positive quality recommendation. Current inference uses the registered, per-task selected model and reports its identity in the preview. The selected llama.cpp runtime must report revision `19cce6919992fdffd92e0ac152caaf1e2b8f254e`; the reported version string does not authenticate the executable binary. Treat the runtime and its loaded libraries as trusted code running with the current user's permissions. SideEffect can download this pinned GGUF through the explicit catalog install flow after typed license acceptance; it does not download the runtime or send evidence to a hosted service.

## Windows GPU path

Native Windows inference supports explicit `cpu`, explicit `cuda`, and `auto`. `auto` prefers CUDA when the selected runtime reports `CUDA0`; otherwise it reports CPU. A CUDA initialization or inference failure is returned as an error, partial output is discarded, and there is no silent CPU fallback. CUDA is reported as used only if the runtime diagnostics contain positive layer-offload evidence.

The runtime is llama.cpp's `llama-completion` built from the pinned source revision with CUDA enabled. For example, from a llama.cpp checkout at that revision, configure with `cmake -B build -DGGML_CUDA=ON -DLLAMA_BUILD_COMMIT=19cce6919992fdffd92e0ac152caaf1e2b8f254e` and build the `llama-completion` target. Passing the full revision is required because llama.cpp's default version string reports only a seven-character short hash, which does not satisfy SideEffect's pinned revision check. SideEffect can install the pinned explanation GGUF from its catalog after the user reviews its license terms and provides the explicit typed acceptance; analysis itself never downloads a model. The runtime remains separately obtained and installed by the user. Users may instead register and select an existing local GGUF as described above. SideEffect verifies the selected model's SHA-256 and size again before inference. Model architecture/runtime compatibility is not guaranteed by registration.

The Windows runner starts the child suspended, assigns it to a kill-on-close Job Object before resuming it, limits the process tree to one process, caps host process memory at 6 GiB, bounds runtime and captured output, and stages the verified model privately. It clears the inherited environment and supplies only required Windows and validated runtime dependencies. These controls do **not** limit CUDA VRAM or deny network access. `--offline` is a runtime option, not an isolation boundary. The result includes this limitation. GPU availability is not a promise of a hard VRAM ceiling; allocation failures are surfaced and CUDA usage is not measured as process-isolated peak VRAM.

Example, after obtaining and verifying the pinned artifacts:

```powershell
$preview = sideeffect model-explain-preview --question "What happened to the observed connection?" --backend cuda TRACE.strace | ConvertFrom-Json
sideeffect model-explain --question "What happened to the observed connection?" --backend cuda --runtime LLAMA_COMPLETION.exe --confirm-sha256 $preview.request_sha256 TRACE.strace
```

Review the preview's complete JSON and sensitive fields before confirming. Replace the placeholder paths with local paths. `auto` prefers CUDA when the selected runtime reports a device, otherwise it reports CPU; CUDA errors do not silently fall back. Windows Job Objects do not limit CUDA VRAM or deny network access. Model downloads require the separate explicit `model install` and license-confirmation flow; inference does not download a model, and SideEffect does not install the runtime.

## Development corpus and release gate

`tests/fixtures/local_model_explain_v1/corpus.json` pins 26 synthetic cases, 14 synthetic traces, one four-case source-order permutation group, and its expected semantic/evidence labels. Its SHA-256 is `cd67fd08e783743808b08914b775992f9c6ee0a24ad7a3568684940ff16be`. The `process-relation.trace` fixture uses a supported `clone3` flag so its expected child relation is present in the parser evidence; the earlier `flags=0` fixture was rejected as unsupported and could not support that question. The evaluator command `py -3 scripts/evaluate_local_model_explain.py --check-corpus` verifies only corpus structure and fixture hashes. The corpus bytes and schema stay at historical v1. `--results` dispatches by results `schema_version`: v1 checks the historical prose-response contract and accepts legacy human-review annotations; v2 checks the selector contract; v3 adds blinded human-review annotations to selector results. V2 and v3 require bounded run metadata (`model_id`, `model_sha256`, `runtime_source_revision`, and `backend_preference`) and record per-case `backend_used`; runtime paths are rejected. Backend and model identity are supplied metadata, not authenticated by the validator. A `cuda` backend value must come from product output, which is emitted only after the runtime reports positive layer offload; the validator does not independently verify that evidence. V2 and v3 report required labels unavailable to the syscall-only selector separately and exclude them from their available-label recall denominator. Supplied `available_evidence.semantic_labels` are annotations and are not verified automatically; recall is diagnostic only. Per-case `latency_ms` is supplied by the results producer, not independently measured; the percentile covers cases with valid selector results and excludes execution-error cases. Selector results do not get compared with legacy prose labels to infer semantic correctness. Neither mode launches a model. The corpus is development-only, must not be used as the final release gate, and must not replace or modify the frozen local query-plan v2 holdout.

### Blinded human review for selector results

Results schema v3 adds `preview_request_sha256` and `review_target_sha256` to each selector result row, plus a `human_reviews` array. Each reviewer annotation repeats both digests. `preview_request_sha256` is the exact `request_sha256` from the SideEffect `model-explain-preview` output. The evaluator checks its format and equality between the result row and each review, but cannot recompute or authenticate the preview digest, verify the redaction, or prove the blind packet came from that preview. The packet preparer—not the reviewer—must inspect the original preview to confirm this value and prepare the blind packet below. Reviewers must see only that packet, never the identity-bearing original preview or model output.

`review_target_sha256` binds the review to a canonical target object containing schema/version, pinned corpus digest, case ID, the case question, `preview_request_sha256`, selector response, source parse status, and the complete bounded `available_evidence` array. Canonical bytes are UTF-8 JSON emitted with lexicographically sorted object keys, `ensure_ascii=false`, separators `,` and `:` with no spaces, and `allow_nan=false`; there is no trailing newline. SHA-256 is computed over those bytes. The validator reconstructs the target digest from the unchanged pinned case question and result row, then rejects an invalid, stale, or reviewer-mismatched digest. Do not include expected corpus semantic labels in the reviewer packet.

Each review uses an opaque `reviewer_id`, attests `blind_to_model_identity` and `independence_attested`, records the reviewer's `answerability` (`answerable`, `unanswerable`, or `uncertain`) and independently identified `required_evidence_labels`, then assesses every selected evidence ID with the subset of required labels it supports and an `unsupported_inference` flag. These are reviewer-provided judgments, not facts the evaluator derives from response shape or the corpus's structural labels.

Prepare each blind packet manually from the exact preview and its corresponding analysis result. Include the preview schema/version, case ID, question, deterministic abstention reason, model-independent `system_prompt`, exact bounded `prompt`, `output_schema`, and `evidence_summary` (including scope/coverage and known unknowns). From the analysis result include only `selection_status`, `evidence_ids`, and `abstain_reason`. Carry `request_sha256` only as the opaque `preview_request_sha256` linkage value. Omit model ID, repository/revision, filename, size/hash/source, license/evaluation status, runtime revision/version, backend/preference, interpretation metadata, and all other identity-bearing fields from both the preview and analysis output. Do not show expected corpus labels, candidate scores, or the original identity-bearing JSON to reviewers.

This is a human-controlled transformation; no tool currently constructs or verifies the blind packet. The evaluator only checks that the result row's opaque preview digest is well formed and repeats consistently in reviewer annotations. Its canonical target hash binds that supplied digest with the row's question, selector result, parse state, and available evidence IDs/labels, but does not hash the packet contents or prove that redaction was complete or correct. The preparer must compare the packet's evidence, question, scope/coverage and selected IDs against the exact preview/result before sending the packet. Keep this comparison and review local; capture values can be sensitive, and digest linkage is not proof of blinding.

Keep reviewers blinded to model/runtime identity, candidate scores and corpus expectations. Give them the case question, bounded evidence preview and selected IDs. Do not include private names or free-form notes in the result file. A reviewer is counted as fully complete only when every corpus case has a selector output and that reviewer has supplied a complete review for every case while attesting to blinding and independence. The report computes each reviewer's required-label coverage, pairwise required-label set agreement, pairwise answerability agreement, and reviewer-marked unsupported-inference count. It also compares reviewer answerability with the selector state: `answerable` versus selected/partial-selection and `unanswerable` versus abstained. The report gives the determinate-case denominator, agreement count/rate, false positives (selected despite reviewer-marked unanswerable), false negatives (abstained despite reviewer-marked answerable), and separately counts `uncertain` cases excluded from that metric. Execution-error cases are outside this metric's denominator and prevent full-review status. This is diagnostic only and has no pass threshold. The review status remains `not_independently_reviewed` unless two or more distinct reviewer IDs fully complete all cases. The IDs and attestations are self-reported; the validator cannot verify reviewer identities, actual independence, or whether blinding was maintained.

A v3 review-entry fragment looks like this; the enclosing case row also carries both digests with the same values, plus the normal selector fields, and the result file must contain every corpus case:

```json
{
  "preview_request_sha256": "<the exact request_sha256 shown by SideEffect preview>",
  "review_target_sha256": "<64 lowercase hexadecimal characters from the case row>",
  "reviewer_id": "reviewer-a",
  "blind_to_model_identity": true,
  "independence_attested": true,
  "answerability": "answerable",
  "required_evidence_labels": ["observed_exec"],
  "selected_evidence_judgments": [
    {
      "evidence_id": "E001",
      "supported_required_evidence_labels": ["observed_exec"],
      "unsupported_inference": false
    }
  ]
}
```

Run `py -3 scripts/evaluate_local_model_explain.py --results PATH_TO_REVIEWED_RESULTS.json` to validate a v1, v2, or v3 results file and print its diagnostic report. Keep both review inputs and any redirected report outside the repository with private permissions; evidence labels and selected records may be sensitive.

This status is a review-completeness indicator, not a model-quality gate. Agreement is not correctness, labels are not automatically validated as semantic truth, and reviewer counts do not establish general accuracy. The report explicitly keeps model semantic correctness unverified. V1 and v2 result files remain supported unchanged; use v3 only for new selector review runs. The frozen corpus remains development-only, and this workflow does not qualify any model or change acceptance thresholds.

An earlier direct CUDA sweep of the catalog candidate returned an answer for only 4 of 26 synthetic cases; the remaining cases abstained, including several with explicit requested facts. A follow-up four-case prompt experiment with concrete examples also abstained on all four cases. CUDA layer offload and output-schema validity do not establish useful semantic quality. These results are a no-go for treating the current explanation model/prompt as a user-ready capability. Do not describe M8 as complete based on GPU execution or schema-valid output.

### Native Windows CUDA development sweep — 2026-11-01

The current SideEffect release CLI was run over all 26 synthetic cases in the unchanged corpus (`cd67fd08e783743808b08914b775992f9c6ee0a24ad7a3568684940ff16be`). The candidate was the existing local Ollama alias `qwen3.5:4b`; SideEffect registered the existing GGUF blob without downloading or copying it. The alias, license, publisher, and model quality are not authenticated by that digest. Inference used a locally built CUDA runtime from pinned llama.cpp revision `19cce6919992fdffd92e0ac152caaf1e2b8f254e`; `llama-completion.exe` SHA-256 was `11ba4b01979ea04e5f0af7b525f475d1a241c356505b56bc9bb0a68cd4f48c63`. The runtime reported an NVIDIA GeForce RTX 3060 as `CUDA0`; no per-process VRAM peak was measured.

The registered model lived in a temporary isolated SideEffect registry. All 26 rows passed the results-v2 structural validator, with zero execution errors. Seventeen cases launched inference and reported `backend_used=cuda`; nine cases were deterministic pre-inference abstentions. Across the full corpus there were 20 abstentions, five selections, and one partial selection. The diagnostic selector recall was 7/25 (28%) over required labels marked available to the selector; four other required labels were not represented in its bounded evidence view. The four-case source-order permutation group remained consistent. The harness supplied per-case wall-clock latency; p95 was 9,708 ms and is not a runtime-provided measurement. Supplied evidence-label mappings and latency were not independently verified by the evaluator.

This is a reproducible, single-machine, single-model development result, not a reviewed semantic benchmark or release gate. The low recall on straightforward supported questions confirms that this model/configuration is not recommended for evidence selection. The evaluator does not prove answer truth, reviewer agreement, publisher identity, GPU memory use, or general model safety. No model is approved, and the deterministic CLI remains usable without an LLM. Temporary result files and the temporary build/registry were kept outside the repository.

### Compact candidate triage — 2026-10-28

Two compact Apache-2.0 GGUFs were checked on the straightforward synthetic case `Which executable was observed to start successfully?` using SideEffect's native Windows `model-explain-preview` / `model-explain` path and a CUDA-requested pinned llama.cpp runtime. IBM Granite 4.0 1B Q4_K_M (`ibm-granite/granite-4.0-1b-GGUF` at `b27c2fe3f211b7f44e80fa620177aea371099aaa`, 1,023,645,440 bytes, SHA-256 `22ec0f9cc99a90185312de3c882c84e7bd6789bdd050389844380a01a831d7f1`) and Qwen2.5 1.5B Instruct Q6_K (`Qwen/Qwen2.5-1.5B-Instruct-GGUF` at `dd26da440ef0330c47919d1ecae0966d24022222`, 1,464,178,720 bytes, SHA-256 `e16d94f3b1eb243f6f6be9eee51090ef5dfd741324394fd5b6e0e425c33df5c7`) both returned `status=abstained`, `abstain_reason=unsupported_scope`, and no statements. The results were produced by the actual product command with isolated temporary Windows model registries and synthetic fixtures. Both previews reported `backend=cuda` and `backend_status=cuda_requested_device_available`; no process-isolated VRAM peak was measured. These one-case triage failures do not constitute a full evaluation, but neither candidate justifies a larger explanation-corpus run. Their weights are temporary and are removed after their results are recorded. No explanation prompt, schema, evaluation set, or acceptance criteria changed.

The Granite file was also selected in an isolated WSL registry. Before the Linux resource-limit fix, `model-explain` rejected its configured 6 GiB address-space cap because the shared Linux runner permits at most 4 GiB; that failure was a product runtime defect and not a model result. The Linux x86_64 configuration now uses 4 GiB, while Windows retains its 6 GiB Job Object limit; platform-specific tests verify that each limit is accepted by its runner. After the Linux diagnostic cap was raised to 32 KiB, the rebuilt product command completed inference on the same synthetic preview and emitted a schema-valid `abstained` / `unsupported_scope` result with no statements. The command returned nonzero for the abstention. This verifies the corrected Linux execution path, not answer quality; Granite remains a no-go for the tested task, and no model is recommended or release-approved.

### Qwen3 candidate and deterministic scope guard — 2026-10-30

A second, user-registered Qwen3 4B Q4_K_M model (`Qwen/Qwen3-4B-GGUF`, model revision `bc640142c66e1fdd12af0bd68f40445458f3869b`, 2,497,280,256 bytes, SHA-256 `7485fe6f11af29433bc51cab58009521f205840f5b4ae3a32fa7f92e8534fdf5`, Apache-2.0) was evaluated through SideEffect's release-mode Windows CLI on the same 26-case development corpus using CUDA and the pinned llama.cpp source revision. The runtime reported GPU layer offload to an NVIDIA RTX 3060. Across this development run, 26/26 response contracts were valid, there were no runtime errors, expected status/reason matched 26/26 after correcting the deterministic absence classification, required evidence-label recall was 100%, and the four-case source-order permutation group was consistent. P95 latency was 16,966 ms. The fast deterministic abstentions took about 1.8 seconds; the model-backed cases were materially slower. These measurements are specific to this machine and synthetic corpus.

An independent read-only review of every historical generated statement found semantic defects: an ENOENT statement broadened the exact observed result into “not found or accessed”; an injection-bearing question received only the path and omitted its requested EACCES result; a partial-parse answer omitted the successful return that qualified the observed start; and one permutation answer repeated the same network event. One other permutation answer used a less precise “network operation” label. The review found the instruction-like text was not followed and other reviewed facts/citations matched the synthetic records. These were defects in the former prose response contract. The current schema v2 does not expose model-authored prose; it returns exact selected preview rows. That change does not establish that a selected row answers a question. This historical review was not a human-reviewed holdout and does not verify broad real-world accuracy. The candidate remains not release-approved because selection quality has not passed a separately frozen, independently reviewed holdout. The deterministic guard handles selected English phrases only and is not general natural-language validation.

Before release consideration, create an independently reviewed, frozen corpus with preregistered scoring, meaningful unanswerable cases, order controls, injection cases, independent reviewers for semantic support and unsafe claims, repeatable latency/resource measurement, and explicit platform/runtime coverage. Keep candidate prompt development separate from the frozen holdout. Require zero invalid citations, zero unsupported safety/root-cause/effective-access/completeness conclusions, strong answerable evidence-label recall, correct abstention on unanswerable cases, and improvement over a deterministic baseline. Passing synthetic criteria would still not prove real-world accuracy. Until that gate and platform security review pass, the feature remains experimental and local-model quality work remains open and release-blocking; M8's administrative implementation closure does not certify model readiness.

### Native Windows GPU runtime smoke — 2026-10-31

On a Windows host with an NVIDIA RTX 3060, the pinned llama.cpp source revision was built with CUDA using MSVC 19.44 and CUDA Toolkit 13.0. The executable reported the full pinned revision after configuring `LLAMA_BUILD_COMMIT`, enumerated `CUDA0`, and a separate bounded `model doctor` report marked the explanation task ready for an explicit inference run. Device enumeration alone was not treated as inference evidence.

One actual SideEffect `model-explain` run used the synthetic `exec-success.trace` fixture and a user-provided local Qwen3.5 4B GGUF main-weight blob (2,648,593,216 bytes, SHA-256 `a9d0a3e1d8c91732a3812becd31f8d4a8ff57414903f226306069f0437e2ac50`). The supplied Apache-2.0 label was unverified metadata. The preview bound the exact question and one `execve` result row; inference completed with `backend_used=cuda` but returned `selection_status=abstained`, no evidence IDs, and exit status 2. This confirms the native Windows GPU inference path for this one local model and input; it is a quality failure on the straightforward case, not a model endorsement or general evaluation. Peak process-isolated VRAM was not measured. The model registration was kept in a temporary isolated SideEffect registry, and the Ollama model files were not copied or changed.
