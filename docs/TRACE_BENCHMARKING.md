# Linux trace benchmark harness

`scripts/trace_benchmark.py` is an initial, reproducible local harness for comparing one small workload run without tracing and one run under the real external `strace`, then timing SideEffect's parser through `inspect`. It is intended to provide repeatable measurements while developing the Linux capture path. A single invocation is not a performance claim or a complete R1 benchmark suite.

## Run

Requirements are Linux, Python 3, `strace`, `rustc`, and a previously built SideEffect executable. The harness does not install dependencies or build the executable.

```sh
cargo build --release --bin sideeffect
python3 scripts/trace_benchmark.py \
  --sideeffect target/release/sideeffect \
  --output "$PWD/trace-benchmark.json"
```

The output must be a new path. It is created exclusively with mode `0600`; an existing file is never replaced. The report includes hostname and OS/kernel details, so treat it as private. The script prints the same report to the terminal. The raw trace and inspect output are held in a private temporary directory and removed on exit, including on errors.

## Workload and measurements

The harness creates a fixed Python workload in its temporary directory. The workload creates 24 deterministic 4096-byte files, reads and hashes each file for 48 rounds, and writes one digest file per input. It uses no network or caller-supplied data. It runs once untraced and once under `strace -f -qq -e trace=%file,%process`; it then invokes the supplied SideEffect executable's `inspect` command on that real trace.

The report records wall time for each workload run, child-process user and system CPU time as reported by `getrusage`, the strace output byte and line counts, SideEffect inspect wall and child CPU time, inspect output byte count, parsed record count and parse status, plus host, strace, Rust, Python, and SideEffect versions. The trace filter intentionally limits observations to file and process syscall classes. The trace line count is not necessarily equal to parsed-record count.

Temporary files are bounded: the traced process group inherits an `RLIMIT_FSIZE` of 16 MiB, the trace is checked against the same limit before parsing, and inspect JSON is limited to 64 MiB. Each measured subprocess has a 60-second process-group timeout. Workload data, raw trace, and parsed JSON are removed after the report is written. No capture or report is uploaded.

## Methodology and limitations

- This is one observation per condition, without warm-up, repetition, randomization, confidence intervals, or statistical aggregation. Repeat invocations manually and compare reports on a stable, otherwise idle host before drawing performance conclusions.
- Child CPU includes CPU reported for waited child processes and does not separate workload CPU from tracer CPU in the traced run. It is not a per-process profiler.
- The untraced and traced runs use separate fresh directories but the same fixed workload. Filesystem cache state, scheduling, thermal state, interpreter startup, and host contention can affect results.
- The script measures `inspect` as a subprocess, including CLI startup, bounded trace reading, parsing, and JSON serialization. It does not isolate parser-only time.
- Only `%file,%process` events are captured; syscall coverage, kernel/strace compatibility, and trace completeness are not established. A completed process and parse do not prove complete observation.
- This harness does not benchmark inventory, diff, HTML rendering, large/hostile inputs, or a matrix of workloads and trace profiles. It does not satisfy all Linux capture performance or compatibility exit criteria.
- The generated capture is a real local `strace` run, not a synthetic fixture. The deterministic workload is newly generated by the harness; it is not representative of arbitrary applications.
