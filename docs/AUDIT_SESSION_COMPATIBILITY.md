# Audit session compatibility

The `sideeffect.audit_session` v4 manifest is a platform-neutral envelope. Readers also accept v1, v2, and v3 manifests; v1 has no `coverage_manifest`, so its coverage status is rendered as `unknown`. Native inventory and runtime artifacts keep their own schemas. Process artifact readers accept both their historical v1 and current v2 contracts so earlier sessions remain reviewable; new collectors write v2. Other artifact contracts remain exact. The reader does not migrate artifact versions or treat an unknown source as complete. Unknown platform strings and artifact contracts are rejected.

V2 includes a bounded `coverage_manifest` with version 1 and one status per selected source role. Status is one of `observed`, `configured`, `not_observed`, `not_checked`, `unsupported`, `inaccessible`, `partial`, or `unknown`. The current producers report `configured` for a complete startup source, `observed` for a complete selected inventory snapshot, preserve partial/not-checked/unsupported/access-denied as `partial`/`not_checked`/`unsupported`/`inaccessible`, and use `unknown` for other incomplete states. Here `observed` means the selected inventory was read; it does not claim runtime activity. Runtime capture remains partial today. These values describe the selected collector result only; they do not assert exhaustive OS coverage.

V3 retains that coverage map and adds bounded per-source requested settings, source-reported effective settings, and runtime loss metadata. A requested setting is kept separate from applied collector limits and source-reported effective settings. An empty setting list means no values were recorded; it does not mean the OS default or effective state is known. Runtime loss is `reported` when any loss counter is positive, `none_reported` only when both statistics and the final snapshot are available and counters are zero, and otherwise `unknown`. Linux `strace` sessions currently report runtime loss as unknown. Windows ETW settings/counters are copied from the validated capture artifact; the reported session buffer count is not a guarantee of complete capture. Inventory sources omit runtime loss metadata. Every source's artifact references continue to provide provenance links by fixed path, native schema/version, byte length, and SHA-256; those hashes establish local byte consistency only, not authorship.

V4 adds bounded `host_context`: OS name, OS version, and the caller process privilege context. Linux reads the OS name/release through `uname` and checks the effective UID; Windows reads the native version through `RtlGetVersion` and the current token's elevation state through `GetTokenInformation(TokenElevation)`. Failed reads are explicit `unknown`; `not_checked` is valid for future producers that skip a fact. Linux `elevated` means effective UID 0, while Windows `elevated` reflects the current token flag. Neither status describes all capabilities or access to every resource. Architecture is a separate field and is never used to infer privilege. Values are bounded to 128 UTF-8 bytes; unknown and not-checked facts carry no value. V1-v3 remain readable with host context absent rather than synthesized.

Windows runtime capture is selected explicitly with `--runtime-source windows-etw --runtime-duration-seconds 1..60 -- PROGRAM [ARGS...]`. ETW setup must succeed before the target launches. The target's arguments remain separate argv values. The NT Kernel Logger is shared and system-wide for the bounded capture window; controlling it requires permission, and SideEffect never elevates. The captured v3 JSON document is included as the fixed runtime artifact in the one atomically published session directory. It retains bounded raw ETW payloads, capture interval, target outcome, loss metadata, and diagnostics. The session source is always `partial` because capture completeness is unknown. Setup, launch, or capture errors fail the audit before session publication; they are not represented as an empty successful artifact. No target/descendant event attribution or causal inference is made.

`complete` means the selected collector produced its declared artifact set. It does not mean exhaustive system coverage. `partial`, `unsupported`, `unavailable`, `access_denied`, and other non-complete states remain visible and force the enclosing session to `partial`. Runtime can never be marked complete in this session version because capture completeness is not established.

Each artifact reference has a fixed basename, exact native schema/version, positive bounded byte length, and lowercase SHA-256 digest. Readers reject unknown fields in the manifest, duplicate roles/artifacts, extra directory entries, unexpected artifact versions, oversized data, and mismatching hashes. The manifest digest is an integrity consistency check only; it does not authenticate who produced the manifest or artifacts. Readers render source metadata and do not claim full semantic validation of native inventory documents.

The envelope version changes when fields or status/completeness semantics change. V2 added the versioned coverage manifest; v3 adds bounded source details; v4 adds host context facts. Current readers accept v1-v4, leaving v1 coverage unknown, v1/v2 source details absent, and v1-v3 host context absent. Older binaries safely reject newer envelopes. A native artifact format change requires its own artifact schema-version change and explicit reader support.
