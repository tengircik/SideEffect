# Audit session compatibility

The `sideeffect.audit_session` v6 manifest is a platform-neutral envelope. Readers accept v1-v6 manifests; v1 has no `coverage_manifest`, so its coverage status is rendered as `unknown`. Native inventory and runtime artifacts keep their own schemas. Process artifact readers accept historical v1-v2 and current v3 contracts so earlier sessions remain reviewable; new collectors write v3. Other artifact contracts remain exact. The reader does not migrate artifact versions or treat an unknown source as complete. Unknown platform strings and artifact contracts are rejected.

V2 introduced a bounded `coverage_manifest` with version 1 and one status per selected source role. Current producers emit coverage manifest version 2; readers continue to accept version 1. `CoverageStatus` is a coarser summary of the detailed per-source `SourceStatus`: `complete` maps to `configured` for startup and `observed` for other roles; `partial`, `not_checked`, and `unsupported` map directly; `access_denied` maps to `inaccessible`; and `unknown`, `not_applicable`, `unavailable`, `failed`, `timed_out`, and `output_limit_exceeded` map to `unknown`. The original source status remains available in each source entry. `not_observed` is reserved and is not emitted by current producers because an empty inventory or zero runtime events cannot establish absence. Here `observed` means a selected inventory completed its declared read; it does not claim runtime activity. Runtime capture remains partial today. These values describe the selected collector result only; they do not assert exhaustive OS coverage.

Coverage manifest v2 may include `runtime_detail` for the runtime source. Its `unsupported_categories` list contains bounded stable codes and counts derived only from diagnostics in the retained selected runtime artifact: Linux reports malformed trace rows, unsupported trace rows, and ambiguous trace continuations; Windows reports malformed ETW payloads, unsupported ETW event layouts, and unsupported ETW providers. The list is capped at eight distinct categories and each count is capped at 100,000. An empty list means none of those conditions were found in the retained artifact; it does not establish broader capture coverage. Missing detail means the category summary is unknown. V1 manifests have no runtime detail and remain readable.

V3 retains that coverage map and adds bounded per-source requested settings, source-reported effective settings, and runtime loss metadata. A requested setting is kept separate from applied collector limits and source-reported effective settings. An empty setting list means no values were recorded; it does not mean the OS default or effective state is known. Runtime loss is `reported` when any loss counter is positive, `none_reported` only when both statistics and the final snapshot are available and counters are zero, and otherwise `unknown`. Linux `strace` sessions currently report runtime loss as unknown. Windows ETW settings/counters are copied from the validated capture artifact; the reported session buffer count is not a guarantee of complete capture. Inventory sources omit runtime loss metadata. Every source's artifact references continue to provide provenance links by fixed path, native schema/version, byte length, and SHA-256; those hashes establish local byte consistency only, not authorship.

V4 adds bounded `host_context`: OS name, OS version, and the caller process privilege context. Linux reads the OS name/release through `uname` and checks the effective UID; Windows reads the native version through `RtlGetVersion` and the current token's elevation state through `GetTokenInformation(TokenElevation)`. Failed reads are explicit `unknown`; `not_checked` is valid for future producers that skip a fact. Linux `elevated` means effective UID 0, while Windows `elevated` reflects the current token flag. Neither status describes all capabilities or access to every resource. Architecture is a separate field and is never used to infer privilege. Values are bounded to 128 UTF-8 bytes; unknown and not-checked facts carry no value. V1-v3 remain readable with host context absent rather than synthesized.

## Read-only session comparability

`compare_sessions` accepts two validated `AuditSessionManifest` values and returns `comparable` with a bounded list of stable reason codes. It compares host platform and architecture; known OS name/version; the selected source-role set, each source's platform, scope, status, and collector identity/version; applied limits; requested and effective settings; coverage metadata; and each source's artifact kinds and native schema/version contracts. Artifact bytes, digests, timestamps, session IDs, diagnostic text/codes, and caller privilege are not comparability keys: they may differ between valid observations without changing the declared collection shape.

Missing metadata is not treated as equal. V1-v3 have no host context, and v1-v2 do not define requested/effective source settings, so any pair containing those omissions is incomparable with an `*_unknown` reason. V1 also lacks coverage metadata and is incomparable on that basis. Explicit unknown/not-checked host OS facts, unknown source states, and absent/unknown runtime loss also make a pair incomparable. When a runtime source is selected, missing v1/v2 category detail is incomparable (`coverage_unknown`), even when both manifests omit it; different category lists or runtime coverage versions are incomparable (`coverage_mismatch`). Coverage v1/v2 version differences alone do not block comparability for sessions with no runtime source. Matching `partial` source statuses remain comparable with `partial_source`; the result still says nothing about capture completeness. A runtime source is comparable only when both manifests report `none_reported` with matching loss metadata. `reported` or `unknown` loss makes it incomparable. A comparable pair is only a metadata-level basis for comparison; it does not establish equal event sets or support claims that an event did not occur.

Reason codes are machine-stable snake_case values, deduplicated and capped at 32 per result. Current codes cover platform/architecture/host OS, source role/platform/scope/status, collector identity, partial or unknown status, applied limits and settings, artifacts, coverage, and runtime loss. Consumers should preserve unknown future codes when persisting results.

The CLI command `sideeffect compare-sessions BEFORE_SESSION_DIR AFTER_SESSION_DIR` first reads both sessions through the platform's verified session reader, then emits `sideeffect.audit_session_diff` schema version 1. It preserves `status`, `comparable`, and `reason_codes` as the existing metadata readiness result; `metadata_scope` is `metadata_readiness_only`, while overall `scope` is `metadata_and_item_level_inventory`. The report adds session intervals plus one `source_diffs` entry for each selected role. Linux package, process, startup, and selected-path permission artifacts are compared with their existing strict native comparators. Windows software-registration, process, startup, and selected-path permission artifacts use the corresponding native comparators. Nested comparator results retain item deltas and native evidence locators; each side's artifact path, schema/version, and SHA-256 link those locators to the bytes already verified by the session reader. The digest is a byte-consistency reference, not producer authentication.

The item comparison status is reported separately from manifest comparability. Missing source/artifact pairs, incompatible platform/scope/schema contracts, invalid native documents, unsupported roles, and pairs above the 64 MiB combined native-comparator input budget are reported with stable per-role reasons and no invented deltas. Runtime and PATH-executable artifacts are currently `not_compared`. Existing per-artifact comparators retain their partial-source, generation-identity, duplicate-identity, and unmatched-row suppression rules. Exit status 0 means the existing metadata `comparable` result is true (including matching partial sources reported with `partial_source`); exit status 2 means it is false. Invalid, malformed, oversized, or insecure session containers are rejected by the existing session readers. This report does not establish equal observations, exhaustive coverage, event absence, equal caller privilege context, causation, or producer authenticity. Caller privilege is deliberately not a comparability key.

V6 collector IDs are fixed by the implementation: Linux `debian_packages`, `procfs_processes`, `selected_path_permissions`, `curated_startup_sources`, `path_executable_candidates`, and `strace_runtime`; Windows `software_registry`, `toolhelp_processes`, `selected_path_permissions`, `curated_startup_sources`, `path_executable_candidates`, and `etw_runtime`. Each is prefixed by its platform (`linux.` or `windows.`). The recorded version is SideEffect's package version. Windows `etw_runtime` alone carries provider ID `nt_kernel_logger`, the fixed ETW session/provider label used by this collector. The Linux runtime collector ID identifies SideEffect's capture path; exact external tracer metadata remains in its `run.json` artifact when available.

Windows runtime capture is selected explicitly with `--runtime-source windows-etw --runtime-duration-seconds 1..60 -- PROGRAM [ARGS...]`. ETW setup must succeed before the target launches. The target's arguments remain separate argv values. The NT Kernel Logger is shared and system-wide for the bounded capture window; controlling it requires permission, and SideEffect never elevates. The captured v3 JSON document is included as the fixed runtime artifact in the one atomically published session directory. It retains bounded raw ETW payloads, capture interval, target outcome, loss metadata, and diagnostics. The session source is always `partial` because capture completeness is unknown. Setup, launch, or capture errors fail the audit before session publication; they are not represented as an empty successful artifact. No target/descendant event attribution or causal inference is made.

`complete` means the selected collector produced its declared artifact set. It does not mean exhaustive system coverage. `partial`, `unsupported`, `unavailable`, `access_denied`, and other non-complete states remain visible and force the enclosing session to `partial`. Runtime can never be marked complete in this session version because capture completeness is not established.

Each artifact reference has a fixed basename, exact native schema/version, positive bounded byte length, and lowercase SHA-256 digest. Readers reject unknown fields in the manifest, duplicate roles/artifacts, extra directory entries, unexpected artifact versions, oversized data, and mismatching hashes. The manifest digest is an integrity consistency check only; it does not authenticate who produced the manifest or artifacts. Readers render source metadata and do not claim full semantic validation of native inventory documents.

`provenance sign-session` and `provenance verify-session` add an optional detached `sideeffect.provenance_signature` v1 envelope. The signature covers a domain-separated transcript containing the Ed25519 key ID, SHA-256 of the exact validated `session.json` bytes, and the signer-supplied local-clock time. The sidecar is kept outside the session directory, so the v1-v6 fixed-entry contract is unchanged. Verification first uses the normal session reader to validate the manifest and every listed artifact, then checks the detached signature against an explicitly supplied raw Ed25519 public key encoded as lowercase hexadecimal. Private keys are PKCS#8 files created explicitly by `provenance keygen`; the files are published with owner-only access controls and without replacing existing files. The private file is unencrypted and must be protected and backed up by the user. The current implementation evaluates cryptographic validity only: it has no trust store, revocation, key labels, key import/export workflow, or trusted timestamp. A valid signature does not establish signer identity, collector honesty, host integrity, event truth, or capture completeness. Exact-byte signing means even a whitespace-only edit to `session.json` invalidates the signature.

V5 adds a bounded collector identity to each source: a stable platform+role ID, the SideEffect package version implementing it, and (only for Windows runtime) the nt_kernel_logger provider ID. Linux runtime identifies SideEffect strace collector; external strace version is not guessed in the envelope and remains linked through run.json metadata when available. V1-v4 remain readable with collector identity absent; v5 and v6 carry identity. compare_sessions treats absent legacy identity as collector_identity_unknown, and differing identities or versions as incomparable. V2 added coverage; v3 source details; v4 host context; v5 collector identity; v6 adds path-executable inventory. Current readers accept v1-v6. The nested coverage manifest reader accepts versions 1 and 2 independently of the audit-session version. Older binaries safely reject newer envelopes. A native artifact format change requires its own artifact schema-version change and explicit reader support.
