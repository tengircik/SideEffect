# Schema compatibility

Startup inventory v3/v5 rows carry `startup_state` schema v1. `configured: "present"` records that the corresponding source row exists. `effective.status` may be `effective`, `not_effective`, or `unknown`; known values require a named context and artifact evidence reference. `observed.status` may be `observed` or `unknown`; an observed value requires a bounded capture interval and direct runtime record reference. Current Linux and Windows collectors emit unknown for both effective and observed because their selected startup sources do not prove applicability under a named live context or link a runtime event directly to a startup row. Existing enabled flags, start types, enablement symlinks, and literal path matches remain source facts/candidates.

This document describes the versioned formats currently emitted by SideEffect and the formats that current commands accept as input. A schema version identifies a serialized contract; it does not promise that every consumer understands every field, nor that a document is authentic or complete.

### Runtime event-query schemas

`sideeffect.event_query` v1 and v2 remain accepted. V2 adds optional `filters.path_exact`; v3 adds optional `filters.path_prefix`. Both are bounded to 8 KiB and require nonempty printable UTF-8 values. `path_exact` performs exact string equality. `path_prefix` performs a case-sensitive literal string-prefix comparison, so `/tmp/a` also matches `/tmp/abc`; it does not mean directory containment. Neither filter folds case, rewrites separators, resolves paths, or performs globbing. Linux matches only parser-derived lexical path hints already present on supported `openat`/`openat2` rows. Windows matches only when a supported FileIo name event's retained raw payload re-decodes to the exact serialized sidecar. Pathless/unsupported events cannot match; absence of a match is not evidence that a path was not accessed.

`sideeffect.common_event_envelope` v5 adds optional `path_observation` values with a source basis. `sideeffect.event_timeline` remains v5; `sideeffect.event_graph` v6 can additionally record a separately fingerprinted Windows startup input and SCM service-to-process-start candidate edges with references into both artifacts. `sideeffect.event_query_result`, `sideeffect.session_event_query_result`, and `sideeffect.multi_session_event_query_result` are v3 outputs that can include these event values and report the current query contract. These outputs are not import formats. Query v1 and v2 files remain accepted for their original filter sets; `path_exact` requires v2 and `path_prefix` requires v3. No query-result or common-envelope JSON import is provided.

The table lists current product command formats, not every development or local-model evaluation artifact in the repository. Text renderings of inspect, diff, evidence, and session review are human-readable output and do not declare a JSON schema version.

The Windows ETW contract has deterministic synthetic conformance checks: `inspect --windows-runtime` preserves the complete validated v3 capture in its v1 inspection envelope; `diff --windows-runtime` verifies the v3 algorithm, canonical representation-fingerprint equality, preserved category counts, event-level exact multiset/candidate/one-sided behavior, the ordinal/QPC normalization ledger and retained QPC values, loss state, and both capture fingerprints with source ordinals; `attribute --windows-runtime` v2 exercises raw Kernel-Process PID/parent-ID cross-checks, TCP/UDP raw payload PID sidecar matches and failures, display-only image metadata, file/disk header context, ambiguity, PID reuse, bounded diagnostics, and partial status. A correctly re-fingerprinted capture with an unsupported schema version is rejected. The opt-in `tests/windows_runtime_etw_integration.rs` hosted live test also runs `attribute --windows-runtime` v2 on the real capture and checks the target PID/start result for supported Kernel-Process versions 0–3; an unsupported target-start version must remain not observed and partial. `tests/windows_associated_behavior_roundtrip.rs` also runs the native Windows startup v10 producer and passes its output to the Windows associated-behavior v2 adapter. `tests/schema_mutation_properties.rs` applies deterministic bounded mutations to synthetic runtime v3 and startup v5/v6/v7/v8/v9/v10 inputs and checks parser/adapter invariants and rejection behavior. These checks validate serialization and bounded reader/adapter behavior; the named live scenario does not establish compatibility with every live ETW provider, Windows version, or capture-completeness claim. See [the release compatibility notes](RELEASE_NOTES.md) for the tested and untested matrix.

### Deterministic mutation exploration

`tests/schema_mutation_properties.rs` applies a fixed, bounded set of truncations and single-byte substitutions to clearly labeled synthetic Windows runtime capture v3 and startup inventory v5 seeds, while separate legacy-v4 acceptance tests preserve reader compatibility. It also checks selected unknown-field, duplicate-key, malformed-row, and over-limit documents. The checks assert that these inputs do not panic; accepted runtime captures retain valid schema, ordinal, and representation-fingerprint invariants; and accepted startup-adapter results retain exact input fingerprints, bounded output, and evidence references to the supplied fixture records. This is deterministic regression exploration, not coverage-guided fuzzing, exhaustive parser coverage, live ETW validation, or a compatibility claim for Windows versions or providers.

## Accepted inputs and unsupported versions

- `inspect` and `evidence` accept bounded raw `strace` text, not prior SideEffect trace JSON. Ordinary `diff` accepts two completely parsed raw `strace` inputs. The separate `diff --windows-runtime` path accepts only two Windows runtime capture v3 documents and emits output-only diff summary v3 with validated representation-fingerprint equality; historical summary v1-v2 are not accepted as inputs. It does not accept trace/diff schemas. `attribute --windows-runtime` accepts one Windows runtime capture v3 document and emits output-only attribution v2; attribution v1 is historical and is not imported. Bundle variants of inspect and diff accept Linux `sideeffect.run` v1 or v2, verify the fixed private bundle layout and trace hash, and then parse the trace text. A v2 bundle may include stop reason and time-limit metadata; v1 does not. Other manifest versions, unknown fields, invalid version-specific capture metadata, wrong fixed entries, and integrity mismatches fail visibly. Bundle output currently uses v2.
- Current trace and diff JSON schemas (v7 and v4) are produced, not JSON import formats. Trace JSON versions v1-v5 and diff JSON versions v1-v3 were standalone exports and are not imported or migrated. Trace schema v6 was not published. This document makes no compatibility or round-trip claim for those historical exports.
- Package inventory comparison requires the Linux package schema `sideeffect.inventory` v2. Unsupported schema versions or malformed documents are rejected; it does not convert older versions. Linux startup correlation and the Linux associated-behavior adapter accept saved Linux aggregate startup v2/v3 and raw trace text. The separate Windows adapter accepts startup inventory v4-v10 and a validated ETW capture v3. Both output schemas are output-only and preserve candidate-only semantics.
- Session readers accept envelope versions v1-v15 and the exact artifact combinations in the table above. Unknown platform/source/artifact combinations, unexpected versions, unknown manifest fields, duplicate or extra artifacts, oversized files, and digest mismatches are rejected. V3 adds bounded requested/effective setting lists and explicit runtime loss metadata; v4 adds bounded host OS/version and privilege facts; v5 adds required per-source collector identity/version and an optional Windows ETW provider ID. V1-v4 remain accepted without collector identity; v6 adds the `path_executables` role and fixed artifact for both platforms, while v1-v5 reject that role. V7 adds the opt-in `selected_root` role and fixed v1 `root-snapshot.json` artifact for Linux and Windows, while v1-v6 reject that role; v8 adds opt-in regular-file hashing and supports root artifact v1 or v2. V9 adds the optional Windows-only `msix` role and fixed `msix.windows.json` artifact; v1-v8 reject that role, and Linux rejects it in all versions. V10 permits Windows startup v6 while v1-v9 remain pinned to v5 (v4 readable). V11 adds optional Windows-only `app_paths`; v1-v10 reject that role and Linux rejects it in every version, while startup remains v6. V12 permits Windows startup v7 and retains App Paths; v7 is rejected in v10-v11, and v6 is rejected in v12. V13 permits startup v8 and retains App Paths; v14 preserves startup v9; v15 permits startup v10; v8 is rejected before v13, v9 before v14, and v10 before v15. Linux continues to emit v9. Session comparison can compare startup v7 against v7, v8 against v8, v9 against v9, and v10 against v10; startup v6/v7, v7/v8, v8/v9, or v9/v10 artifact-contract mismatches remain metadata-incomparable while the native startup diff reports a partial result and suppresses unavailable-state claims. The nested coverage manifest independently accepts v1 and v2: v2 adds bounded Linux trace and Windows ETW unsupported-category counts derived from retained artifact diagnostics. Missing detail is unknown for selected runtime sources, and differing detail is a `coverage_mismatch`; without a runtime source, the coverage format change alone does not block comparability. A session's `complete` status means the selected collectors produced their declared artifacts, not exhaustive coverage.
- The Windows ETW v3 capture remains experimental; `inspect --windows-runtime` validates and renders it offline. The explanation JSON, aggregate summary, audit-session review, and HTML report are likewise output-only.
- `sideeffect.common_event_envelope` v5 is JSON-only output from the `events` CLI adapters, not a persisted session artifact or import format. Linux conversion verifies the exact raw trace fingerprint and each line/byte evidence tuple; native Windows conversion first validates the bounded ETW v3 capture, then preserves capture-local QPC and ETW record references. Linux retains caller-task-to-returned-child-PID semantics separately from trace-task observations. For a completely parsed trace, exact prefixed `+++ exited with N +++` and `+++ killed by SIG... +++` control rows close an active source-local task context; a later row with the same prefix starts another observed task epoch. The first and terminal raw rows remain the observation's exact evidence. This epoch is only a segment in the supplied trace: it does not establish task start time, OS process/PID generation, TGID, parentage, or cross-capture identity. Partial parses keep the prior task-ID-only mapping and emit no epoch numbering. A terminal row with no active observed context is diagnosed and makes the adapter partial. Windows process IDs are checked against retained raw bytes for reviewed Kernel-Process v0-v3 layouts and matched against the serialized TDH sidecar before process identity, start/end links, or parent relationships can be observed. Invalid descriptors or pointer flags, malformed/truncated payloads, zero PIDs, and sidecar mismatches remain unresolved and make output partial; lifecycle continuity is invalidated conservatively. Raw image names are not decoded and stay decoder metadata only. Parent PID matching is capture-local reported ancestry, not causal parentage; ETW loss and PID reuse remain ambiguity sources. For supported classic TCP/UDP records, the adapter re-decodes raw payload bytes and checks the serialized observation sidecar; only the raw payload PID can support an event link. A sidecar mismatch makes output partial, while unsupported or malformed network payloads remain raw with unresolved links and diagnostics. Network payload PIDs without a unique active process instance remain unresolved event links. Neither fingerprint authenticates the producer. Invalid source fingerprints and process references are reported; both adapters retain uncertainty and diagnostics. No event-envelope reader or migration is provided. Graph and timeline outputs are source-local views, not an integrated cross-source graph or timeline.
- Local-model previews and analyses are versioned outputs, not persisted capture evidence or general import formats. The local model registry is persisted per user and accepts only its current exact schema version; no registry migration is promised. Model runtime compatibility and schema validation do not establish answer quality.
- Unsupported or malformed raw trace rows are represented by parser diagnostics/partial status where possible; this is separate from accepting an unsupported SideEffect JSON schema. Diff refuses partial parsed traces rather than treating unparsed rows as absent events.

No automatic schema migration is provided. The explicit `case migrate` operation is the one documented exception: it converts a v1 case to v2 only after the user selects an initial status, preserves case/evidence fields, and links the new file to the exact v1 bytes. Other readers that support only an exact version must reject unsupported versions visibly rather than infer fields or silently reinterpret values. An output that has no schema-name field (the deterministic explanation shapes) is still versioned by its `schema_version` field, but is not a general import contract.

## Integrity and semantic limits

SHA-256 fields bind a reference to particular bytes for equality and consistency checks. A successful hash check does not authenticate a producer, prove when or how the bytes were collected, prove capture completeness, establish that an operation succeeded beyond the recorded syscall result, or make the data safe to share. Hashes may reveal equality and can be guessable for low-entropy inputs.

For trace inspection, `source_sha256` is computed over the exact bounded byte buffer parsed, and evidence references identify line number, byte offset, and byte length within those bytes. The evidence command verifies that tuple against the supplied raw trace. Diff references carry separate left/right fingerprints and source tuples. Bundle and session hashes check artifact consistency against local bytes; session inspection's schema-header check is not full semantic validation. Windows ETW's `document_sha256` identifies its serialized representation and is not authentication. Inventory evidence hashes, where present, have the same integrity-only limitation.

## Versioning and compatibility policy

- Keep source evidence, uncertainty, diagnostics, and partial/unsupported states explicit. A derived field or summary must not replace its underlying evidence or overstate what the source establishes.
- Increment the relevant schema version when a serialized contract's fields, meanings, requiredness, or interpretation change incompatibly. Do not reuse an unpublished version number as if a format had shipped; trace v6 is intentionally noted as unpublished.
- A new artifact contract can be added to the session platform matrix without changing the session envelope version only when envelope fields and status/completeness semantics remain unchanged. Changing those envelope semantics requires a new envelope version. A native artifact's format changes require that artifact's own version change and explicit reader support.
- Add reader support for each accepted version deliberately. Document whether it is parsed, validated, rejected, or migrated. If a migration is introduced, preserve raw source evidence and uncertainty, describe the conversion, and test that supported input versions round-trip without silent semantic loss. No migration is promised by the current formats.
- Document tested and untested operating systems, architectures, toolchains, tracer versions, and trace sources in the compatibility matrix and release notes. Current tested scope is summarized in [INSTALL.md](INSTALL.md#compatibility-and-observation-matrix); it is bounded evidence, not broad OS or trace-source compatibility.

For current run-bundle details, see [ARCHITECTURE.md](ARCHITECTURE.md#versioned-run-record). For the exact session reader contract, see [AUDIT_SESSION_COMPATIBILITY.md](AUDIT_SESSION_COMPATIBILITY.md).
