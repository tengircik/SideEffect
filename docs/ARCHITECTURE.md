# SideEffect Architecture Plan

**Status:** implementation in progress. Linux provides bounded local inventory, `inspect`, `diff`, evidence lookup, static HTML, and `record` using external `strace`. Native Windows provides bounded software/process/selected-path-permission/startup inventory and an experimental ETW capture and review workflow. Windows capture comparison preserves aggregate counts and adds validated capture representation-fingerprint equality, exact event-record multiset comparison, a field-level normalization ledger, conservative candidate-changed groups, source references, loss metadata, and offline HTML/text output. `attribute --windows-runtime` emits a separate evidence-linked candidate view; process-start payloads establish only observed candidate lineage, network payload IDs can be associated with observed active instances, and file/disk header PIDs remain context candidates. Hosted live ETW acceptance passed on Windows Server 2022/2025 for source commit [`797ba86`](https://github.com/tengircik/SideEffect/commit/797ba86dc41d024129da35b2fc4be7ad5eca6756) ([CI run](https://github.com/tengircik/SideEffect/actions/runs/40867530573)); Windows 11 live capture remains unverified. Opt-in Linux `record --bundle` writes a `sideeffect.run` v2 manifest and raw trace together; Linux `inspect --bundle DIR` validates supported v1 and v2 formats. Trace inspection JSON uses schema v7 and detailed diff JSON uses schema v3; earlier trace schema v1-v5 and diff schema v1-v2 JSON are not imported. Windows runtime diff JSON is schema v3 and reports canonical validated representation-fingerprint equality; schemas v1-v2 are output-only historical formats. A real Linux tracer integration covers a child execution, temporary-file activity, and loopback TCP; broad OS/runtime coverage remains unverified.

The security requirements and current safeguards are summarized in [SECURITY.md](../SECURITY.md); requirements marked future remain release gates.

## Shared audit-session manifest contract

`sideeffect.audit_session` v6 is a bounded envelope for grouping existing source artifacts without merging or rewriting their evidence. Its platform-neutral fields include a stable session ID, host platform/architecture, bounded OS name/version and caller privilege facts, a best-effort session interval, an explicit non-atomic collection marker, and per-source platform, scope, interval, operational status, versioned coverage status, applied-limit codes, requested settings, source-reported effective settings, runtime loss state, collector identity/version and optional Windows ETW provider ID, diagnostic codes, and artifact references. Artifact references carry the provenance link (fixed path, native schema/version, length, and digest); digests do not authenticate origin. Source schemas remain native and versioned. Readers accept v1-v6 with version-appropriate fields absent; v1 coverage remains unknown. Current producers emit nested coverage manifest v2, which adds bounded runtime unsupported-category counts derived from retained trace/ETW artifact diagnostics; coverage v1 remains readable. Missing runtime detail is unknown and cannot make selected runtime sessions comparable. V6 adds the shared `path_executables` source role and `path-executables.json` artifact on Linux and Windows; v1-v5 retain their prior role and artifact allowlists. Collector IDs identify the concrete platform+role implementation; the version records the SideEffect package version. Linux runtime does not guess an external strace version; run.json retains tracer metadata when available. The exact platform/role/artifact/schema allowlist is documented in [AUDIT_SESSION_COMPATIBILITY.md](AUDIT_SESSION_COMPATIBILITY.md); readers reject unknown platforms, names, and schema versions rather than migrating or guessing.

The read-only `compare_sessions` contract operates on two validated manifests and returns a comparable flag plus at most 32 stable reason codes. It requires matching platform, architecture, known OS name/version, source roles/platforms/scopes/statuses and collector identities/versions, applied limits, requested/effective settings, source coverage metadata, and artifact kind/schema/version contracts. Legacy versions that omit host context, source settings, or collector identity remain incomparable because omission is unknown, not evidence of equality. For selected runtime sources, absent legacy category detail is incomparable and differing unsupported-category counts are a coverage mismatch. With no runtime source, the coverage v1-to-v2 format change alone does not block comparison when source coverage statuses match. Matching partial sources can be comparable with a `partial_source` reason; unknown source states and runtime loss that is reported or unknown make the pair incomparable. The function compares declared collection metadata only: a comparable result does not establish complete capture, equal observations, or absence of events.

The parser accepts at most 512 KiB. Validation limits the source count to 8, diagnostic codes to 256 per source, applied limits to 64 per source, each artifact to 64 MiB, and all referenced artifacts together to 128 MiB. Artifact paths and schema/version pairs must match fixed names; digests must be lowercase SHA-256. A complete source means its selected collector produced the declared artifact set; it does not mean exhaustive system coverage. The current runtime bundle records capture completeness as unknown, so a runtime source cannot be marked complete in this session schema. A complete source must reference its full artifact set, while incomplete sources may retain a subset or none. A session cannot claim complete when any source is incomplete. Hashes detect byte changes but do not authenticate artifacts.

On Linux, `audit --output DIR` can collect explicitly selected package, process, startup, current-PATH executable-candidate, explicit-path permission, and bounded runtime sources. The PATH source stores the existing point-in-time heuristic artifact with its status, limits, provenance, and collector identity; it does not execute candidates or resolve commands through a shell. Runtime collection reuses the existing `strace` bundle capture path, keeps command arguments as separate OS strings, uses an explicit 1–3600 second deadline and the existing trace byte cap, and copies the `sideeffect.run` v2 manifest plus raw trace from private recorder staging into the session's own private staging directory. The run manifest deliberately keeps capture completeness unknown; the runtime source is always partial, and an unavailable/failed capture is represented by a source status and fixed diagnostic code without artifacts. Linux publication uses mode `0600` files in a mode `0700` directory, no-follow/exclusive creation, exact-layout checks, and atomic no-replace publication.

On Windows, `audit --output DIR` collects selected bounded native software registration, process, startup, current-PATH executable-candidate, and explicit-path permission artifacts. The PATH source preserves the existing heuristic inventory semantics and does not execute candidates or resolve commands through a shell. It preserves each native schema and records intervals/status/selected limits/diagnostics. The directory publisher applies a protected current-user-only DACL to the staged directory and files and atomically moves it without replacing an existing destination. An explicit `--runtime-source windows-etw --runtime-duration-seconds 1..60 -- PROGRAM [ARGS...]` selection collects the bounded system-wide NT Kernel Logger capture in memory and adds its fixed v3 JSON document as `runtime.windows.json` in that same atomic publication. ETW setup must succeed before target launch; capture completeness is unknown, so runtime and containing sessions remain partial. Windows `inspect --session DIR` rejects reparse points, requires a protected owner-only DACL, permits only one current-user allow ACE, restricts names and files to the manifest's fixed set, bounds reads, checks artifact schema headers and verifies length/hash before emitting metadata-only review. Both readers reject unknown platform/artifact/schema contracts. Neither reader semantically validates all inventory fields; SHA-256 checks consistency with the supplied manifest, not origin authenticity. The written M9 implementation exit criteria are met. Broader collector-level fault injection and release validation remain follow-up work.

## Common event envelope v2 (CLI and library adapters)

`sideeffect.common_event_envelope` v2 is emitted as JSON by the read-only `events --trace FILE` command and, on native Windows, `events --windows-runtime FILE`. The envelope itself is not a persisted session artifact or graph. V2 adds bounded source-local process observations, direct process relationships, and event-to-process links. Observation IDs are envelope-local indexes, never identities shared across captures. The source digest is serialized as `null` when invalid. Linux adapts a parsed `TraceDocument` only when the exact raw trace bytes match its length and SHA-256; each retained syscall reference is checked against the source byte slice, one-based line number, and bounds. Unsupported/control rows and invalid references remain diagnostics and make the envelope partial. A complete Linux envelope means the parser covered the supplied trace bytes; it does not establish that the trace captured all system activity. Syscall outcome stays distinct from attempt, unfinished calls have no invented result, and the `strace` timestamp text retains an unverified source-local clock label. `timeline --trace` and, on native Windows, `timeline --windows-runtime` emit the shared `sideeffect.event_timeline` v1 source-local listing, optionally filtered by exact event kind. Each item keeps its source ordinal, original timestamp representation, and exact raw-record reference. Timeline building does not parse or compare timestamps, merge sources, or establish causal ordering. The `graph` command provides the bounded single-source view described below; broader graph filters, broader timeline filters, and an interactive evidence viewer remain open R3 work.

The Windows CLI strictly validates the bounded ETW v3 JSON and representation fingerprint before passing the capture to the shared adapter. It keeps event ordinal and raw QPC ticks local to that capture, re-computes a digest for each bounded payload, and links it with its `/events/N` JSON pointer. Header PID is explicitly ambiguous event context, not an actor identity. It caps source events at 50,000, one payload at 64 KiB, aggregate decoded payload at 8 MiB, copied diagnostics at 256 entries/512 UTF-8 bytes each, source-local process observations and relationships at 50,000 each, event-to-process links at 50,000, and process diagnostics at 256 entries. The shared/Linux process-observation ceiling is 150,000. The envelope preserves the capture's completeness claim: unknown remains unknown even when loss counters report zero; known loss, limits, invalid references, and other collection failures are partial. These fingerprints and payload digests provide byte-consistency references, not authentication. Partial or unknown status exits with code 2; the output is JSON-only.

The read-only `graph --trace` and native Windows `graph --windows-runtime` commands emit `sideeffect.event_graph` v1 from one common-envelope adapter result. Event nodes and process-observation nodes retain their source references. Process-relationship and event-process-link edges preserve the adapter's type, status, basis, and evidence. When a PID has no unique process observation, the graph adds a separate context node for that edge instead of merging by numeric PID. Optional exact `--event-kind` filtering retains matching events, their direct process links, and one-hop process relationships incident to those linked processes; the JSON records the filter while source diagnostics and completeness still describe the full input. The graph carries source completeness and diagnostics; partial or unknown input exits 2. Construction is capped at 500,000 nodes and 200,000 edges and the shared 64 MiB report output limit; limit or reference-contract violations fail visibly rather than silently truncating. This source-local graph is not a complete process tree and does not prove ownership, causation, or system coverage. Hosted live tests exercise the graph over the named Linux trace and Windows ETW scenarios; broader timeline filters and interactive graph drilldown remain open R3 work.

Linux process observations distinguish a `strace -f` caller task ID from a returned child PID; the edge means only that a successful process-creation row reported that PID, not that the caller is the OS parent. Supporting rows for split calls must be the matching unfinished creation syscall with the same caller task ID. These observations do not infer later PID generations. Windows process identities and parent relationships are derived from serialized ETW decoder metadata. The offline adapter validates metadata shape and source references but does not re-decode retained process-lifecycle payload bytes; it labels derived identities and relationships `decoder_metadata_unverified` and related event links as context candidates. For supported classic TCP/UDP events, the adapter re-decodes the retained raw payload using its provider, descriptor, header pointer-width flags, and bytes, then compares the full result with the serialized observation sidecar. It uses only the PID decoded from raw bytes. A mismatch is diagnosed, makes the envelope partial, and leaves the link a context candidate; malformed or unsupported records remain raw events with unresolved PID links and diagnostics. An invalid or unsupported process-start row invalidates all currently active instances because it may conceal a PID transition. Parent-PID relationships resolve only when a unique active start instance is present and capture loss statistics are reliable; unresolved and ambiguous parent IDs remain explicitly labeled. Reported ETW event/buffer loss or unavailable loss statistics disables generation-confident parent and network links. Payload PID attribution remains a context candidate unless lifecycle continuity is unavailable, in which case it is unresolved. Supported serialized process-end metadata can identify a matching instance only as an unverified candidate when lifecycle continuity is reliable. File/disk header-PID links are labeled context candidates only. Invalid lifecycle evidence marks affected identities as continuity-unknown; `ambiguous_pid_reuse` is reserved for observed overlapping starts or repeated PID claims. Neither platform creates a cross-platform clock, total ordering, file ownership, or causation. Linux and Windows synthetic CLI tests and adapter unit tests validate bounded conversion contracts; they are not a live capture through the common envelope. Synthetic CLI tests cover timeline filtering, references, and incomplete states; hosted Ubuntu 24.04 real-`strace` and Windows Server 2022/2025 live ETW acceptance also exercise source-local timeline adaptation over the named file/loopback scenarios. These tests do not validate every event relationship or OS/provider combination. The integrated process graph, broader filters, and interactive evidence-drilldown workflow remain open R3 work.

## Goals
- Windows is a first-class product target, not a compatibility promise for the current Linux adapters. Windows implementations must use native evidence sources and expose their own scope, permissions, timestamps, and collection-loss states. Shared command concepts should remain familiar while platform-specific coverage stays explicit. Cross-platform 1.0 is gated on native Windows inventories and bounded process/file/network runtime capture; WSL2 does not meet that gate. See [the delivery plan](PLAN.md#milestone-10--native-windows-inventory-and-startup-audit).
- Build a local-first Rust CLI whose first implementation is Linux x86_64 with external `strace`, then provide useful native Windows workflows for the same core audit jobs.
- Preserve raw evidence while making paired-run differences readable and reviewable.
- Keep uncertain or incomplete observations explicit.
- Render portable JSON and offline HTML without executing trace-provided content.
- Keep dependencies and runtime infrastructure small; no hosted service or LLM is required.

## Package database inventory slice

`inventory packages --output FILE` queries available dpkg, RPM, pacman, and APK databases at fixed system paths on Linux, plus installed Flatpak references from `/usr/bin/flatpak list --columns=ref`. Every adapter uses fixed arguments and a cleared child environment; APK explicitly disables network access, and Flatpak only lists refs without launching installed apps. The Flatpak source does not currently identify the installation scope or provide package versions, so those fields remain unknown; duplicate refs remain ambiguous rows. A shared stdout, stderr, row, and 20-second aggregate deadline bounds the combined snapshot. Schema `sideeffect.inventory` v2 associates each row with its source ID and retains source-row evidence. Known inapplicable adapters can be marked `not_applicable`; unavailable, unsupported, failed, or skipped sources remain explicit and prevent an unjustified complete result, except optional Flatpak absence alone does not invalidate otherwise complete sources. Unknown distribution metadata remains conservative. Unsupported-manager detection checks documented fixed paths for XBPS, Nix, Guix, and Snap; custom/user installs outside those paths can be missed. This is not a complete inventory: manually copied or otherwise unregistered software and unsupported package formats are not represented.

`inventory processes --output FILE` separately walks visible numeric `/proc` directories and reads each `status` file, `stat` record, `exe` link, and seven namespace links. Its process inventory schema v3 stores selected Name, PID/TGID/PPID/State, UID/GID values, capability masks, `NoNewPrivs`, `Seccomp`, the `NSpid` vector where reported, namespace link identities, and the raw `/proc/<pid>/stat` start-time tick count (field 22) as bounded PID-generation evidence. Collection reads `stat` before and after status/executable/namespace collection and preserves unknown generation when the PID or start time changes, the record is malformed, inaccessible, or vanishes. This brackets the observation but is not an atomic snapshot. Selected status fields link to their raw source lines with relative byte offset/length and SHA-256; namespace fields refer to bounded exact symlink target bytes, parsed namespace inode, and source path. The executable-link observation stores exact target bytes as bounded hex, an optional UTF-8 display, and a SHA-256 fingerprint; SideEffect does not open the target. It excludes `cmdline` and other procfs files. Start/end timestamps describe the interval of a non-atomic walk; processes can change or vanish, and visibility restrictions and caps mean the result is not exhaustive. Missing, duplicate/ambiguous, malformed, inaccessible, vanished, and limit-affected values produce diagnostics and partial status. Limits are 8,192 numeric process entries, 64 KiB per status read, 4 KiB per stat record (read twice to bracket collection), 32 MiB aggregate status bytes, 4 KiB per executable link, 4 MiB aggregate executable-link bytes, 128 bytes per namespace symlink, 2 MiB aggregate namespace-link bytes, a 10-second scan deadline, and the 64 MiB serialized-output ceiling. Output reuses the private mode-0600 no-clobber writer. This remains a narrow process inventory, not a process security assessment.

`inventory path-executables --output FILE` writes shared schema `sideeffect.path_executable_inventory` v1. It snapshots current-process `PATH`, preserves ordered PATH components and repeated directories, records directory entries in observed enumeration order (not a stable cross-run sort), explicitly maps empty components to current working directory, and reads one level of each selected directory. Linux candidate detection checks regular-file metadata for any execute bit. Windows checks regular-file names against the captured current-process `PATHEXT` suffix list; if `PATHEXT` is unavailable, regular-file rows remain unknown. Neither heuristic runs or opens a candidate. Component and row ordinals act as evidence references; exact filesystem strings are encoded as raw bytes on Unix or UTF-16 code units on Windows, with a display string alongside. Symlink/reparse directories are unknown and skipped; child symlink/reparse entries are retained as unknown without following and make that directory partial. Collection bounds are 256 components, 4 KiB per Linux component / 32,767 UTF-16 units per Windows component, 20,000 directory entries, 16 MiB aggregate path/name bytes on Linux or UTF-16 code units on Windows, five seconds checked at boundaries, and 64 MiB serialized output. A changed filesystem can race between metadata checks and directory enumeration; the result is a bounded point-in-time heuristic rather than an atomic or shell-resolution result. Partial documents retain rows and exit 2. Output uses the platform's private no-clobber writer.

Every successfully enumerated child row remains in order with `candidate`, `not_candidate`, or `unknown` status plus metadata status. A symlink/reparse row is explicitly unknown and is skipped without following it; metadata failure is likewise retained as an unknown row. Directory read failures have directory-level status and diagnostics. The discovery heuristic does not inspect file contents.

The native Windows process adapter writes a separate `sideeffect.windows_process_inventory` v3 document. One Tool Help snapshot supplies process ID, parent process ID, thread count, and executable name; `QueryFullProcessImageNameW` supplies an image path and `GetProcessTimes` supplies the raw creation FILETIME when `PROCESS_QUERY_LIMITED_INFORMATION` succeeds. A bounded token query also records user SID text, integrity RID, and session ID when accessible; it does not resolve account names. Rows cite their source API and snapshot index. Creation time provides process-generation evidence for comparing reused PIDs, but the snapshot and later queries are non-atomic: processes can exit or PIDs can be reused between them. Token-query generation is compared against the process row's creation FILETIME and cleared when identity cannot be verified or changed. The adapter never reads command lines or process memory and does not elevate. It caps rows at 8,192, image paths at 32,768 UTF-16 code units each and 4 Mi code units combined, token SID text at 256 UTF-16 units per SID and 2 Mi units combined, scan duration at 10 seconds, and serialized output at 64 MiB. Inaccessible, vanished, malformed, or limit-affected entries make the result partial and preserve unknown status. Output is staged in a sibling directory with a protected current-user-only DACL and moved without replacing an existing destination. This is an initial process view, not exhaustive Windows process coverage.

The native Windows startup adapter emits a distinct `sideeffect.windows_startup_inventory` v4 document. Its scope is selected current-user Run/RunOnce keys, accessible machine-wide Run/RunOnce keys in the 32-bit and 64-bit registry views, current-user/common Startup folders, visible Win32/driver service start configuration, and boot/logon triggers on local Task Scheduler tasks visible to the current token. The task enumerator includes hidden tasks, traverses folders iteratively with depth/count bounds, and collects task path, task/trigger enabled flags, typed trigger, and logon user when available. For tasks with a boot/logon trigger, it records indexed action types and the inert executable path, arguments, and working directory of Exec actions. Other action types and unreadable/oversized fields are explicitly unsupported or partial with diagnostics; task XML is not read. No action is launched, expanded, or shell-parsed. COM connects locally with the current token and no alternate credentials; no automatic elevation is requested. Current-token visibility does not guarantee an all-users task inventory. Each source records its hive/key/view, Known Folder path, or API scope, status, and diagnostics. Registry strings retain display text plus exact UTF-16 code units as hex; `REG_EXPAND_SZ` values are not expanded and commands remain inert. Startup-folder rows record entry path/type without opening shortcuts. Service rows retain service/display names, base configured start type, account, and binary path; delayed-auto-start and service trigger configuration remain outside scope. Service bounds are 8,192 entries, 256 KiB enumeration buffer, 64 KiB/config and 4 MiB aggregate configuration bytes, 32,768 UTF-16 code units/string and 4 Mi aggregate service-string units. Task bounds are 1,024 folders/depth 16, 8,192 tasks, trigger rows, and action rows, 256 triggers/actions per task, 32,768 code units/string, 4 Mi aggregate task-string units, and 256 diagnostics. The shared 10-second deadline is checked between calls and cannot cancel an in-flight Windows API call. Registry values/folder entries remain capped at 4,096 each, data at 64 KiB/value and 4 MiB aggregate, value names at 16,384 code units each and 1 Mi aggregate, paths at 32,768 code units each and 4 Mi aggregate, and output at 64 MiB. Access, malformed-data, and limit issues remain visible through source states/diagnostics. The snapshot does not establish applicability or execution and is not exhaustive.

`inventory permissions --output FILE PATH...` collects a separate `sideeffect.permission_inventory` v1 document for explicitly selected Linux paths. It accepts at most 256 paths (4 KiB of path bytes each), and checks only regular files and directories. It first opens each path with `O_PATH|O_NOFOLLOW|O_CLOEXEC` and reads metadata from the pinned descriptor; final-component symlinks are reported but not followed. It reopens `/proc/self/fd/N` read-only to call `fgetxattr` on the pinned object, then checks device/inode/type identity against the original descriptor. Access ACLs are checked for both object types; default ACLs only for directories; `security.capability` is also read and strictly decoded for Linux VFS revisions 1–3. ACL and capability xattr data each have 64 KiB per-attribute and 8 MiB aggregate budgets and are retained as hex with byte length and SHA-256. ACL absence, access denial, unsupported xattrs, malformed bytes, I/O failures, and limit hits have distinct states/diagnostics. Any incomplete requested item makes the document partial and the CLI exits 2 after publishing through the existing private no-clobber writer. Non-UTF-8 path bytes are preserved as hex alongside an optional UTF-8 display path. The collector does not recurse, request elevation, execute a selected path, follow final symlinks, or calculate effective access. Intermediate components follow normal Linux path resolution. The 5-second deadline is checked between paths; an in-flight filesystem syscall cannot be canceled by the collector and can take longer. This is a selected-object observation, not a complete permission inventory or an atomic snapshot of filesystem state.

On Windows, the same CLI surface writes the distinct `sideeffect.windows_permission_inventory` v1 schema. It accepts explicit paths only, opens each path with `CreateFileW` using `READ_CONTROL|FILE_READ_ATTRIBUTES` and `FILE_FLAG_OPEN_REPARSE_POINT` (plus backup semantics for directories), then reads metadata and owner/group/DACL using that same handle. It never requests SACL data, elevates, recurses, follows the final reparse point, or evaluates effective access. The returned self-relative descriptor is retained as raw bytes, byte length, and SHA-256. DACL presence/null/empty states and protection/inheritance control flags are reported; ACE order, flags, masks and raw ACE bytes are retained. Only bounded basic allow/deny/audit ACE fields are decoded; unsupported ACE types stay intact as raw evidence. Malformed structures and limits are surfaced, not guessed. Bounds are 256 paths, 32,767 UTF-16 units/path, 1 Mi aggregate path units, 64 KiB/descriptor, 1,024 ACEs/descriptor, 8 MiB aggregate descriptors, 5 seconds checked between paths, and the shared 64 MiB output cap. Publication uses the current-user-only Windows no-clobber publisher. Intermediate path resolution follows normal Windows behavior; this remains a selected-object observation, not a complete or atomic permission inventory.

`inventory access-check` is a separate experimental partial probe. On Linux it accepts one bounded absolute path and `read|write|execute`, pins the resolved final object with `O_PATH`, records selected metadata and calling-thread credential facts, then calls `faccessat2(AT_EMPTY_PATH|AT_EACCESS)` without modifying the object. The syscall result is an observed preflight, not proof that a later operation will work; configured ACLs, capabilities, MAC, seccomp filters, mount policy, and retained ancestor/symlink context are not fully evaluated, so the calculated conclusion is always `unknown`. On Windows it requires a PID plus the matching process creation FILETIME from a process snapshot, opens that process's primary token without elevation, and asks Authz to evaluate a selected local regular file's DACL for one requested file right. The handle's final NT volume path is checked after opening; only `\Device\HarddiskVolume` paths with a numeric volume suffix are evaluated, so a path that resolves to an unrecognized or remote device path is returned unsupported before DACL evaluation. It reads owner and DACL in the descriptor because Authz requires both; the exact bounded descriptor length and SHA-256 identify bytes only. The overall result is always `conditional`, even when the DACL grants or denies that right. Direct remote/device paths, directories, reparse points, AppContainer tokens, and unsupported ACE semantics are not evaluated. Ancestor traversal under the selected token, thread impersonation, SACL/integrity labels, central access policy, and other policy remain unevaluated. Both commands write private, no-clobber JSON and exit `2` because they publish partial/conditional evidence. They request no elevation and do not perform the requested read, write, or execution operation.

The `sideeffect.inventory` v2 document records scope, collection timestamp, source status, package row values/source IDs, raw-row evidence, and diagnostics. The collector shares stdout (32 MiB), stderr (64 KiB), row (8 KiB each, 200,000 total), a 20-second aggregate deadline, and serialized-output (64 MiB) bounds across adapters. Malformed or missing row terminators remain diagnostics; source failures, timeout, and limit conditions make the document partial rather than presenting affected data as absent. The user-selected output file is published privately with mode `0600` and no-clobber semantics. Package values and raw rows can disclose installed software or system details, remain on disk until deleted, and are not automatically redacted.

## Proposed data path

```text
CLI request
    │
    ▼
Capture coordinator ───────► command stdout/stderr + exit status
    │
    ├───────────────────────► raw strace output + tracer status
    ▼
Trace parser ───────────────► parse diagnostics / completeness indicators
    ▼
Versioned run record ───────► raw event references + capture metadata
    │
    ├── Run A ─┐
    └── Run B ─┴─► canonical comparison keys ─► paired diff
                                                   │
                                      ┌────────────┴──────────┐
                                      ▼                       ▼
                               versioned JSON          offline HTML
```

The current paths are `inspect <trace-file>` → bounded regular-file read → strict UTF-8 and line parsing → versioned JSON by default or ASCII-only escaped text with `--format text`; `diff <left-trace> <right-trace>` → parse both inputs → conservative multiset comparison → versioned JSON or ASCII-only escaped text; `explain <trace-file>` → bounded typed summary retaining selected outcome/evidence references and known unknowns; `explain --diff LEFT RIGHT` → the conservative diff engine → bounded count/evidence summary; `explain --inventory-diff BEFORE AFTER` → strict same-platform Linux package v2, Windows software-registration v1, Linux/Windows process v3, Linux/Windows selected-path permission v1, or same-platform Linux startup v2/Windows startup v4 parsing → bounded selected-fact comparison with source completeness, platform-specific identity, ambiguity, and evidence handling; Linux `diff --format html --output REPORT LEFT RIGHT` → bounded HTML buffer → mode-0600 no-clobber report publication; Linux `record --trace OUTPUT -- PROGRAM [ARGS...]` → private FIFO → bounded raw trace → no-clobber file publication; and Linux `record --bundle DIR -- PROGRAM [ARGS...]` → the same bounded capture → trace hash plus fixed schema-v2 metadata → fsynced two-file staging directory → atomic sibling `renameat2(RENAME_NOREPLACE)`. The record command executes the selected program under strace with the user's normal permissions.

Deterministic explanations do not invoke a language model and omit raw arguments, raw result strings, source fingerprints, and free-form diagnostics. Package inventory comparison covers only listed package-manager sources. Process comparison uses PID plus an observed platform-specific generation value (Linux proc start ticks or Windows creation FILETIME), and compares only selected inert process facts. Permission inventory comparison matches exact selected path encodings within the same platform, compares bounded metadata and native ACL/capability facts, and omits raw xattr/security descriptor bytes. Duplicate path identities or incomplete sources suppress uncertain presence changes; inode and Windows file-index values are compared only as reported metadata and do not establish object persistence. Permission comparisons do not calculate effective access. These are bounded pairs of snapshots, not start/exit history, exhaustive inventory, causation, or proof of absence; PIDs and paths in output are sensitive. Startup inventory comparisons are implemented for Linux v2 and Windows v4 with source-specific identities, incomplete-source suppression, and no raw command/configuration values in the output. Optional local-model features use a per-task selected model from the bounded model registry. Every preview digest binds the selected model ID and SHA-256, catalog source/revision or user-provided marker, license/evaluation status, and the task's pinned runtime/backend metadata. Inference revalidates the selected file and stages an exact hash-verified copy. A changed selection requires a new preview digest. The evidence-selection request contains typed syscall facts and direct process relations, and may include strictly recognized errno names plus conservative ASCII lexical path hints for selected `openat`/`openat2` records. Hints remain untrusted, potentially sensitive, lexical values; they do not resolve filesystem paths. The output schema exposes every evidence ID in the bounded request without question-based candidate filtering. The model can return only an existing evidence ID or abstain, which SideEffect validates against the preview; this proves inclusion in the request, not that the record answers the question. Deterministic source evidence remains visible, and model output is not a finding. Resource limits and Linux network-syscall denial provide defense in depth rather than a sandbox. Evidence selection remains Linux x86_64-only and subject to the full-evidence M8 gate in `docs/LOCAL_MODEL_EVALUATION.md`.

## Current parser contract

Linux `sideeffect diff --bundles LEFT_DIR RIGHT_DIR` reads both operands through the strict v1/v2 bundle validator used by `inspect --bundle`, then parses and compares the contained trace bytes. JSON and text output preserve raw-trace diff semantics and omit local bundle paths; HTML is also available through the existing bounded offline report writer. The manifest status fields do not establish capture completeness or command success. A bundle stopped by its requested time limit is rejected before comparison because its event set is known to be incomplete.

The parser accepts a bounded subset of line-oriented `strace` output. Record uses `-f -ttt -yy -s 256 -e trace=%process,%file,%network --kill-on-exit -o <generated FIFO>`; `inspect` does not verify how an input was produced. For current `strace` option and output behavior, see the [`strace(1)` manual](https://man7.org/linux/man-pages/man1/strace.1.html). A smoke test used an extracted strace 6.19 package in WSL without installing it system-wide: `/usr/bin/true` and `/usr/bin/false` produced bounded traces which parsed completely. This does not validate broad syscall or file/network-event coverage.

The parser recognizes PID and timestamp prefixes, syscall calls, common control records, and unfinished/resumed calls. It retains the original raw line and byte offset/length, plus raw syscall argument/result text. Unknown, malformed, or unpaired continuation lines remain in the JSON with diagnostics; invalid UTF-8 and hard budget violations return an error and no document. `parse_status` reports whether the parser classified and reconciled the supplied text; it never asserts capture completeness.

For `openat` and `openat2`, an optional `lexical_path_hint` is derived only from a plain printable-ASCII quoted path operand. An absolute operand is preserved as written; a relative operand is joined to an absolute `AT_FDCWD</...>` or numeric `<...>` directory annotation from `-yy`. The derived JSON value names its basis and stays attached to the original record evidence. Trace inspection schema v7 and comparison schema v3 include the source fingerprints; earlier trace schema v1-v5 and diff schema v1-v2 JSON exports are not imported or migrated. The CLI reads raw `strace` text and does not import or migrate prior SideEffect JSON exports. The hint does not query the filesystem, normalize `.`/`..`, follow symlinks, or track descriptor identity; it may be wrong around symlinks, descriptor reuse/deletion, `openat2` resolution flags, or truncated traces. Escaped, non-ASCII, deleted, truncated, malformed, or unsupported cases omit the hint. Raw arguments are authoritative. Diff output may carry a separate hint from each side strictly for display; `matching_policy.display_only_fields` marks it as display-only, and the matcher never consults it. The text and HTML renderers label it accordingly and keep original arguments visible.

For complete `execve`/`execveat`, `openat`/`openat2`, and `connect` rows, inspection attaches a conservative `outcome` enum to the same record as its exact evidence reference. It recognizes only strict success forms, Linux `-1 ERRNO (message)` failure forms, and `connect`'s `EINPROGRESS` as `in_progress`; other result spellings are `unknown`. Unfinished/resumed rows and other syscall names have no outcome. This is a syscall-result summary only and does not infer a higher-level effect.

For `-yy` output, an unquoted `<` begins a file-descriptor annotation and the parser skips through its next `>`. An unterminated annotation makes that line malformed. Other valid strace representations may be reported as partial until fixtures demonstrate support.

The current hard budgets are 32 MiB total input bytes, 64 KiB per physical record (excluding LF), 100,000 physical records, and 64 MiB for the serialized JSON document. Records include control and unparsed lines. The event fields duplicate portions of raw text and have bounded string lengths because every source record and the overall input are bounded; the serialized document is independently capped before it is written to stdout. These initial values need review against real captures before release.

## Component responsibilities

### CLI and capture coordinator

The CLI preserves argument boundaries, starts the external tracer, manages private staging, and publishes either one raw trace file or one complete run bundle. Linux `inspect --bundle DIR` securely opens and validates supported v1 and v2 bundles before passing its bounded trace bytes through the same parser and renderer as raw trace inspection. The target runs with the invoking user's normal permissions; tracing is observation, not isolation. `--duration-seconds <seconds>` (integer from 1 to 3600) optionally bounds wall-clock capture time; on expiry SideEffect stops the direct tracer, publishes available nonempty partial evidence, and exits `2`, while target outcome and capture completeness remain unknown. No automatic privilege escalation or capture of arbitrary environment variables occurs. The command's stdout/stderr remain inherited. Trace output may contain command arguments, paths, socket addresses, and other sensitive data.

Recording uses a generated FIFO instead of `strace -o FILE`, allowing the parent to read incrementally and enforce the same 32 MiB cap used by `inspect`. When the cap is exceeded, it stops reading, kills only its direct strace process, and discards the staged partial trace without publishing it. SideEffect's tested minimum is strace 6.8; strace introduced `--kill-on-exit` in 6.6, and the option also depends on supported kernel behavior. It is best-effort cleanup; descendants that escape tracing via `CLONE_UNTRACED` may survive. A smoke test with extracted strace 6.19 ran `/usr/bin/true` and `/usr/bin/false`; their traces were bounded, mode 0600, and parsed completely. This test does not establish broad compatibility or file/network-event coverage. The recorder rejects an empty trace to avoid presenting a tracer startup/option failure as a usable artifact. Existing destinations, including symlinks, are rejected. Publication first uses same-directory `linkat`; only errors indicating hard links are unsupported trigger an anchored `renameat2(RENAME_NOREPLACE)` fallback. Both routes atomically preserve no-clobber behavior, and other link errors are returned without fallback. If the kernel or filesystem does not support the no-replace rename operation either, publication fails closed. The selected parent directory is canonicalized and opened once; subsequent FIFO, staging, publication, and cleanup operations are relative to held directory descriptors, so renaming that directory during capture does not redirect writes. Traces are staged with mode 0600 in a private mode-0700 directory. After SideEffect finalizes and publishes a nonempty trace, it propagates the normal exit code reported by strace or re-raises the reported signal (with a conventional 128+signal fallback if re-raising fails). The strace manual says it normally mirrors the wrapped command's exit status or signal; this is not independent verification of command outcome, tracer success, or capture completeness. Detected SideEffect capture failures take precedence and are reported as errors. Command stdout/stderr remain inherited, and arbitrary environment values are not collected by SideEffect. SIGINT, SIGTERM, SIGHUP, and SIGQUIT received by SideEffect trigger direct tracer termination and staged-output cleanup; parent death sends SIGKILL to strace, which requests best-effort traced-process cleanup. A system crash can leave a private staging directory. See the [`strace(1)` manual](https://man7.org/linux/man-pages/man1/strace.1.html).

The FIFO anchor is opened with `O_CLOEXEC`, so the traced command cannot keep it open. Parent supervision polls the FIFO and strace child; there is no separate reader process or shell command string. A hard kill or system crash can leave a private staging directory behind. Command execution remains unrestricted and tracing may alter timing or behavior.

Evidence bundles and report exports use conservative output-path handling. The HTML exporter is Linux-only, buffers rendered output up to the shared 64 MiB cap before creating a staged report, writes it with mode 0600, and publishes without replacing an existing destination using the same hard-link and narrowly selected no-replace rename fallback as trace output. It uses a static HTML/CSS template, restrictive CSP, no script or remote assets, and inserts trace values only as escaped text; local input paths are omitted. Reports can still contain sensitive raw arguments, paths, and endpoints. Tests cover injection strings, controls/bidi formatting, output limits, existing destinations, symlink targets, and staged cleanup. Any deliberate overwrite option requires separate product/security review.

### `strace` integration

The initial capture backend invokes external `strace` on Linux x86_64 with child-following enabled and a scoped set of process, file, and network-related syscalls. The selected capture profile is versioned as `linux_process_file_network_v1`. New bundle schema v2 records optional requested duration and stop reason; schema v1 remains readable. In bundle mode, the manifest records parsed strace major/minor, the raw strace-reported exit code or signal, command outcome `not_independently_verified`, capture completeness `unknown`, and inherited-but-not-captured markers for command streams and tracer diagnostics. It does not store the program/argv, environment, cwd, username, absolute paths, streams, diagnostics, or parsed event copies. The same raw trace remains the evidence artifact; its byte length and SHA-256 are recorded. The hash identifies bytes only and does not establish authenticity or completeness. Bundle mode is opt-in. `inspect --bundle DIR` accepts supported v1 and v2 schemas, rejects unknown fields and extra directory entries, requires the invoking user to own the directory and its mode-0700 directory/mode-0600 single-link regular files, and verifies the bounded manifest and trace length/SHA-256 before parsing. Inspecting a bundle stopped at its time limit returns status `2` and warns that absence from the trace is not evidence of non-occurrence; `diff --bundles` refuses such bundles because their event sets are incomplete. If the atomic rename succeeds but syncing the parent directory fails, the complete bundle is visible and the CLI warns that persistence across sudden power loss is uncertain while propagating the recorded strace status.

The backend does not claim complete coverage. Kernel/version support, permissions, tracing restrictions, untraced code paths, tracer failures, and event loss or truncation can limit observation. When detectable, those conditions are represented as capture diagnostics. A successful tracer exit is not equivalent to a proof that every relevant OS interaction was captured.

### Windows ETW process/file/network capture prototype

The Windows prototype is a separate runtime source and schema, `sideeffect.windows_runtime_capture` v3. It uses the NT Kernel Logger real-time process, FileIo, DiskIo, TcpIp, and UdpIp event classes and writes one user-private, no-clobber JSON file. Process records retain provider GUID, event ID/version/opcode, ETW header PID/TID and flags, QPC timestamp, exact `EVENT_RECORD.UserData` bytes as hex, and a capture-local ordinal. Process payload fields are decoded only after matching the process GUID, documented version/opcode, exact TDH MOF schema, and expected property types. FileIo/TcpIp/UdpIp records are decoded only for explicit event ID 0, schema version 2, supported opcodes, and bounded exact payload layouts; DiskIo records are limited to event ID 0, schema version 0, and supported read/write/flush layouts. Their raw payload bytes remain unchanged alongside typed observations. The Windows Server 2022/2025 live acceptance records use a 4-byte network connection ID even with a 64-bit ETW header; that observed encoding is accepted only when it exactly consumes the final four payload bytes. The exact pointer-sized encoding remains accepted, and extra/truncated bytes remain malformed. FileIo name records can omit the drive letter; requested read/write sizes are not completion results. Network process identity comes from the provider payload, not the header PID/TID. Header fields remain event-context only and no record is currently attributed to the selected command or its descendants. Unknown versions/opcodes, schema or property mismatches, malformed payloads, ambiguous pointer width, and TDH failures retain the raw event with an undecoded status and make collection partial. No command line or SID is decoded. Record/payload limits, unavailable or nonzero final ETW loss counters, timeout, or stop failures also make collection partial. Final loss counters are read from a successful `ControlTrace(STOP)` response. If STOP fails, the pre-stop query is retained as explicitly non-final and collection is partial; cleanup retries STOP once through the session drop path. The ETW interval timestamp begins immediately after session start; the requested target runtime deadline begins only after the real-time consumer is ready. The `document_sha256` field fingerprints the serialized JSON with that field empty; it identifies that representation, not an authenticated trace.

The capture is system-wide for its bounded window and stores the selected target PID and reported exit code separately. It retains event payloads, not the ETL container or ETW extended data. `capture_completeness` remains unknown even when ETW reports no lost events. `inspect --windows-runtime` validates the bounded v3 representation. The v3 `diff --windows-runtime` output compares canonical validated capture representation fingerprints and preserves the v1 category counts plus exact normalized event records as multisets, excluding only capture-local ordinal and QPC timestamp. Fingerprint equality does not compare JSON formatting or authenticate a producer. Its normalization ledger names both excluded fields, why they are excluded, and where the original before/after values remain available. Candidate-changed pairs require a unique same-operation/path or same-process-event/image key. These candidates do not prove event identity. Partial/loss-affected captures never turn unmatched records into removals; ambiguous rows remain unpaired. The separate `attribute --windows-runtime` view follows validated process-start parent IDs in capture order, uses payload process IDs for supported network records, and labels file/disk header PID matches as context candidates only. Every derived item points to the capture fingerprint and record ordinal. The static HTML report presents source references and loss/uncertainty data. A live integration is configured in hosted Windows CI; report only the OS versions for which it actually passes.

The session requests 16 KiB buffers, 8 minimum and 32 maximum, but ETW may adjust actual allocation. Runtime limits are 1–60 seconds, 50,000 events, 8 MiB total payload, 64 KiB per event, and 32 MiB serialized output. The NT Kernel Logger is a shared singleton; if it is already in use or access is denied, capture fails before launching the selected process. The command is started through `std::process::Command` with separate argument values. No automatic elevation occurs. Duration expiry kills only the selected process; descendants may outlive the capture. A manual ignored integration test exercises real process, temporary file, and loopback network events when the local token has permission; ordinary CI covers deterministic decoder fixtures, status rules, limits, argument forwarding, CLI preconditions, and no-clobber behavior without requiring ETW privileges.

### Raw trace and parser

Raw trace text is retained as the evidence source. The parser converts supported records into structured events while keeping a stable reference to each raw record (for example, raw-log offset or record index plus source-file identity). Parse failures are diagnostics with partial results where safe; they must not silently drop an entire run or imply completeness.

The parser must tolerate concurrent processes and unfinished/resumed syscall records according to supported `strace` output formats. Unsupported record forms are surfaced as unsupported or unparsed evidence rather than guessed into structured events.

Each parser input is limited to 32 MiB, 64 KiB per physical record excluding LF, and 100,000 physical records. A diff therefore reads at most 64 MiB combined; output is bounded to at most 200,000 grouped rows and JSON, text, or HTML serialization has a 64 MiB cap. Console formats are buffered before stdout is written; HTML is buffered before file publication. The comparison borrows argument/result strings from parsed inputs and retains source offsets rather than copying full raw lines into deltas. The current diff compares parsed syscall rows as a multiset, ignores only parser-level PID/timestamp prefixes, and keeps syscall names, arguments, and results exact. It refuses partial parses, reports excluded control-row counts, and treats unfinished/resumed rows separately. Its category labels are syscall-name buckets. Capture completeness remains unknown. Oversized input fails explicitly; malformed or unsupported lines remain raw evidence with diagnostics rather than implying they were understood.

### Versioned run record

The run record separates:

- **Capture metadata:** OS/architecture, tracer name/version/arguments, timestamps, command metadata, and capture status.
- **Exact evidence:** raw trace reference, stdout/stderr references, and exact parsed values.
- **Canonical event data:** typed event kind, process identity within the run, operation, observed arguments/result, and raw-evidence references.
- **Diagnostics:** parser warnings, truncation or unsupported conditions, and capture errors.

The JSON format receives an explicit schema version before it is treated as a user-facing interface. Current inspection documents are schema v7; diff documents remain schema v3. Schema-v2 bundle inspection adds its stop reason and optional requested time limit as `bundle_capture`; raw traces and legacy schema-v1 bundles omit the field. The source fingerprint fields were added in v3, outcome summaries in v4, process-creation evidence relations in v5, schema v6 was not published; schema v7 adds optional schema-v2-bundle capture context and clarifies `caller_task_id`. Earlier trace schema v1-v5 and diff schema v1-v2 exports remain standalone and are not imported by this CLI. Unknown future fields should be handled according to a documented compatibility policy.

### Inventory startup configuration

Linux `inventory startup` emits aggregate `sideeffect.startup_inventory` v2 with distinct XDG autostart, systemd unit-file/enablement-reference, common SysV init/runlevel, and common cron components. Each component retains source paths, source status, diagnostics, and bounded line or link-target evidence. Commands and scripts are inert; no parser executes or shell-interprets them. The scan uses curated paths rather than an exhaustive view of systemd's effective load paths or distribution-specific startup mechanisms. It does not determine whether an item is applicable, enabled in a running manager, or executed. Missing optional paths are distinct from inaccessible/unsupported/limit-affected source data.

`explain --inventory-diff` accepts same-platform Linux startup v2 pairs and Windows startup v4 pairs. Linux identities use XDG display paths only when they contain no replacement character, systemd scope/record type/raw path bytes, and legacy source/entry type/raw path bytes. Windows identities use source-specific registry and folder paths, service names, task path plus trigger type, and one ordered action sequence per task. Duplicate identities, incomplete sources, lossy XDG paths, and actions without task paths cannot establish presence. The validator bounds input bytes, JSON nesting/collections/strings, rows, and output, and rejects unknown nested fields. It emits hashed identities, changed-field labels, and input evidence references while omitting raw command/configuration values. Identity hashes are not anonymization: common paths/names may be guessable, so output remains sensitive. It does not infer installation/removal, effective state, execution, or cross-platform equivalence.
### Event model and provenance

The canonical event vocabulary should initially include process execution/lifecycle, supported file operations, and connection-related operations. Event fields distinguish request/attempt from successful result where the syscall result provides that distinction.

Schema v5 introduced `process_lineage`; current schema v7 records a `caller_task_id` and the positive child PID returned by supported process-creation calls. The `strace -f` line prefix identifies the calling task/thread ID, not necessarily the Linux parent process PID when a non-leader thread creates a process. These relations link syscall caller evidence to the returned PID and do not assert an OS parent-child relationship. Complete successful `fork`/`vfork` calls and qualifying `clone`/`clone3` calls are considered. A uniquely paired unfinished/resumed `clone3` call may supply its flags and result across two rows; the relation links to the result row and supporting unfinished row. Unpaired continuation rows, ambiguous child-PID claims, unsupported clone flags, and configured bounds produce diagnostics and omitted relations. No OS parent PID, PID generation, transitive tree, capture root, or configured-startup causation is inferred. The separate `correlate-startup` operation reports only exact literal absolute executable-path candidate matches between selected XDG/systemd configuration values and successful exec filename arguments in saved inputs. It retains source and trace references and all duplicates; its runtime evidence calls the `strace -f` row-prefix identifier `caller_task_id`, which can be a thread ID. Unsupported relevant syntax makes correlation partial; copied configuration/source metadata is capped at 8 MiB. It does not resolve command semantics, symlink targets, or canonical paths, and leaves cron/SysV unassociated. Exact literal paths are compared as written and can themselves name symlinks. File paths may be resolved using observed working-directory changes, directory file descriptors, and path arguments where the parser can do so reliably. If resolution is ambiguous, preserve the original path and mark the canonical path unresolved rather than inventing a location.

For network events, retain the observed address family, IP address, port, operation, and result as available. Do not silently convert an IP to a hostname or claim DNS identity. DNS-related events are out of scope unless separately and explicitly captured by a future backend.

Every derived field and rendered finding should link to the source event(s). This provenance supports review; it does not turn temporal proximity into causal proof.

### Comparison engine

The initial comparison engine keys observed rows by record kind, category, syscall, and exact raw arguments, then compares raw result values with multiset semantics. The JSON `matching_policy.exact_fields` names those fields, and `display_only_fields` marks `lexical_path_hint` as excluded from matching. It classifies added, removed, and uniquely paired changed rows and preserves source references on both sides. It emits a changed row only if exactly one unmatched same-signature row remains on each side after exact matches; ambiguous residual multiplicities stay as additions/removals. `before` references the first CLI input and `after` the second. Parsed PID and timestamp prefixes are ignored only for matching and remain in the original input records. Optional lexical path hints stay side-specific and are explicitly excluded from the matching key; if a grouped evidence row has inconsistent side hints, that side's hint is omitted. The comparison output does not claim to merge continuation rows into logical calls or prove that a capture observed every event.

`sideeffect evidence TRACE SHA256 LINE BYTE_OFFSET BYTE_LENGTH` is a read-only drilldown for a diff's source tuple. The parser computes `source_sha256` from the same bounded byte buffer used to parse records, avoiding a separate read/hash race. The command first verifies the supplied lowercase SHA-256 against that field, then requires an exact match to one parsed syscall, unfinished-syscall, or resumed-syscall record, including the physical line, byte offset, and byte length. It rejects malformed or mismatched fingerprints, control and unparsed rows, and does not print output for a mismatch. On a partially parsed file, it can display a selected parsed row only while marking the input partial; this does not make the trace usable for comparison or establish capture coverage. The fingerprint is an identity check relative to the supplied bytes, not authenticity or completeness; hashes may reveal equality and be guessed for low-entropy inputs. Trace bytes are not uploaded.

The initial rule omits only the parser's top-level PID and timestamp prefixes; values inside syscall arguments or results are not normalized. This can produce differences from run-local identifiers embedded in arguments/results. Future normalization requires explicit evidence and tests. File descriptor numbers and paths are currently compared exactly; there is no blanket rule that removes temporary directories or equates paths by suffix.

Concurrency can change event order even when behavior is similar. The diff should avoid presenting raw sequence order as semantic equivalence. A matching algorithm may group equivalent events, but must surface ambiguous matches and retain original ordering/timestamps in evidence. Unstable matching or normalization must be visible in the output.

### Renderers

JSON is the machine-readable output. The current text view escapes quotes, backslashes, control characters, and all non-ASCII scalars to ASCII, preventing trace input from emitting terminal control sequences. It is still sensitive and not redacted. The Linux HTML exporter creates a self-contained local report with static CSS, restrictive CSP, no scripts, remote assets, or active content sourced from the trace. Every trace-derived value is escaped into a text node; controls and known bidi/default-ignorable characters are presented as literal visible spellings. The report shows comparison context, observed differences, uncertainty, and direct raw-evidence references, but does not include local input file paths.

An export must not be described as sanitized or safe to publish by default. Command arguments, paths, output, and syscall arguments may contain secrets or personal information. If a future redaction option is added, the report must distinguish redacted data from absent data and preserve the original local evidence separately according to an explicit policy.

## Error and status model

The implementation should distinguish at least:

- command's own exit status;
- tracer startup/runtime/exit failure;
- parser errors or unsupported records;
- incomplete or potentially truncated capture;
- comparison ambiguity;
- report export failure.

Resource exhaustion, unsafe output-path resolution, destination collision, and atomic publication failure must also be surfaced distinctly enough for a user to understand whether evidence was captured and whether any final output was written.

The exact CLI exit-code scheme remains open. It must not overwrite or conceal the wrapped command's result; the interface needs a documented way to retrieve both outcomes.

## Security and privacy considerations

See [SECURITY.md](../SECURITY.md) for the project threat model, privacy guidance, and release requirements.

- Treat raw traces, command output, imported traces, and report fields as untrusted input.
- Escape trace-derived content in HTML and avoid remote scripts/assets.
- Enforce the documented input, record, string, event/collection, comparison, and rendered-output budgets for malformed or unusually large traces. Boundary tests must cover the exact chosen limits and limit-plus-one cases.
- Create bundles and reports without following attacker-controlled symlinks or overwriting existing user data; publish completed reports atomically and test collision, symlink, and interrupted-write cases.
- Avoid shell-string interpolation for user-provided command arguments; preserve argument boundaries.
- Do not collect environment variables intentionally unless a separately reviewed feature explicitly requires it.
- Still warn that syscall arguments and stdout/stderr can contain sensitive values.
- Keep data local by default; no telemetry or upload path in v0.
- Do not market the tool as a sandbox, malware detector, complete audit, or proof that a command is safe.

## Runtime and distribution assumptions

Rust is the implementation stack for the core CLI, parser, schema, diff engine, and renderer. The source crate declares Apache-2.0 in `Cargo.toml` and includes the matching `LICENSE`. Runtime capture requires a separately installed external `strace` 6.8 or newer; SideEffect does not link, bundle, or redistribute `strace`. Upstream identifies `strace` itself as LGPL-2.1-or-later ([upstream license statement](https://github.com/strace/strace/blob/master/README.md)). Users obtain it through their operating-system package source. Any future installer or binary distribution that includes `strace` requires a separate review of the exact binary's license, notices, and package obligations; current source-only distribution does not establish legal clearance for such bundling.

Linux x86_64 remains the first capture target. Native Windows inventory and the bounded ETW v3 reader/capture/session path are available without WSL2. Windows runtime diff v3 adds evidence-linked event comparisons and validated representation-fingerprint equality, and the separate attribution view avoids treating header PIDs as file ownership. Hosted live-acceptance evidence is still pending for this source revision; WSL2 runs count only as Linux validation and do not establish native Windows runtime coverage.

The separate `model-explain` path includes bounded typed facts and coverage metadata in the reviewed prompt. Its selector-only response accepts unique syscall-result evidence IDs; SideEffect returns the exact matching preview rows and does not expose model-authored prose or status claims. A selection is a navigation aid, not a verified answer, and cannot establish causation, root cause, safety, effective permissions, or complete coverage. Native Windows uses a suspended process assigned to a Job Object before it resumes, bounded host-process resources, a private temporary model copy, and explicit CUDA offload detection. The Job Object is not GPU-memory isolation and does not deny networking; the selected runtime executable and loaded libraries remain trusted-code dependencies. Selection quality has no semantic pass and the workflow is not release-approved. See `docs/LOCAL_MODEL_EXPLANATION_EVALUATION.md`.

## Optional local model management

`model list`, `show`, `install`, `add`, `select`, and `remove` expose the local model catalog and registry. Selection is independent for evidence selection, explanation, and query planning. The bounded versioned registry is stored in the per-user SideEffect data directory; the model directory has restrictive Unix permissions or a protected current-user Windows DACL. User-provided GGUF registrations store a path, size and SHA-256, plus optional user-supplied license text that is not verified. Removing a user-provided registration does not delete its model file. The current catalog contains query-plan candidates only, supported on Linux x86_64; each has failed a task-specific quality evaluation. No model is recommended as accurate.

Catalog installation accepts only fixed catalog IDs and URLs, displays the exact source/revision, size, platform scope and license, then requires a typed `ACCEPT <license-id>` response. The accepted model ID/revision/license ID/terms URL is persisted before network access and may remain recorded if transfer fails or is cancelled. The downloader uses HTTPS to the pinned Hugging Face source, validates approved redirects, enforces the pinned byte count and SHA-256, stages privately and publishes without replacing an existing destination. It does not send traces or prompts. Analysis commands never download weights. Model selection never installs a runtime; users obtain and trust runtime executables separately. The catalog's local license metadata and a recorded user acknowledgement are not legal advice or a claim that a model is safe or useful.

## Validation strategy

Future implementation must include meaningful automated tests before release:

- parser fixtures covering successful and failed syscalls, child process execution, path handling, concurrent/unfinished records, and unsupported or malformed input;
- capture integration fixtures verifying child following, output handling, tracer status, and preservation of the command exit result;
- comparison fixtures for stable pairs with varied PIDs/timestamps, added/removed/changed events, ambiguous descriptor/path resolution, and nondeterministic order;
- incomplete-capture and diagnostic fixtures proving missing events are not reported as absent behavior;
- JSON schema and round-trip fixtures;
- HTML tests showing malicious trace strings are inert and offline assets are self-contained;
- tests for large or malformed inputs that exercise resource bounds.

No benchmark or coverage percentage is promised in this planning document.
