# Windows Task Scheduler startup lifecycle acceptance

The Windows hosted CI matrix runs `scripts/test_windows_task_startup_lifecycle.ps1` on disposable GitHub-hosted Windows runners after building SideEffect. The script requires both hosted-runner markers and an already-administrative token. It does not elevate and must not be run on a developer or self-hosted machine.

The script creates one GUID-named task in the root task folder and a unique artifact directory under `RUNNER_TEMP`. It refuses to reuse either identity. Its only trigger is a logon trigger configured as disabled, and the task is created with disabled settings. The action points to a generated executable path that must not exist. The script never starts, enables, or runs the task; it makes one static action-path update while both task and trigger remain disabled. Cleanup unregisters only the exact generated task and removes only the checked temporary directory, including failure cleanup.

For baseline, added, changed, and removed states, the acceptance runs the real `inventory startup` CLI and validates schema v10 plus an available `scheduled_task_triggers` source (complete or partial). Source status and up to eight bounded diagnostic codes are reported. A partial Task Scheduler source does not imply complete coverage. The fixture rows themselves must still be present, uniquely identified, and carry exact evidence. The real `explain --inventory-diff` CLI must link the matched action change to the exact before/after action rows. When aggregate inputs are complete, add/remove deltas must link to exact task-trigger and action rows. When an aggregate input is partial, unmatched presence claims must be suppressed and reported as such; the script separately confirms the generated task row appears or disappears in each snapshot. When the Task Scheduler source is partial, the script retains that status and diagnostic codes, verifies the exact fixture rows directly, requires unmatched-presence suppression, and accepts only an evidence-linked matched action change.

These checks validate configured task and trigger data only. `startup_state.observed` and effective state must remain `unknown`; the acceptance makes no claim that Windows would execute the task, that an action succeeds, or that task configuration caused runtime behavior. It does not establish complete Task Scheduler visibility outside the current token and supported boot/logon trigger slice.
