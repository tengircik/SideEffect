# Current source acceptance matrix

This document records what the current repository implementation collects and what evidence it provides for each inventory or runtime source. It is a review aid for the implemented source boundaries, not a phase-acceptance decision, release approval, or claim of complete operating-system coverage. A row marked complete describes the collector's bounded work, not exhaustive coverage of the computer.

“Status/loss” distinguishes source unavailability, malformed data, limits, and runtime loss where the implementation reports them. “Identity/provenance” describes the identifiers and source references retained by the output; fingerprints establish byte consistency, not authenticity. Validation evidence below is repository-local unless a named hosted CI run is linked. Synthetic fixtures and deterministic tests do not establish live source compatibility.

## Session coverage-status crosswalk

`SourceStatus` preserves the selected collector's detailed result in its source record. The session `CoverageStatus` is a coarser summary and uses this explicit mapping:

| Source status | Coverage status | Meaning |
| --- | --- | --- |
| `complete` | `configured` for startup; otherwise `observed` | The selected bounded collector completed its declared work. This does not establish exhaustive coverage; `observed` for an inventory source does not mean runtime activity. |
| `partial` | `partial` | The collector retained a partial result or reported a relevant limitation. |
| `not_checked` | `not_checked` | The selected source was explicitly not checked. |
| `unsupported` | `unsupported` | The selected source or operation is not supported. |
| `access_denied` | `inaccessible` | Access prevented the selected source from being read. |
| `unknown`, `not_applicable`, `unavailable`, `failed`, `timed_out`, `output_limit_exceeded` | `unknown` | The collector cannot claim a complete observation for this source. The original detailed `SourceStatus` remains available in the source entry. |

`not_observed` is reserved and no current session producer emits it: an empty inventory or zero captured events does not establish that software or activity was absent. Do not infer it from a complete source with zero rows.

Current audit-session producers write coverage manifest v2; the reader still accepts coverage v1. For selected runtime sources, v2 includes bounded counts of fixed unsupported/malformed categories derived from retained artifact diagnostics. An empty category list only means no listed diagnostic category was found in that retained artifact; it is not an OS coverage claim. Legacy v1 or missing runtime detail remains unknown for comparison.

## Cross-source comparison notes

- Inventory snapshots are best-effort observations over intervals and are not atomic. A complete collector status means its declared bounded work finished; it does not mean complete OS coverage.
- The session coverage vocabulary defines `not_observed`, but current session producers do not emit it. Empty inventory rows or zero runtime events must not be translated into a claim that software or activity was absent.
- The audit-session comparator requires matching declared platform, architecture, known OS identity/version, source scopes/statuses, collector identities/versions, settings, limits, and artifact contracts. A comparable session pair is not proof of equal coverage or event absence; see `docs/ARCHITECTURE.md` and `docs/AUDIT_SESSION_COMPATIBILITY.md`.
- Linux and Windows schemas often represent different native facts. Similar labels such as “package”, “permission”, “process”, “startup”, or “event” do not imply equivalent semantics. See `docs/SCHEMA_COMPATIBILITY.md` for exact versions and accepted adapters.
- Raw data, paths, names, identifiers, registry/configuration values, and traces may be sensitive. Local output is not automatically redacted or safe to publish; see `SECURITY.md` and `docs/INSTALL.md`.
