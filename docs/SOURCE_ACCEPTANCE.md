# Current source acceptance matrix

This document records what the current repository implementation collects and what evidence it provides for each inventory or runtime source, and accepts R0 only for the documented bounded source set. This is not release approval or a claim of complete operating-system coverage. A row marked complete describes the collector's bounded work, not exhaustive coverage of the computer.

“Status/loss” distinguishes source unavailability, malformed data, limits, and runtime loss where the implementation reports them. “Identity/provenance” describes the identifiers and source references retained by the output; fingerprints establish byte consistency, not authenticity. Validation evidence below is repository-local unless a named hosted CI run is linked. Synthetic fixtures and deterministic tests do not establish live source compatibility.

## Session coverage-status crosswalk

`SourceStatus` preserves the selected collector's detailed result in its source record. The session `CoverageStatus` is a coarser summary and uses this explicit mapping:

| Source status | Coverage status | Meaning |
| --- | --- | --- |
| `complete` | `configured` for startup; otherwise `observed` | The selected bounded collector completed its declared work. This does not establish exhaustive coverage; `observed` for an inventory source does not mean runtime activity. |
| `partial` | `partial` | The collector retained a partial result or reported a relevant limitation. |
| `not_checked` | `not_checked` | The selected source was explicitly not checked. |
| `unsupported` | `unsupported` | The selected source or operation is not supported. |
| `access_denied` | `inaccessible` | Access prevented the selected source from being read. |
| `unknown`, `not_applicable`, `unavailable`, `failed`, `timed_out`, `output_limit_exceeded` | `unknown` | The collector cannot claim a complete observation for this source. The original detailed `SourceStatus` remains available in the source entry. |

`not_observed` is reserved and no current session producer emits it: an empty inventory or zero captured events does not establish that software or activity was absent. Do not infer it from a complete source with zero rows.

Current audit-session producers write coverage manifest v2; the reader still accepts coverage v1. For selected runtime sources, v2 includes bounded counts of fixed unsupported/malformed categories derived from retained artifact diagnostics. An empty category list only means no listed diagnostic category was found in that retained artifact; it is not an OS coverage claim. Legacy v1 or missing runtime detail remains unknown for comparison.

## Downstream consumer identity and comparability contract

These rules describe what each current consumer may claim from its inputs. “Confirmed” below means a source-local fact supported by the cited source records and validated identity rule; it does not mean authenticated producer, durable identity across audits, ownership, or causation. A candidate is never promoted to confirmed merely because its inputs are complete.

| Consumer | Confirmed identity or fact | Candidate identity or association | Unresolved identity and presence-claim suppression |
| --- | --- | --- | --- |
| `compare-sessions` | A verified artifact locator and its bytes belong to the selected session input; exact native inventory keys can establish an item match under that comparator's platform-specific contract. A process snapshot does not gain durable identity from this. | Linux process v4/v5 exact PID plus start-tick pairs, and Windows v3/v4 exact PID plus creation-FILETIME pairs, support candidate field changes only. Linux v5 boot-ID/PID-namespace evidence is a local comparison hint, not host authentication. | Linux v3 process identity is incomparable across snapshots. Process unmatched additions/removals are suppressed when the identity domain is unavailable and for the candidate-only v4/v5 and Windows v3/v4 process schemas; duplicate/ambiguous identities also cannot support presence. For all source roles, platform/scope/artifact-contract or verified-reference mismatch prevents item comparison; incomplete source status makes the item result partial and suppresses that role's unmatched presence rows even when the artifact says complete. Runtime comparison does not infer absence from missing events. Metadata `comparable` is readiness only, independent of per-role status and equal observations. |
| `graph` | A source-local process observation/lifecycle relation may be marked observed when the adapter's reviewed evidence rule is satisfied (including Windows raw Kernel-Process identity agreeing with the TDH sidecar and a unique validated process instance). ## Native Windows 11 inventory-only check (2026-11-03)

The release CLI was rebuilt from branch commit `a160cae` and run on Windows 11 Pro x64, build 26300, under a non-elevated token. The three read-only commands `inventory processes`, `inventory startup`, and `inventory path-executables` each wrote their expected native schema and returned partial status (exit code `2`) rather than hiding unavailable or unsupported rows. Process schema v4 reported inaccessible/malformed process-time or token fields and invalid process identifiers; startup schema v5 reported a service API failure and unsupported scheduled-task action types; PATH schema v1 reported unavailable directories and skipped symlink/reparse-point entries. The artifacts were kept in a unique current-user temporary directory for inspection and then deleted; no row values or raw artifacts were committed.

On the same host and token, a one-second `record --windows-etw` preflight with a controlled `whoami.exe` target returned exit code `1`, reported NT Kernel Logger access denied, stated that no elevation was requested and the target command was not started, and published no capture file. This live denial-path check agrees with the prelaunch ordering tests in `src/record/windows_etw.rs`; it validates refusal behavior only. No successful Windows 11 ETW event capture or provider compatibility is established. Together these checks verify that bounded inventory commands run and expose limitations on this Windows client; they do not establish row completeness, elevated capture, or performance, and do not substitute for the Server 2022/2025 ETW acceptance.

## Cross-source comparison notes

- Inventory snapshots are best-effort observations over intervals and are not atomic. A complete collector status means its declared bounded work finished; it does not mean complete OS coverage.
- The session coverage vocabulary defines `not_observed`, but current session producers do not emit it. Empty inventory rows or zero runtime events must not be translated into a claim that software or activity was absent.
- The audit-session comparator requires matching declared platform, architecture, known OS identity/version, source scopes/statuses, collector identities/versions, settings, limits, and artifact contracts. A comparable session pair is not proof of equal coverage or event absence; see `docs/ARCHITECTURE.md` and `docs/AUDIT_SESSION_COMPATIBILITY.md`.
- Linux and Windows schemas often represent different native facts. Similar labels such as “package”, “permission”, “process”, “startup”, or “event” do not imply equivalent semantics. See `docs/SCHEMA_COMPATIBILITY.md` for exact versions and accepted adapters.
- Raw data, paths, names, identifiers, registry/configuration values, and traces may be sensitive. Local output is not automatically redacted or safe to publish; see `SECURITY.md` and `docs/INSTALL.md`.

## Investigation case evidence authoring

`case add-evidence` is a bounded convenience over the existing case v2 entry and locator contracts. Analyst text is read only from a regular UTF-8 file capped at 16 KiB. The separate strict JSON locator array is capped at 64 KiB and 64 typed locators; any supplied locator is resolved against all explicitly supplied verified sessions before the private no-clobber revision is published. A missing or mismatched session, invalid locator, or locator that does not identify a source row is rejected without output. If a locator resolves while its source/session is partial or unknown, the revision retains that status and exits `2`. Notes may have no locators or include references, while assertions require at least one; both carry `analyst_supplied_unverified` authorship; an exact source reference does not validate analyst interpretation. Cross-platform CLI coverage includes selected-root references on the native host and a dedicated Linux real-strace scenario; a native Windows synthetic ETW CLI scenario is labeled synthetic and validates schema/evidence linkage, not live ETW provider compatibility. See `tests/case_cli.rs` and `tests/case_add_evidence_windows.rs`.
