# Security Policy

**Project status:** early implementation. `sideeffect inspect TRACE` reads one local regular trace file; `inspect --bundle DIR` accepts supported Linux `sideeffect.run` v1 and v2 bundles. Inspection emits schema-v7 JSON with bounded raw `strace` rows, syscall-result summaries, and evidence-linked process-creation observations where exact rows support them. Current schema-v7 relations identify the calling task/thread ID from the `strace -f` prefix and the child PID returned by the syscall; the caller ID is not necessarily the Linux parent PID. `sideeffect diff` emits schema-v3 comparisons only for complete parses. Linux also supports local static HTML diff reports, raw trace recording, and opt-in bundle recording; new bundles use schema v2 with optional requested duration and a stop reason. A time-limited capture publishes available nonempty partial evidence, and its command outcome and capture completeness remain unknown. A narrow Linux real-tracer integration covers a child process, temporary-file activity, and loopback TCP under strace 6.8/6.19 as described below. Broad tracer/kernel compatibility and event coverage remain unverified. The HTML renderer has focused tests but has not received broad browser compatibility or accessibility review. The safeguards below distinguish current behavior from requirements for future features.

The `sideeffect.audit_session` v1 Rust contract parses manifests up to 512 KiB and validates bounded source metadata, fixed Linux artifact names/schema versions, declared per-file and aggregate sizes, and SHA-256 syntax. It is not yet wired to a CLI or filesystem reader: artifact existence, file type, symlink resistance, actual byte length/hash, private staging, and no-clobber directory publication are not implemented. A manifest reference is not verified evidence until those checks exist.

Linux `sideeffect inventory startup --output FILE` is a user-triggered, bounded, read-only aggregate `sideeffect.startup_inventory` v2 snapshot. It has separate XDG autostart, systemd unit/drop-in and enablement-link, common SysV init/runlevel, and common cron configuration/periodic components. The collectors retain source locations, statuses, diagnostics, and bounded line or symlink-target evidence; they never execute or shell-parse commands. Applicability and effective manager state are not evaluated. These are curated common paths, not exhaustive startup coverage; optional missing locations are distinguished from inaccessible, unsupported, malformed, or limit-affected sources.

Linux `sideeffect inventory packages --output FILE` is a user-triggered, read-only, bounded point-in-time snapshot from available dpkg, RPM, pacman, and APK databases at fixed system paths. Adapter arguments are fixed, child environments are cleared, and APK network access is disabled. Shared stdout, stderr, row, and deadline budgets apply across sources. Unsupported manager detection checks fixed system paths for XBPS, Nix, Guix, Snap, and Flatpak; custom or per-user installations can be missed. Schema `sideeffect.inventory` v2 records source IDs, evidence, and explicit complete/partial/unavailable/unsupported/not-checked states. Its private mode-0600 output is published without replacing an existing destination. This remains a partial view of registered software and does not inspect startup hooks/scripts or runtime activity.

Linux `sideeffect inventory processes --output FILE` reads bounded `/proc/<pid>/status` values and `/proc/<pid>/exe` link text for visible numeric process entries. It does not read command lines or open executable targets. Duplicate selected status keys are omitted as ambiguous. Limits include 8,192 process entries, 64 KiB per status file, 32 MiB aggregate status bytes, 4 KiB per executable link, 4 MiB aggregate executable-link bytes, and a 10-second scan deadline. The walk is non-atomic and visibility-limited; process paths and identity data are sensitive. Output remains local until deleted and is not automatically redacted or uploaded.

Windows `sideeffect inventory processes --output FILE` takes one bounded Tool Help process snapshot and queries accessible image paths with `PROCESS_QUERY_LIMITED_INFORMATION`. It does not read command lines, inspect process memory, launch processes, or request elevation. Snapshot rows and path lookups are separated in time; a process may exit or a PID may be reused between them. Access-denied, vanished, malformed, and limit-affected data remain partial/unknown. The collector limits process rows, duration, per-image UTF-16 code units, aggregate path data, and serialized output. It writes through a sibling staging directory and file whose protected DACL grants full access only to the current user's token SID, then atomically moves without replacing an existing destination. Names and paths are sensitive. This initial Windows inventory does not establish complete process visibility.

Windows `sideeffect inventory packages --output FILE` reads only selected values from current-user and accessible machine-wide Uninstall registry keys in the native and 32-bit views. It does not call `Win32_Product`, which can trigger installer consistency checks, and it never expands `REG_EXPAND_SZ`, parses uninstall commands, or launches them. The collector bounds registration count, subkey/value lengths, aggregate data, and duration; the 10-second deadline is checked between registry calls and cannot cancel an in-flight Windows API call. Exact selected registry value bytes are retained as hexadecimal. Missing, malformed, unsupported, inaccessible, and limit-affected values are explicit/partial. Output uses the current-user-only DACL publisher and contains sensitive application names, paths, and uninstall commands. Portable/unregistered software and other registration formats may not appear.

Windows `sideeffect inventory startup --output FILE` reads only selected current-user/machine Run/RunOnce registry views and the current/common Startup folders. It keeps `REG_SZ` and `REG_EXPAND_SZ` values as inert text with raw UTF-16 code-unit evidence; it never expands environment variables, parses commands, opens shortcut targets, or executes entries. Registry value names/data, folder entry counts, paths, and elapsed collection time are bounded. Inaccessible, malformed, unsupported, and limit-affected sources are partial; service configuration and scheduled-task boot/logon triggers are explicitly `not_checked`. Paths and commands can reveal usernames, software, projects, or internal structure; review output before sharing. This is not an effective or exhaustive startup inventory and does not establish that an entry ran.

Windows `sideeffect inventory permissions --output FILE PATH...` inspects only explicitly supplied paths. It opens each final object with read-control and file-attribute access plus `FILE_FLAG_OPEN_REPARSE_POINT`, then reads metadata and owner/group/DACL through the same handle. It does not request SACLs, recurse, elevate, follow the final reparse point, or calculate effective access. The self-relative security descriptor is retained with length and SHA-256; DACL state/control and ordered ACE raw bytes are preserved, with bounded decoding only for basic allow/deny/audit ACEs. Unsupported ACE forms remain raw and inert. Path, descriptor, ACE, aggregate, duration, and output bounds are enforced; malformed or inaccessible objects remain partial/unknown. Paths and ACL evidence may reveal user and system configuration and should be reviewed before sharing.

Linux `sideeffect inventory permissions --output FILE PATH...` is a user-triggered, read-only, bounded snapshot of explicitly selected paths. It records metadata, supported POSIX ACL xattrs, and `security.capability` file-capability xattrs (Linux VFS revisions 1–3) for regular files and directories in `sideeffect.permission_inventory` v1. It pins each final path component with `O_PATH|O_NOFOLLOW`, then reopens the pinned descriptor read-only through `/proc/self/fd` for xattr reads; it checks the reopened object identity against the pinned descriptor. It does not follow final-component symlinks, recurse, execute paths, or request elevation. Intermediate components use normal Linux resolution. Bounds are 256 paths, 4 KiB per path, 64 KiB per xattr, 8 MiB total ACL bytes, 8 MiB total capability bytes, and a 5-second deadline checked between paths. An in-flight filesystem syscall cannot be canceled and may exceed that interval. Missing xattrs, access denial, unsupported xattrs, malformed bytes, and limits are represented distinctly; incomplete rows produce overall partial status. Raw ACL/capability bytes and path bytes are retained in bounded hex form with SHA-256 metadata. This is not a recursive or exhaustive permission inventory and does not calculate effective access.

## System, scope, and threat model

Linux `diff --bundles LEFT_DIR RIGHT_DIR` validates each operand with the same no-follow, strict-schema bundle reader used by `inspect --bundle`, including ownership/mode, fixed-entry, size, and trace length/SHA-256 checks before parsing. Both bundles are validated before comparison output is serialized. Bundles stopped at their requested time limit are refused before comparison. The manifest's `unknown` completeness and unverified command-outcome markers are not treated as proof; parsed partial traces are rejected by the existing diff policy. The resulting JSON/text/HTML comparison has the same evidence and sensitivity characteristics as a raw-trace diff and does not include local bundle paths.

The current inspector reads user-selected trace text and emits schema-v7 JSON with raw rows, parsed fields, selected-syscall outcome summaries, source byte references, a SHA-256 fingerprint over the parsed bounded bytes, and `process_lineage`. When the source is a schema-v2 run bundle, it also emits `bundle_capture` with the recorded stop reason and optional requested time limit; raw trace inputs and legacy v1 bundles omit that field. Schema v5 introduced process-creation relations; schema v7 names the source field `caller_task_id`. A `strace -f` line prefix identifies the calling task/thread ID, which may differ from the Linux parent process PID when a non-leader thread creates a process. Current relations link that caller task ID to the strict child-PID result from a complete successful `fork`, `vfork`, or qualifying non-thread `clone`/`clone3` row; each relation links to the result row and, for a split `clone3`, also links to the unfinished arguments row. They are evidence of syscall caller/result association, not an OS parent-child claim. Incomplete calls, unsupported clone flags, thread clones, `CLONE_PARENT` calls, and ambiguous repeated child-PID claims do not become guessed edges. No complete tree, PID-generation model, root identity, or startup-to-execution attribution is claimed. `source_sha256` identifies bytes but does not authenticate them or prove capture completeness. The trace parse status remains separate from lineage diagnostics. With a timed schema-v2 bundle, `inspect --bundle` includes its stop reason and requested time limit in JSON/text, returns status `2`, and warns that absence is not evidence of non-occurrence; `diff --bundles` refuses timed bundles because their event sets are incomplete. `evidence` references remain offsets into the exact source bytes, and the fingerprint identifies those bytes without authenticating them.

`diff-summary` is a separate aggregate-only serializer, not a transformation of the detailed diff schema. Its type can contain only a fixed schema identifier, version, parse/capture status enums, four category enums, and bounded integer group counts, plus a static disclosure. It does not serialize or retain syscall names, arguments/results, lexical paths, source hashes, evidence references, or local input paths. This is field omission, not secret detection or a safe-to-share guarantee: category/count patterns remain potentially sensitive. JSON is written to stdout; its optional Linux HTML form uses the same bounded private no-clobber writer and includes no scripts or remote assets. No network upload is performed by this command.

The operator is trusted to select a trace file or choose a command and decide whether to run it. The selected file's contents, trace strings, command arguments, capture output, and future report values are untrusted. The inspector does not execute trace content. The recorder invokes the external `strace` binary and runs the selected command with the invoking user's permissions. The kernel, tracer, and selected syscall set form part of the observation boundary. Repository vulnerabilities are reportable when a realistic input or action crosses that boundary and causes impact beyond the documented behavior.

## Security invariants

SideEffect is a local observation and comparison tool. It is not a sandbox, malware detector, vulnerability scanner, or security verdict. `inspect` does not run the represented command. `record` runs the chosen command with the permissions of the user who starts it; it may change files, start child processes, access the network, or perform any other action available to that account.

Only run commands and inputs you trust. Use least privilege. If you choose to run an untrusted command, arrange operating-system isolation separately before running it; SideEffect itself does not provide that isolation. Do not run it as an administrator or root user unless the target command genuinely requires those privileges.

The planned v0 target is Linux x86_64 with an external `strace` executable. An existing WSL2 installation may provide a Linux environment for Windows users; native Windows tracing is not supported or promised. Capture completeness depends on the kernel, tracer version and configuration, permissions, and supported syscall set. A successful trace does not prove that every relevant interaction was observed.

Temporal order and process ancestry can help a human investigate a behavior change, but they do not prove that one event caused another. Failed syscalls represent observed attempts, not successful effects. Reports must preserve uncertainty and capture limitations.

## Data handling and privacy

The current commands have no telemetry, hosted service, or automatic report upload. `inspect` and JSON/text `diff` read local files and write to stdout; HTML `diff` writes a mode-0600 report locally; `record --trace` writes a raw trace locally; `record --bundle` writes a raw trace and privacy-minimized manifest locally; Linux inventory outputs use mode 0600, and the Windows process inventory uses a protected current-user-only DACL. These files remain until the user deletes them. This does not make trace or inventory data safe to share:

- Raw traces can contain command-line arguments, file paths, IP addresses and ports, and other values passed to traced syscalls. Arguments can contain credentials or tokens. Paths and output can reveal usernames, project names, customer data, or internal infrastructure.
- Package snapshots contain installed package names, versions, architecture, package status where provided, and raw rows from supported local package databases. This information can reveal installed software and system details. The snapshot is not automatically redacted; review it before sharing and delete it when no longer needed. It excludes unregistered software and can miss unsupported managers or custom installations outside checked paths.
- Process snapshots contain observed process names, executable-link targets, IDs, parent/thread-group relationships, UID/GID tuples, capability masks, and `NoNewPrivs`/`Seccomp` values from visible numeric `/proc/<pid>` entries. They omit command lines and do not open executable targets, but paths and process details remain sensitive system data. The walk spans explicit start/end timestamps and is not atomic or exhaustive; procfs visibility, concurrent changes, unreadable/vanished rows, and configured limits can leave unknown data. Review before sharing and delete when no longer needed.
- Windows process snapshots contain process and parent IDs, thread counts, Tool Help executable names, and image paths where limited query access succeeds. They omit command lines and process memory; paths can still reveal usernames, applications, projects, or organization structure. Tool Help visibility, protected processes, PID reuse, process exit, and configured limits can leave unknown data. Review before sharing and delete when no longer needed.
- Startup snapshots contain configured XDG, systemd, SysV, cron, Windows Run/RunOnce, Startup-folder, and visible Windows service configuration, including potentially sensitive command/script text, service accounts, and binary paths. They are bounded source inventories: commands and paths remain inert, applicability and execution are not established, scheduled-task triggers remain uncollected on Windows, and missing, inaccessible, or unreadable sources remain distinct from discovered entries. Non-UTF-8 Unix paths may have a display string and a byte-preserving hexadecimal form. The inventory is not a race-proof or exhaustive snapshot. Review it before sharing and delete it when no longer needed.
- Permission snapshots contain selected paths, owner/group IDs, mode bits, device/inode identifiers, and raw ACL/file-capability xattr bytes. These can reveal directory structure and local accounts or capability assignments. The collector preserves exact Unix path bytes but does not redact them. It reports only selected objects and supported metadata/ACL/capability data; it does not resolve effective access under a user's full credentials, namespaces, mount options, or security-module policy. Final-component symlinks are not followed; intermediate path components use normal Linux resolution. Review before sharing and delete when no longer needed.
- Command stdout and stderr may also contain sensitive information.
- The product does not plan to deliberately collect environment variables in v0, but that does not make a trace secret-free. The exact information captured depends on the command, selected syscalls, tracer behavior, and platform.
- No automatic redaction or guarantee that an export is safe to publish is planned. If redaction is added later, it must be described as best-effort unless it can be proven otherwise. Users must inspect traces and reports before sharing them.

Keep evidence bundles in a directory whose access you control. Bundle creation rejects a parent writable by other users unless the sticky bit protects directory entries. Processes running as the same user remain trusted and can alter files owned by that user; the bundle hash is not an authenticity guarantee. Do not attach real traces, command output, or report exports to public issues or pull requests. Use synthetic fixtures or carefully reviewed, sanitized examples instead. Do not assume that replacing a username or one apparent token removes all sensitive data.

## Implemented and planned safeguards

The following safeguards are implemented in part across `inspect`, `diff`, and `record`; remaining capture and rendering requirements are listed explicitly:

- Treat input traces, command arguments/capture output, and future report values as untrusted input.
- Preserve argument boundaries when starting a command; never construct a shell command by interpolating user-supplied text. The current record command does this and uses a generated FIFO path rather than the user-selected output path as strace's `-o` value.
- Recorded and inspected trace inputs are limited to 32 MiB; each parser limits physical records to 64 KiB and total records to 100,000. Each diff input is limited to 32 MiB (64 MiB combined); diff rows are limited to 200,000, and JSON/text/HTML serialization is capped at 64 MiB before stdout or report publication. The package inventory JSON comparison also caps each package list at 200,000 rows and each document at 200,000 diagnostic entries; diagnostic entries are validated and counted without retaining them. The trace diff holds parsed inputs and bounded references/keys rather than copying raw lines into every delta. Reject or clearly flag malformed, oversized, truncated, and unsupported input rather than silently treating it as complete.
- The current recorder and HTML report exporter reject an existing destination (including symlinks), stage output with mode 0600 in a mode-0700 directory, and use directory descriptors plus same-directory `linkat` for no-replace publication. Only errors that identify unsupported hard links trigger an anchored `renameat2(RENAME_NOREPLACE)` fallback; collisions, permission errors, and other failures do not. If no-replace rename is unsupported, publication fails closed. It discards oversized captures after terminating its direct strace process. It handles SIGINT, SIGTERM, SIGHUP, and SIGQUIT by terminating and reaping that child; parent death requests SIGKILL for strace. Traced descendants can still escape via `CLONE_UNTRACED`, and a system crash can leave a private staging directory behind. The destination parent is the canonicalized directory object opened at operation start; subsequent operations remain anchored to that object even if it is renamed. Filesystems must support either hard-link publication or `renameat2(RENAME_NOREPLACE)` for completed output publication.
- Render every trace-derived value as inert text in offline HTML. The current renderer escapes values into text nodes and uses a restrictive CSP with no script or remote assets; keep context-aware escaping, do not evaluate values as markup or script, and do not add network requests from a report.
- Keep raw evidence local and distinguish exact evidence from normalized or derived comparison fields.

Fake-tracer tests exercise argument construction, bounded FIFO recording, output collisions, symlink safety, and staging cleanup for pre-launch failures. Linux integration tests exercise real strace with fixed Python targets, including a child execution on the candidate side, temporary files, loopback-only TCP, a normal target exit code of 37, and target termination by SIGTERM; they require `strace` and `python3`. They check that traces are published before the reported target outcome is propagated. This follows strace's documented wrapper behavior but does not establish tracer success or capture completeness. The event test checks successful child `execve` evidence in either one complete row or a matching-PID unfinished/resumed pair, verifies the diff references the observed child row, checks that selected trace sentinels do not appear in captured command output, and removes its private temporary directory. CI stores no traces or reports as artifacts. HTML renderer and Linux CLI tests cover injection strings, control/bidi visibility, no remote assets, output limits, mode 0600, and no-clobber behavior. Before release, broader real-tracer testing must verify additional options, selected observations, output limits, and cleanup behavior; HTML still needs broader browser and accessibility review.

Trace text is already an untrusted input to `inspect`. The bundle reader accepts fixed schema-v1 and v2 manifests and files; future import formats or schema versions require separate review before support.

## Reportable findings and severity context

Report security issues that demonstrate a concrete violation of a documented or planned invariant, for example:

- Report rendering executes trace-derived content or initiates a network request; or SideEffect itself makes an outbound request unrelated to the wrapped command and without user request.
- A crafted command argument, path, trace, or report value causes SideEffect to execute an unintended command, overwrite unrelated files, escape its selected output directory, or disclose local data to another party.
- An input bypasses parser or renderer resource limits and can cause a reproducible denial of service beyond the documented per-run limits.
- A vulnerability in the evidence handling path exposes command output, arguments, paths, or trace data outside the local user's intended access.

Severity depends on reachability and impact. The fact that the user intentionally ran a command does not make a separate SideEffect vulnerability acceptable; conversely, that command's expected actions under the user's permissions are not a SideEffect security finding by themselves.

## Out of scope and known limitations

SideEffect is not intended to prevent the chosen command from modifying files or accessing the network, identify malware, establish that a command is safe, capture every system interaction, or prove causation. These are product limitations, not vulnerabilities, provided the implementation does not make contrary claims or violate the invariants above. Sensitive values appearing in a local trace as a result of the selected capture are an acknowledged privacy risk; unexpected external disclosure or unsafe rendering is reportable.

The current comparison is a conservative parser-row diff, not a capture-completeness check or logical syscall reconstruction. One Linux real-tracer integration case observes a temporary file operation, a child `execve` attempt and successful return as either one row or a pair of continuation rows, and a loopback connection; another checks inherited target stdout/stderr and captures a child `execve` failure with `ENOENT` evidence. A separate smoke test used `/usr/bin/true` and `/usr/bin/false`; lifecycle tests also use controlled fake executables, and parser/diff fixtures remain synthetic. HTML output is static and offline, but broad browser compatibility and accessibility remain unreviewed. Real `strace` compatibility beyond the tested 6.8 and 6.19 versions, other file/network-event coverage, and capture completeness remain unverified. The Linux/`strace` scope, incomplete observation possibilities, local raw-data exposure, absence of automatic redaction, and non-causal nature of event comparison are known product limitations that must remain visible in user-facing documentation.

## Reporting a vulnerability

**Private reporting is available.** Use GitHub's [Report a vulnerability](https://github.com/tengircik/SideEffect/security/advisories) action on the repository Security advisories page. GitHub private vulnerability reporting was enabled and the API returned `enabled: true` on 2026-10-25. See GitHub's [private vulnerability reporting requirements](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository). Recheck the setting periodically and before each release.

Do not post exploit details, sensitive traces, or unpublished vulnerability information in a public issue. Use the private reporting action above for security reports.

Please include the affected commit or release, operating system and architecture, required tracer version, reproduction steps, and the impact you observed. Do not include real secrets or personal data in a report unless they are essential to the reproduction.

## Release security review

Before each public release, maintainers should verify the supported platform and `strace` range, parser limits and failure behavior, path handling, HTML escaping and offline behavior, data-retention guidance, and the private vulnerability reporting route. Release notes must distinguish implemented and tested behavior from known limitations and planned work.
