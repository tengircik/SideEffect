# Security Policy

**Project status:** early implementation. `sideeffect inspect TRACE` reads one local regular trace file, while `inspect --bundle DIR` reads a validated Linux v1 bundle; both parse bounded `strace`-style text and write JSON by default; `inspect --format text` emits an ASCII-only terminal-safe view of all parser rows and diagnostics. `sideeffect diff LEFT RIGHT` parses two local trace files and writes a bounded JSON comparison or ASCII-only terminal-safe text view only when both parses are complete. Linux also supports `diff --format html --output REPORT LEFT RIGHT` for a bounded static offline report. Linux `sideeffect record --trace OUTPUT -- PROGRAM [ARGS...]` runs a command under external strace and writes a capped raw trace through a private FIFO; opt-in `record --bundle DIR -- PROGRAM [ARGS...]` publishes the same raw trace with a fixed `sideeffect.run` v1 manifest. A narrow Linux integration test records temporary file operations, a fixed child process, and loopback TCP activity, then checks inspect/diff evidence; it passed in WSL with extracted Ubuntu strace packages 6.8 and 6.19, without system installation. The test keeps captures in a private temporary directory, checks selected trace sentinels do not appear in captured command output, removes the directory, and creates no report; CI has no artifact-upload step. These results do not verify every supported strace version or kernel/distribution combination. Broad real-tracer compatibility and event coverage remain unverified. The HTML renderer has focused tests but has not received broad browser compatibility or accessibility review. The safeguards below distinguish current behavior from requirements for future features.

Linux `sideeffect inventory startup --output FILE` is a user-triggered, bounded, read-only discovery of `.desktop` files in XDG autostart directories. It writes separate schema `sideeffect.startup_inventory` v1, preserves selected raw keys and other nonempty `[Desktop Entry]` lines as evidence only when each physical line is within the 64 KiB line limit, and marks applicability not evaluated; it never executes `Exec`/`TryExec`. The scan examines at most 100,000 physical lines globally; reaching that limit emits a source-location diagnostic and makes the result partial. An overlong line produces only a line/byte-offset diagnostic, not retained contents, and makes the source partial. Invalid UTF-8 values are represented as hex. Source paths are serialized using lossy UTF-8 conversion, so non-UTF-8 path bytes are not faithfully represented. Missing optional directories are empty, while inaccessible, malformed, or limit-affected sources are partial. This is bounded XDG file discovery, not an effective or exhaustive startup inventory.

Linux `sideeffect inventory packages --output FILE` is a user-triggered, read-only, bounded point-in-time snapshot of the local Debian dpkg package database. Its private mode-0600 JSON output is published without replacing an existing destination; partial or unavailable source data is recorded as partial/unknown with diagnostics. This is not complete software inventory and does not inspect processes, permissions, startup hooks/scripts, or runtime activity.

## System, scope, and threat model

Linux `diff --bundles LEFT_DIR RIGHT_DIR` validates each operand with the same no-follow, strict-schema bundle reader used by `inspect --bundle`, including ownership/mode, fixed-entry, size, and trace length/SHA-256 checks before parsing. Both bundles are validated before comparison output is serialized. The manifest's `unknown` completeness and unverified command-outcome markers are not treated as proof; parsed partial traces are rejected by the existing diff policy. The resulting JSON/text/HTML comparison has the same evidence and sensitivity characteristics as a raw-trace diff and does not include local bundle paths.

The current inspector reads user-selected trace text and emits schema-v4 JSON containing raw lines, parsed fields, conservative selected-syscall outcomes, and `source_sha256`, a SHA-256 fingerprint computed over the same bounded byte buffer used for parsing. For a small `openat`/`openat2` subset it may add a printable-ASCII lexical path hint based on the argument spelling and a `-yy` annotation. The hint does not query or canonicalize filesystem state and can be wrong around symlinks, descriptor reuse, resolution flags, or incomplete traces; raw arguments remain authoritative. Complete `execve`/`execveat`, `openat`/`openat2`, and `connect` records may receive an outcome derived only from strict success, Linux `-1 ERRNO (message)` failure, or `connect` `EINPROGRESS` result forms; other forms are `unknown`. The outcome stays on the evidence-linked record, preserves raw result/line fields, and describes only the syscall result, not a higher-level effect. Its text view shows each row and diagnostic. The `evidence` command requires a lowercase source fingerprint and exact source tuple, compares the fingerprint before lookup, rejects unparsed/control/mismatched rows, and emits the selected parsed row using the terminal-safe formatter within the regular-file and output limits. For partial traces it labels the result partial. A matching hash identifies the supplied bytes relative to that fingerprint but does not authenticate them or prove capture completeness. Hashes can reveal equality or be guessed for low-entropy inputs; treat them as sensitive metadata. Trace bytes remain local and are not uploaded. Both text formatters escape controls and non-ASCII characters to prevent terminal-control injection, but do not redact secrets. The current diff reads two such files and emits schema-v3 event deltas with source offsets and separate fingerprints for the exact left/right bytes; it ignores only parsed PID/timestamp prefixes for matching, keeps raw arguments/results exact, reports control-row counts, and states capture completeness is unknown. The JSON `matching_policy.exact_fields` documents exact comparison fields, while side-specific lexical hints are listed in `display_only_fields` and never affect matching. Text and HTML repeat this boundary next to each hint. The HTML formatter emits static markup and CSS, applies a restrictive CSP, escapes trace values into text nodes, and includes no scripts or remote assets; it omits the local input paths. Current capture runs the selected command under `strace` and stages a bounded raw trace locally; after successful publication, it propagates strace's reported exit code or signal. The strace manual says it normally mirrors the wrapped command outcome; this does not independently verify command status, tracer success, or capture completeness. Detected SideEffect capture errors take precedence. Bundle mode writes exactly `run.json` and `trace.strace` in a mode-0700 directory, with mode-0600 files, and atomically renames the sibling staging directory without replacing an existing destination. The manifest records fixed tool/platform/profile metadata, parsed strace major/minor version, raw strace-reported exit code or signal, explicit `not_independently_verified` command outcome and `unknown` capture completeness, inherited-but-not-captured stream/diagnostic markers, and exact trace length/SHA-256. It omits command/program/argv, environment, cwd, username, absolute paths, stdout/stderr, tracer diagnostics, and event copies. The hash can reveal equality and does not authenticate the trace. Linux `inspect --bundle DIR` reads only the current schema-version-1 bundle. It opens the bundle directory and fixed files without following symlinks, rejects extra entries, requires current-user ownership and private 0700/0600 modes, limits the manifest to 16 KiB and trace to 32 MiB, rejects unknown schema fields, and validates exact trace byte length and SHA-256 before parsing. The resulting inspect JSON contains no local bundle path. There is no migration support. Earlier trace schema-v1-v3 and diff schema-v1-v2 documents are not imported or migrated. The main assets are the user's machine and files, input traces, command execution context, and potentially sensitive raw trace data.

`diff-summary` is a separate aggregate-only serializer, not a transformation of the detailed diff schema. Its type can contain only a fixed schema identifier, version, parse/capture status enums, four category enums, and bounded integer group counts, plus a static disclosure. It does not serialize or retain syscall names, arguments/results, lexical paths, source hashes, evidence references, or local input paths. This is field omission, not secret detection or a safe-to-share guarantee: category/count patterns remain potentially sensitive. JSON is written to stdout; its optional Linux HTML form uses the same bounded private no-clobber writer and includes no scripts or remote assets. No network upload is performed by this command.

The operator is trusted to select a trace file or choose a command and decide whether to run it. The selected file's contents, trace strings, command arguments, capture output, and future report values are untrusted. The inspector does not execute trace content. The recorder invokes the external `strace` binary and runs the selected command with the invoking user's permissions. The kernel, tracer, and selected syscall set form part of the observation boundary. Repository vulnerabilities are reportable when a realistic input or action crosses that boundary and causes impact beyond the documented behavior.

## Security invariants

SideEffect is a local observation and comparison tool. It is not a sandbox, malware detector, vulnerability scanner, or security verdict. `inspect` does not run the represented command. `record` runs the chosen command with the permissions of the user who starts it; it may change files, start child processes, access the network, or perform any other action available to that account.

Only run commands and inputs you trust. Use least privilege. If you choose to run an untrusted command, arrange operating-system isolation separately before running it; SideEffect itself does not provide that isolation. Do not run it as an administrator or root user unless the target command genuinely requires those privileges.

The planned v0 target is Linux x86_64 with an external `strace` executable. An existing WSL2 installation may provide a Linux environment for Windows users; native Windows tracing is not supported or promised. Capture completeness depends on the kernel, tracer version and configuration, permissions, and supported syscall set. A successful trace does not prove that every relevant interaction was observed.

Temporal order and process ancestry can help a human investigate a behavior change, but they do not prove that one event caused another. Failed syscalls represent observed attempts, not successful effects. Reports must preserve uncertainty and capture limitations.

## Data handling and privacy

The current commands have no telemetry, hosted service, or automatic report upload. `inspect` and JSON/text `diff` read local files and write to stdout; HTML `diff` writes a mode-0600 report locally; `record --trace` writes a raw trace locally; `record --bundle` writes a raw trace and privacy-minimized manifest locally; `inventory packages`, `inventory processes`, and `inventory startup` write mode-0600 snapshots locally. These files remain until the user deletes them. This does not make trace or inventory data safe to share:

- Raw traces can contain command-line arguments, file paths, IP addresses and ports, and other values passed to traced syscalls. Arguments can contain credentials or tokens. Paths and output can reveal usernames, project names, customer data, or internal infrastructure.
- Package snapshots contain installed package names, versions, architecture, package status, and raw dpkg query rows. This information can reveal installed software and system details. The snapshot is not automatically redacted; review it before sharing and delete it when no longer needed. It covers only records available from the local dpkg database, not manually copied or otherwise unregistered software.
- Process snapshots contain observed process names and IDs, parent/thread-group relationships, UID/GID tuples, capability masks, and `NoNewPrivs`/`Seccomp` values from visible numeric `/proc/<pid>/status` entries. They omit command lines and executable paths, but remain sensitive system data. The walk spans explicit start/end timestamps and is not atomic or exhaustive; procfs visibility, concurrent changes, unreadable/vanished rows, and configured limits can leave unknown data. Review before sharing and delete when no longer needed.
- Startup snapshots contain discovered XDG `.desktop` paths and selected raw configuration keys, including potentially sensitive command strings and paths. Other nonempty lines in `[Desktop Entry]` are retained only up to the 64 KiB physical-line limit; an overlong line contributes a diagnostic but not its contents. Non-UTF-8 source paths are rendered through lossy UTF-8 conversion and cannot be recovered faithfully from the path string. The collector does not evaluate applicability, resolve or execute `Exec`/`TryExec`, or establish effective startup behavior. Path-based directory enumeration has a race window after the no-follow metadata check; this bounded discovery is not a race-proof filesystem snapshot. Review before sharing and delete when no longer needed.
- Command stdout and stderr may also contain sensitive information.
- The product does not plan to deliberately collect environment variables in v0, but that does not make a trace secret-free. The exact information captured depends on the command, selected syscalls, tracer behavior, and platform.
- No automatic redaction or guarantee that an export is safe to publish is planned. If redaction is added later, it must be described as best-effort unless it can be proven otherwise. Users must inspect traces and reports before sharing them.

Keep evidence bundles in a directory whose access you control. Bundle creation rejects a parent writable by other users unless the sticky bit protects directory entries. Processes running as the same user remain trusted and can alter files owned by that user; the bundle hash is not an authenticity guarantee. Do not attach real traces, command output, or report exports to public issues or pull requests. Use synthetic fixtures or carefully reviewed, sanitized examples instead. Do not assume that replacing a username or one apparent token removes all sensitive data.

## Implemented and planned safeguards

The following safeguards are implemented in part across `inspect`, `diff`, and `record`; remaining capture and rendering requirements are listed explicitly:

- Treat input traces, command arguments/capture output, and future report values as untrusted input.
- Preserve argument boundaries when starting a command; never construct a shell command by interpolating user-supplied text. The current record command does this and uses a generated FIFO path rather than the user-selected output path as strace's `-o` value.
- Recorded and inspected trace inputs are limited to 32 MiB; each parser limits physical records to 64 KiB and total records to 100,000. Each diff input is limited to 32 MiB (64 MiB combined); diff rows are limited to 200,000, and JSON/text/HTML serialization is capped at 64 MiB before stdout or report publication. The diff holds parsed inputs and bounded references/keys rather than copying raw lines into every delta. Reject or clearly flag malformed, oversized, truncated, and unsupported input rather than silently treating it as complete.
- The current recorder and HTML report exporter reject an existing destination (including symlinks), stage output with mode 0600 in a mode-0700 directory, and use directory descriptors plus same-directory `linkat` for no-replace publication. Only errors that identify unsupported hard links trigger an anchored `renameat2(RENAME_NOREPLACE)` fallback; collisions, permission errors, and other failures do not. If no-replace rename is unsupported, publication fails closed. It discards oversized captures after terminating its direct strace process. It handles SIGINT, SIGTERM, SIGHUP, and SIGQUIT by terminating and reaping that child; parent death requests SIGKILL for strace. Traced descendants can still escape via `CLONE_UNTRACED`, and a system crash can leave a private staging directory behind. The destination parent is the canonicalized directory object opened at operation start; subsequent operations remain anchored to that object even if it is renamed. Filesystems must support either hard-link publication or `renameat2(RENAME_NOREPLACE)` for completed output publication.
- Render every trace-derived value as inert text in offline HTML. The current renderer escapes values into text nodes and uses a restrictive CSP with no script or remote assets; keep context-aware escaping, do not evaluate values as markup or script, and do not add network requests from a report.
- Keep raw evidence local and distinguish exact evidence from normalized or derived comparison fields.

Fake-tracer tests exercise argument construction, bounded FIFO recording, output collisions, symlink safety, and staging cleanup for pre-launch failures. Linux integration tests exercise real strace with fixed Python targets, including a child execution on the candidate side, temporary files, loopback-only TCP, a normal target exit code of 37, and target termination by SIGTERM; they require `strace` and `python3`. They check that traces are published before the reported target outcome is propagated. This follows strace's documented wrapper behavior but does not establish tracer success or capture completeness. The event test checks successful child `execve` evidence in either one complete row or a matching-PID unfinished/resumed pair, verifies the diff references the observed child row, checks that selected trace sentinels do not appear in captured command output, and removes its private temporary directory. CI stores no traces or reports as artifacts. HTML renderer and Linux CLI tests cover injection strings, control/bidi visibility, no remote assets, output limits, mode 0600, and no-clobber behavior. Before release, broader real-tracer testing must verify additional options, selected observations, output limits, and cleanup behavior; HTML still needs broader browser and accessibility review.

Trace text is already an untrusted input to `inspect`. The v1 bundle reader accepts only its fixed manifest and files; future import formats or schema versions require separate review before support.

## Reportable findings and severity context

Report security issues that demonstrate a concrete violation of a documented or planned invariant, for example:

- Report rendering executes trace-derived content or initiates a network request; or SideEffect itself makes an outbound request unrelated to the wrapped command and without user request.
- A crafted command argument, path, trace, or report value causes SideEffect to execute an unintended command, overwrite unrelated files, escape its selected output directory, or disclose local data to another party.
- An input bypasses parser or renderer resource limits and can cause a reproducible denial of service beyond the documented per-run limits.
- A vulnerability in the evidence handling path exposes command output, arguments, paths, or trace data outside the local user's intended access.

Severity depends on reachability and impact. The fact that the user intentionally ran a command does not make a separate SideEffect vulnerability acceptable; conversely, that command's expected actions under the user's permissions are not a SideEffect security finding by themselves.

## Out of scope and known limitations

SideEffect is not intended to prevent the chosen command from modifying files or accessing the network, identify malware, establish that a command is safe, capture every system interaction, or prove causation. These are product limitations, not vulnerabilities, provided the implementation does not make contrary claims or violate the invariants above. Sensitive values appearing in a local trace as a result of the selected capture are an acknowledged privacy risk; unexpected external disclosure or unsafe rendering is reportable.

The current comparison is a conservative parser-row diff, not a capture-completeness check or logical syscall reconstruction. One Linux real-tracer integration case observes a temporary file operation, a child `execve` attempt and successful return as either one row or a pair of continuation rows, and a loopback connection; a separate smoke test used `/usr/bin/true` and `/usr/bin/false`; lifecycle tests also use controlled fake executables, and parser/diff fixtures remain synthetic. HTML output is static and offline, but broad browser compatibility and accessibility remain unreviewed. Real `strace` compatibility beyond these narrow cases, other file/network-event coverage, and capture completeness remain unverified. The Linux/`strace` scope, incomplete observation possibilities, local raw-data exposure, absence of automatic redaction, and non-causal nature of event comparison are known product limitations that must remain visible in user-facing documentation.

## Reporting a vulnerability

**Private reporting is not currently available.** This repository is private, and GitHub's private vulnerability reporting feature is available only for public repositories. Before making the repository public, maintainers must decide on a private disclosure route. As part of the visibility transition, enable and verify GitHub private vulnerability reporting before announcing the project or inviting reports, then update this section with the working path. See GitHub's [private vulnerability reporting requirements](https://docs.github.com/en/code-security/how-tos/report-and-fix-vulnerabilities/configure-vulnerability-reporting/configure-for-a-repository). No security email address or other private channel is designated here.

Until a private channel is verified, do not post exploit details, sensitive traces, or unpublished vulnerability information in a public issue. Do not announce a security reporting route until maintainers have tested it.

When a verified channel is available, please include the affected commit or release, operating system and architecture, required tracer version, reproduction steps, and the impact you observed. Do not include real secrets or personal data in a report unless they are essential and you have arranged a private channel.

## Release security review

Before each public release, maintainers should verify the supported platform and `strace` range, parser limits and failure behavior, path handling, HTML escaping and offline behavior, data-retention guidance, and the private vulnerability reporting route. Release notes must distinguish implemented and tested behavior from known limitations and planned work.
